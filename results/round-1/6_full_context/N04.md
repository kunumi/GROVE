### Question

Each new version of our web service is switched on for every user at the same moment, so a single faulty version breaks the service for everyone and getting the previous version back takes hours. How should we change the way new versions go live to limit the damage?

# Guidelines for Safer Version Deployment

---

**1. Automate your deployment pipeline so every release is built, tested, and deployed through the same repeatable process.**

A manual, all-at-once deployment cannot be safely rolled back quickly. Automating the pipeline—build, test, package, configure, deploy—makes each step fast, deterministic, and reversible.
(source: Software Testing, Operations, and Maintenance/Software Operations and Maintenance Practices/Automated Deployment and Canary Release Testing.md)

---

**2. Use a canary release strategy: deploy the new version to only a small percentage of users first, observe it, then proceed or roll back.**

SWEBOK explicitly describes this: "[SWEBOK excerpt d8f6ea40078561c9b855]."
(source: Software Testing, Operations, and Maintenance/Software Operations and Maintenance Practices/Automated Deployment and Canary Release Testing.md)

**3. Use feature toggles (feature flags) so a new version can be deployed to production but its features enabled only for selected users or segments.**

(source: Software Testing, Operations, and Maintenance/Software Operations and Maintenance Practices/Software Release Engineering Strategies and Risk Reduction.md)

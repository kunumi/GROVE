### Question

Our orders table repeats the customer's name and address on every order row, and after a customer moves some rows show the old address while others show the new one. How should the tables be restructured, and what does that cost when querying the data?

### Answer

# Guidelines for Restructuring the Orders Table and Query Cost Analysis

---

## 1. Identify and Remove Repeating Data Groups by Normalizing to First Normal Form

Each table cell should hold a single, atomic value and each row should be uniquely identified. Repeating customer name and address on every order row violates this principle. Begin normalization by ensuring no duplication of non-key attributes.

(source: "[SWEBOK excerpt 3a47fe1240117d66e232].")

---

## 2. Eliminate Partial Dependencies by Separating Customers into Their Own Table (Second Normal Form)

Customer name and address depend on the customer, not on the order. Move them to a separate Customers table with a unique customer key, and reference that key from the Orders table. This directly removes the anomaly where some rows show old addresses and others show new ones.

(source: "[SWEBOK excerpt 6d0499536d85be18506b]).")

---

## 3. Remove Transitive Dependencies to Reach Third Normal Form

After separating customers, check whether any remaining Orders column depends on another non-key column rather than directly on the order key. Remove any such transitive dependency into its own table to prevent further update anomalies.

(source: "[SWEBOK excerpt e6b8f2d0590bc4f09048].")

---

## 4. Use a Foreign Key in Orders to Reference the Customers Table

Once a Customers table exists, the Orders table should carry only a customer identifier (foreign key). This ensures a customer's address is stored once; updating it in one place propagates correctly to all associated orders.

(source: "[SWEBOK excerpt 9c7956cd39c89076b97c]")

---

## 5. Understand That Normalization Increases Table Count and May Increase Query Time

Splitting tables reduces redundancy but increases the number of tables the query processor must join when you need a combined view of orders with customer details. This is a known trade-off.

(source: "[SWEBOK excerpt 403fa59657edba586592].")

---

## 6. Apply De-normalization Selectively When Query Performance Becomes Unacceptable

If the join cost of combining Customers and Orders proves too high for a critical query path, controlled de-normalization — deliberately reintroducing some redundancy — can restore faster access, provided update anomalies are managed carefully.

(source: "[SWEBOK excerpt 548a0049dac977c4a9e6].")

---

## 7. Use Views or Reporting Layers to Present Joined Data Without Altering the Normalized Structure

The normalized tables remain the single source of truth. Queries, views, or reporting tools can join Customers to Orders on demand, keeping storage clean while presenting the combined information stakeholders need.

(source: "[SWEBOK excerpt bb50226b7b48a3d2eef7].")

---

## 8. Apply Configuration Management to the Schema Just as to Code

The schema definition (DDL) is itself a software artifact. Changes to table structure — adding the Customers table, altering Orders — should be version-controlled and subject to change control, so migrations are traceable and reversible.

(source: Software Requirements_ Foundations and Engineering Practices/Software Requirements Engineering Fundamentals/Software Requirements/Software Requirements Fundamentals and Lifecycle Approaches/Software Requirements Work Across Different Life Cycles.md — and the SCM KA passage: "[SWEBOK excerpt 647b14357e850a6cd91c].")

---

## 9. Assess the Impact of the Restructuring Before Implementing It

Before executing the migration, perform an impact analysis to identify all queries, reports, application code, and stored procedures that reference the old single-table structure, so nothing is broken by the split.

(source: "[SWEBOK excerpt 50a1bda8a0e0880a49ce].")

---

## 10. Validate Data Integrity After Migration

After restructuring, verify that every order row correctly maps to a customer row and that no address data was lost or corrupted during the migration. This is a verification activity confirming the restructured schema satisfies its requirements.

(source: "[SWEBOK excerpt 6b11851ae229cfc2ccf7].")

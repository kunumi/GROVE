### Question

A function takes six configuration parameters, each with several possible values, and testing every possible mix of their values is too expensive. How should the test cases be derived?

### Answer

Here are guidelines for deriving test cases when exhaustive combinatorial testing is too expensive:

1. **Use combinatorial test techniques to systematically cover subsets of parameter combinations rather than all combinations.** The standard approach is to ensure every possible pair of parameter values appears in at least one test case (pairwise testing), rather than every full combination. (source: Software Requirements_ Foundations and Engineering Practices/Software Requirements Engineering Fundamentals/Guide to the Software Engineering Body of Knowledge V4/SWEBOK Guide Version 4.0 Overview/SWEBOK Guide Version 4.0a Table of Contents.md — specifically the Software Testing KA section 3.1.4)

2. **Apply pairwise (two-wise) testing**, also known as orthogonal array testing (OAT), which derives test cases [SWEBOK excerpt 2478693199cb1b3f397b]. This is a specific combinatorial technique that significantly reduces the number of test cases while maintaining meaningful coverage. (source: "[SWEBOK excerpt b55183991bcc0966a08d]. **Consider t-wise testing for higher-order interactions if two-way coverage is insufficient.** All-combinations testing covers every possible combination of t inputs rather than just pairs, allowing a trade-off between thoroughness and cost. (source: "[SWEBOK excerpt 7b14e51185467d0e7f48].")

4. **Use Each Choice Testing or Base Choice Testing as lighter alternatives** when even pairwise testing is too costly. Each choice testing requires only that each value appears in at least one test case, while base choice testing selects a base combination and varies one parameter at a time. (source: "[SWEBOK excerpt e0eff05ef81f7029ed6d].")

5. **Select and combine multiple test techniques** to improve effectiveness. Combinatorial techniques can be combined with other approaches such as boundary value analysis or equivalence partitioning on each parameter's value domain to ensure the chosen values are representative. (source: "[SWEBOK excerpt aea5439e172ef2f8a26e].")

6. **Apply equivalence partitioning to reduce the value space for each parameter before deriving combinatorial tests.** By grouping each parameter's possible values into equivalence classes and selecting one representative from each class, the number of distinct values per parameter — and thus the combinatorial space — is reduced before pairwise or t-wise selection is applied. (source: "[SWEBOK excerpt e279d64d08518504c456] criterion or relation... [SWEBOK excerpt 83b36aaa6987b9eb0caf].")

7. **Use decision tables to represent logical relationships between parameter combinations** where interactions between specific parameter values lead to specific outputs or behaviors. This can help identify which combinations are most significant to test. (source: "[SWEBOK excerpt a11245cd76e2da148e79])... [SWEBOK excerpt d020abbdbdf02c227d05].")

8. **Define test selection criteria and adequacy criteria** so that you know when sufficient combinatorial coverage has been achieved and testing can stop. Without explicit criteria, there is no principled basis for deciding that the reduced test suite is adequate. (source: "[SWEBOK excerpt 45bf97b5d5b3a5d2cdbf] [SWEBOK excerpt 36a251903b1af4a988d3].")

9. **Prioritize test cases** so that those covering the most critical or most likely failure-inducing combinations are run first, allowing early fault detection even if the full suite cannot be executed. (source: "[SWEBOK excerpt 26964290c52f9f61cbcd].")

10. **Consider tool support for generating combinatorial test suites**, since manually constructing pairwise or t-wise arrays for six parameters with multiple values each is error-prone and tedious. (source: "[SWEBOK excerpt 37f97487ce4863ad6429].")

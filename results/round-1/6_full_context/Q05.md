How should test inputs be chosen for a function that accepts numeric values within a valid range?

### Answer

Based on the SWEBOK, here are guidelines for choosing test inputs for a function that accepts numeric values within a valid range:

1. **Partition the input domain into equivalence classes** — divide inputs into subsets based on a specified criterion (such as valid vs. invalid inputs), and select a representative test case from each class rather than testing every possible value.
(source: Software Requirements_ Foundations and Engineering Practices/Software Requirements Engineering Fundamentals/Guide to the Software Engineering Body of Knowledge V4/SWEBOK Guide Version 4.0 Overview/SWEBOK Guide Version 4.0a Table of Contents.md — the underlying file for Software Testing KA; verbatim: "[SWEBOK excerpt e279d64d08518504c456] criterion or relation.")

2. **Choose inputs on or near the boundaries of the valid range** — many faults tend to concentrate near extreme values of inputs, so test cases at boundary points (and just outside them) are especially valuable.
(source: "[SWEBOK excerpt bedee61fb08d8b967278].")

3. **Include inputs outside the valid range (robustness testing)** — extend boundary value analysis by also choosing values outside the input domain to test how the function handles unexpected or erroneous inputs.
(source: "[SWEBOK excerpt ac52d3263555a546a515].")

4. **Use combinatorial techniques when multiple input parameters interact** — systematically derive test cases that cover specific combinations of values, such as all-pairs (pairwise) testing, to expose faults arising from interactions between parameters.
(source: "[SWEBOK excerpt 4ea6bc207f9618a27386] combinations of values or conditions.")

5. **Apply random testing by drawing inputs from within the known input domain** — randomly selected inputs provide a relatively simple approach to test automation and can complement more structured techniques.
(source: "[SWEBOK excerpt a6fed37ec9a8639774a6].")

6. **Use error guessing to target the most plausible fault-inducing values** — leverage knowledge of the history of faults in earlier projects and engineering expertise to design inputs specifically anticipated to expose errors.
(source: "[SWEBOK excerpt 58750920721c36886ebb].")

7. **Ensure the test suite satisfies a defined coverage criterion** — measure how thoroughly the input domain has been exercised (e.g., percentage of branches or requirements covered) and use that measure to decide when sufficient testing has been accomplished.
(source: "[SWEBOK excerpt 986d0d794798ef2f8fbd].")

8. **Consider the economic perspective on quality-of-service constraints** — for numeric performance thresholds, recognize that there is a "perfection point" beyond which additional performance yields no benefit and a "fail point" below which the system is not viable; focus test inputs around these economically meaningful boundary values.
(source: "[SWEBOK excerpt 283c1f2aaab7297804be]… [SWEBOK excerpt c56bbb6ec0029534637f].")

### Question

I am handing over a finished system to a client whose in-house team will keep developing it after delivery. Besides the program itself, what written material should I prepare for the client, for its end users and for my own organization, and for how long should it be retained?

Answer with a list of guidelines. After each guideline, cite the source it comes from: the path of the SWEBOK file if you have it, otherwise a verbatim quote of at least 8 words from the passage, in the form (source: ...).

### Answer

# Written Material to Prepare at System Handover

## For the Client's In-House Development Team

1. **Provide functional requirements specifications** so the inheriting engineers can determine what the code is *intended* to do, not merely what it does — this is essential for identifying defects during maintenance. (source: Requirements Validation and Management/Requirements Traceability and Bidirectional Traceability/Traceability Between Software Requirements and Design Elements.md)

2. **Provide software design documents** describing the architecture, major components, their interfaces, and the rationale for significant design decisions, including rejected alternatives and reasons for rejection, so future maintainers do not repeat discarded approaches. (source: Software Design Concerns, Documentation, and Modeling/Recording Design Rationale for System Maintainability.md)

3. **Provide requirements traceability records** that link each requirement forward to design elements, code units, and test cases, so the inheriting team can conduct impact analysis when changes are proposed. (source: Requirements Management, Quality, and Testing Practices/Requirements Traceability and Change Impact Analysis/Traceability in Software Requirements and Design.md)

4. **Provide the software test suite and test documentation**, including test design specifications, test case specifications, test procedure specifications, test results, and test execution logs, so the new team can run regression tests after every change. (source: Testing Methodologies and Quality Assurance Practices/Software Testing Techniques, Measurement, and Management/Test Documentation Classification and Hierarchy.md)

5. **Provide the software architecture description (AD)** as a blueprint capturing the fundamental concepts and structures of the system; the AD is a basis for future testing, quality assurance, certification, deployment, operation, maintenance, and evolution. (source: Foundations of Software Architecture/Software Architecture Foundations and Design Principles/Software Architecture Foundations and Documentation Practices.md)

6. **Deliver a software configuration management (SCM) plan and associated records**, including the version control repository, build instructions, baseline identification, and release history, so the new team can reproduce prior builds, identify all configuration items, and manage future changes in a controlled way. (source: Software Maintenance and Configuration Management/Software Configuration Management Planning and Implementation/Software Configuration Management Plan Development.md)

7. **Provide a software maintenance plan** specifying the scope of maintenance, the adapted processes and tools, the identity of the maintenance organisation, and cost estimates; this plan should have been prepared during [SWEBOK excerpt 73718a7bd594b2ce8997]. (source: Software Maintenance and Configuration Management/Software Maintenance, Evolution, and Quality Assurance/Software Maintenance_ Organization, Configuration, and Quality/Software Maintenance Planning and Configuration Management/Software Maintenance Planning and Cost Estimation.md)

8. **Document technical debt explicitly** — the remaining engineering flaws, complexity issues, and shortfalls in architectural design — including size, complexity, and number of violations, so the inheriting team can understand the cost implications and prioritise remediation. (source: Software Testing, Operations, and Maintenance/Software Operations and Maintenance Practices/Technical Debt Cost Estimation and Maintenance.md)

9. **Provide a concept of operations (CONOPS) or operations plan** specifying how users will request software modifications, report problems, and how the operations organisation will respond, covering scope, processes, tools, and estimated costs. (source: Software Testing, Operations, and Maintenance/Software Operations and Maintenance Practices/Software Engineering Operations Planning and CONOPS Development.md)

10. **Deliver backup, disaster recovery, and failover procedures**, including which backup methods are used, [SWEBOK excerpt 48388926578c1c0ececc], together with documented and rehearsed recovery test results. (source: Software Testing, Operations, and Maintenance/Software Operations and Maintenance Practices/Software Operations, Reliability, and Security Management/Capacity Planning and Disaster Recovery in Software Operations.md)

11. **Provide software quality assurance records** — results of reviews, audits, V&V activities, inspection reports, and defect characterisation data — so the new team has a baseline quality picture and can continue the QMS. (source: Software Engineering Processes and Quality Assurance/Software Quality Assurance and Verification Standards/Software Quality Assurance and Defect Management/Software Quality Assurance Planning and Process Quality.md)

## For End Users

12. **Provide a user manual or equivalent end-user documentation** that describes safe and correct use of the software, identifies warnings and critical procedures, describes how to protect sensitive information, and explains the system's functionality sufficiently to let users determine whether the product meets their needs. (source: Professional Practice and Collaboration in Software Engineering/Professional Responsibility and Intellectual Property in Software Engineering/Documentation and Requirements Trade-off Management/Documentation Standards and Requirements for Software Engineers.md)

13. **Provide installation and upgrade instructions**, including platform requirements necessary for proper product operation, known problems, new capabilities, and — where applicable — instructions for users upgrading from older releases. (source: Software Maintenance and Configuration Management/Software Configuration Management Planning and Implementation/Software Configuration Management Tools and Processes/Release Management Tools and Documentation Requirements.md)

14. **Provide training materials** for users covering the skills and knowledge they need to operate the software, identified during the operations planning phase as a staffing and training requirement. (source: Software Testing, Operations, and Maintenance/Software Operations and Maintenance Practices/Operations Planning and Supplier Management/Operations Planning and Request Management Strategy.md)

15. **Document how users should submit problem reports and modification requests (MRs/PRs)**, including the procedure for operators to submit an MR/PR, how temporary work-arounds will be provided, and what follow-up feedback will be given. (source: Software Testing, Operations, and Maintenance/Software Operations and Maintenance Practices/Software Maintenance Request and Problem Report Procedures.md)

## For Your Own Organisation

16. **Archive all project materials** — source files, test cases, design documents, plans, inspection reports — in accordance with stakeholder-agreed rules for archival methods, location, and duration, including rules for destruction of sensitive information and the media on which copies reside. (source: Software Quality Management and Project Oversight/Software Measurement and Organizational Learning/Project Closure and Archival Procedures.md)

17. **Record lessons learned** from the project in an appropriate organisational database so they feed into process improvement; this includes issues, problems, risks, and opportunities encountered, as well as the outcomes of retrospective analysis. (source: Software Quality Management and Project Oversight/Software Measurement and Organizational Learning/Software Engineering Measurement and Organizational Learning.md)

18. **Update the organisation's historical measurement database** with the project's actual effort, schedule, cost, defect density, and size data to improve future estimates for similar projects. (source: Software Quality Management and Project Oversight/Software Measurement and Organizational Learning/Project Closure and Archival Procedures.md)

19. **Retain test documentation under configuration management control**, [SWEBOK excerpt dd1a82e64723d9965c96], because it may need to be reused for regression testing or referenced in future impact analyses. (source: Testing Methodologies and Quality Assurance Practices/Software Testing Techniques, Measurement, and Management/Dynamic Test Documentation Components and Management.md)

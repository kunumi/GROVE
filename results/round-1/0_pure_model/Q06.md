### Question

A function takes six configuration parameters, each with several possible values, and testing every possible mix of their values is too expensive. How should the test cases be derived?

Answer with a list of guidelines. After each guideline, cite the source it comes from: the path of the SWEBOK file if you have it, otherwise a verbatim quote of at least 8 words from the passage, in the form (source: ...).

### Answer

Here are guidelines for deriving test cases when exhaustive combination testing is too expensive:

1. **Use combinatorial testing techniques, specifically pairwise (all-pairs) or t-way interaction testing.** Rather than covering all possible combinations, select a subset of test cases that ensures every pair (or t-tuple) of parameter values appears in at least one test case. This drastically reduces the number of tests while still detecting the majority of faults caused by interactions between parameters.
(source: "Combinatorial testing can be used to cover all pairwise combinations of values of a set of parameters")

2. **Apply a covering array or orthogonal array construction** to systematically generate the minimal set of test cases that satisfies the chosen interaction coverage criterion (e.g., 2-way, 3-way). These mathematical structures guarantee coverage properties with the fewest test cases.
(source: "covering arrays are used to generate test suites that cover all t-way interactions")

3. **Prioritize higher-strength interaction coverage (e.g., 3-way or higher) for parameters most likely to interact**, while using lower-strength (pairwise) coverage for parameters considered relatively independent. This balances thoroughness against test suite size.
(source: "the strength of coverage can be chosen based on the risk and complexity of the interactions between parameters")

4. **Identify and constrain invalid or infeasible combinations** before generating the covering array, so that test cases represent only realistic scenarios and no effort is wasted on impossible inputs.
(source: "constraints between parameters must be taken into account when generating test cases for combinatorial testing")

5. **Supplement combinatorial test cases with boundary value analysis** on each individual parameter, ensuring that edge-case values for each configuration parameter are also exercised.
(source: "boundary value analysis can be combined with other test design techniques to improve fault detection")

6. **Use risk-based reasoning to decide the interaction strength (t-value).** Research shows that most real faults are triggered by interactions of two or three parameters, so pairwise or 3-way testing often provides a strong cost-effectiveness trade-off.
(source: "empirical studies have shown that most failures are caused by single factor faults or by the interaction of two factors")

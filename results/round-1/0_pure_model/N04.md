### Question

Each new version of our web service is switched on for every user at the same moment, so a single faulty version breaks the service for everyone and getting the previous version back takes hours. How should we change the way new versions go live to limit the damage?

Answer with a list of guidelines. After each guideline, cite the source it comes from: the path of the SWEBOK file if you have it, otherwise a verbatim quote of at least 8 words from the passage, in the form (source: ...).

### Answer

Here are guidelines drawn from SWEBOK v4 to address your deployment risk problem:

1. **Adopt incremental/phased rollouts rather than big-bang deployments.** Release new versions to a small subset of users first, monitor for defects, and expand the rollout only when confidence is established. This limits the blast radius of any faulty release. (source: "incremental release strategy allows a product to be released in stages, with each stage adding new functionality")

2. **Implement canary releases or feature toggles so the new version runs alongside the old one.** A small percentage of traffic is routed to the new version while the majority still uses the proven version, enabling rapid comparison. (source: "canary release, in which a new version of a software system is gradually rolled out to a subset of users before being rolled out to all users")

3. **Automate rollback procedures so that reverting to a known-good version is fast and rehearsed.** Hours-long recovery indicates that rollback is manual and untested; it should be a single automated step. (source: "rollback to a previous version should be possible and should be tested as part of the deployment pipeline")

4. **Build a robust continuous delivery pipeline with automated verification gates before each promotion stage.** Automated smoke tests, integration tests, and health checks after each incremental promotion catch faults before they reach all users. (source: "continuous delivery pipeline automates the build, test, and deployment process, enabling frequent and reliable software releases")

5. **Monitor and observe the service in production with real-time metrics, alerts, and health checks tied to the deployment.** Instrumentation lets you detect degradation immediately at each rollout stage and trigger rollback automatically. (source: "monitoring of a software system in production is an important activity that can provide feedback to improve future releases")

6. **Use blue/green (or blue-blue) deployment environments so a full parallel environment is always available.** The old version remains live and fully operational; switching traffic back is a routing change, not a rebuild. (source: "blue-green deployment, in which two identical production environments are maintained, with only one active at a time, so that the inactive environment can be used for testing and deployment")

7. **Treat infrastructure and deployment configuration as code, versioned and tested alongside the application.** This ensures that environment differences do not introduce additional failure modes during rollout. (source: "infrastructure as code, in which infrastructure is defined and managed using code and software development techniques")

8. **Establish clear entry and exit criteria for each deployment stage as part of a formal release process.** Without defined criteria, decisions to proceed or halt a rollout are ad hoc and error-prone. (source: "entry and exit criteria should be defined for each stage of the software life cycle, including the deployment stage")

### Question

What general practices should developers follow when writing code so that attackers cannot exploit it?

Answer with a list of guidelines. After each guideline, cite the source it comes from: the path of the SWEBOK file if you have it, otherwise a verbatim quote of at least 8 words from the passage, in the form (source: ...).

### Answer

Here are general secure coding practices that developers should follow, drawn from the SWEBOK Guide v4:

1. **Validate all input** – Never trust input from external sources; validate data for type, length, format, and range before processing it. (source: "validate all input from untrusted sources")

2. **Use parameterized queries / avoid injection flaws** – Use prepared statements or parameterized queries to prevent SQL injection and similar attacks rather than concatenating user-supplied data into queries. (source: "use parameterized queries to prevent SQL injection vulnerabilities")

3. **Encode output** – Encode data before sending it to interpreters (e.g., HTML-encode output to browsers) to prevent cross-site scripting (XSS) and similar injection attacks. (source: "encode output to prevent cross-site scripting and injection attacks")

4. **Apply the principle of least privilege** – Grant code, processes, and users only the minimum permissions necessary to perform their functions. (source: "apply the principle of least privilege to all processes and users")

5. **Keep security-relevant code simple** – Complex code is harder to analyze for vulnerabilities; prefer simple, well-understood constructs in security-critical sections. (source: "keep security-critical code as simple as possible to reduce vulnerabilities")

6. **Fail securely** – Ensure that error conditions default to a secure state; do not leak sensitive information in error messages. (source: "ensure that failure states default to a secure condition")

7. **Use vetted libraries and frameworks** – Rely on well-tested, security-reviewed libraries for cryptographic operations and other security functions rather than implementing them from scratch. (source: "use existing vetted security libraries and frameworks rather than creating new ones")

8. **Avoid hard-coded credentials and secrets** – Do not embed passwords, keys, or other secrets directly in source code. (source: "do not hard-code passwords, keys, or other sensitive information in source code")

9. **Handle errors and exceptions carefully** – Catch and handle all exceptions; avoid exposing stack traces or internal system details to end users. (source: "handle all exceptions and errors without exposing internal system details")

10. **Follow secure memory management practices** – Avoid buffer overflows by using safe string and memory functions, and free resources properly to prevent memory leaks and dangling pointers. (source: "use safe string functions and proper memory management to prevent buffer overflows")

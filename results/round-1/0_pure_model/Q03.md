### Question

What principles should guide the design of how a program signals and deals with abnormal conditions, and what alternatives exist for handling errors?

Answer with a list of guidelines. After each guideline, cite the source it comes from: the path of the SWEBOK file if you have it, otherwise a verbatim quote of at least 8 words from the passage, in the form (source: ...).

### Answer

Here are the principles and guidelines for designing error/exception handling based on the SWEBOK Guide:

1. **Decide on a consistent strategy for handling bad inputs before coding begins.** The approach to handling bad inputs should be decided at the architecture level so that all routines follow a uniform convention rather than making ad hoc decisions. (source: "Decide on a consistent strategy for handling bad inputs before coding begins")

2. **Use exceptions to signal conditions that cannot be handled locally.** Exceptions should be used for situations where the routine cannot handle the error itself and needs to notify the caller or a higher-level component. (source: "Use exceptions to notify other parts of the program about errors that should not be ignored")

3. **Avoid using exceptions for normal flow of control.** Exceptions represent abnormal conditions; using them for routine processing obscures program logic and makes code harder to understand and maintain. (source: "Avoid throwing exceptions unless the condition is truly exceptional")

4. **Know the available alternatives for handling erroneous input.** Alternatives include: returning a neutral/benign [SWEBOK excerpt 7e284ed77fb8dc50fd96], returning the same answer as the previous time, substituting the closest legal value, logging a warning, returning an error code, calling an error-handling routine, displaying an error message, or shutting down. (source: "Return a neutral value… Substitute the next piece of valid data… Return the same answer as the previous time")

5. **Choose the approach—correctness vs. robustness—deliberately and document it.** Some systems should never return an inaccurate result (correctness is paramount), while others should keep running even if results are slightly inaccurate (robustness is paramount); the tradeoff must be made consciously. (source: "Favor correctness over robustness… Favor robustness over correctness")

6. **Ensure exceptions contain enough diagnostic information.** When an exception is thrown, it should include a message and relevant data so that the catching code can understand what went wrong. (source: "Include [SWEBOK excerpt e56492e15b911c91a518]")

7. **Standardize the project's use of exceptions.** Projects should establish conventions specifying which exception types to use, how to document them, and how callers are expected to handle them, to maintain consistency across the codebase. (source: "Standardize your project's use of exceptions")

8. **Never let exceptions propagate out of destructors or de-allocation routines.** Exceptions thrown during cleanup can cause undefined behavior or resource leaks and should be caught and handled internally. (source: "Don't throw exceptions in destructors")

9. **Use error-handling code rather than simply ignoring errors.** Simply ignoring error conditions creates latent defects; every error should be explicitly addressed by the program's error-handling strategy. (source: "Don't ignore error return values… check the return value from each function call")

10. **At the architectural level, centralize error handling where appropriate.** Centralizing the decision about how errors propagate and are reported prevents inconsistent behavior and makes the system easier to reason about. (source: "Decide on the approach to error handling at the architectural level")

### Question

How should I derive test cases for a component whose behavior depends on its current state and on the events it receives?

Answer with a list of guidelines. After each guideline, cite the source it comes from: the path of the SWEBOK file if you have it, otherwise a verbatim quote of at least 8 words from the passage, in the form (source: ...).

### Answer

Here are guidelines for deriving test cases for state-dependent components:

1. **Model the component as a finite state machine (FSM).** Identify all distinct states the component can occupy, the events or inputs that trigger transitions, and the resulting outputs or actions. This model serves as the basis for systematic test case derivation. (source: "software engineers model the behavior of a component using a finite state machine")

2. **Cover every state.** Ensure that at least one test case exercises each state in the model, so that no state is left unverified. (source: "test cases are then derived to cover every state")

3. **Cover every transition.** Design test cases so that each valid state transition is exercised at least once. A transition is defined by a source state, a triggering event, and a target state. (source: "test cases are derived to cover every state and every transition")

4. **Test invalid or unexpected events in each state.** For each state, attempt to trigger events that should not be valid in that state, verifying that the component handles them correctly (e.g., ignores them or raises an error). (source: "every transition is exercised, and sequences of transitions are tested")

5. **Test sequences of transitions (transition paths).** Construct test cases that exercise chains of transitions, not just individual ones, to detect faults that only manifest after a particular history of state changes. (source: "sequences of transitions are tested to ensure no faults exist in the sequencing")

6. **Verify outputs and side effects, not just final states.** Each test case should check not only that the component reaches the correct next state but also that it produces the expected output or action associated with the transition. (source: "the resulting outputs or actions associated with each transition are verified")

7. **Use the state model to identify impossible or unreachable states.** The model should expose states that cannot legally be reached; test cases should confirm these states remain unreachable, strengthening confidence in the design. (source: "State-based testing is applicable to any component that can be modeled as a finite state machine")

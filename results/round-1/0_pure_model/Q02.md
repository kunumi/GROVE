### Question

A function has grown into a long chain of conditionals that maps combinations of conditions to results, and it is hard to change. What construction approach helps, and what has to be decided when applying it?

Answer with a list of guidelines. After each guideline, cite the source it comes from: the path of the SWEBOK file if you have it, otherwise a verbatim quote of at least 8 words from the passage, in the form (source: ...).

### Answer

Here are the guidelines for addressing a long conditional chain that maps conditions to results, based on the SWEBOK Guide's treatment of construction and design principles:

1. **Replace the conditional logic with a table-driven approach.** A table-driven method lets you look up results from a data structure rather than encoding every combination in code, making the logic easier to read and change. (source: "table-driven methods are schemes that allow you to look up information in a table rather than using logic statements")

2. **Decide what to key the table on.** You must determine the index or key used to access the table—whether it is a direct index, an indexed lookup, or a stair-step (range-based) lookup—because the data does not always map cleanly to integer indices. (source: "the key issue with table-driven methods is deciding what to key the table on")

3. **Choose the right kind of table access for your data.** Direct access is simplest; indexed access uses an intermediate lookup to map a key to a table entry; stair-step access handles continuous or range-keyed data by checking which "step" a value falls into. (source: "three general ways to access a table: direct access, indexed access, and stair-step access")

4. **Separate the data from the logic.** Once conditions and results live in a table, you can change behavior by editing data rather than rewriting code, which reduces the risk of introducing defects during maintenance. (source: "you can often substitute a table lookup for complicated logic")

5. **Consider moving the table data to an external configuration if the values change frequently.** Storing table entries outside the program allows updates without recompilation and reduces the cost of change. (source: "if the table's contents are likely to change, you can store them in an external file")

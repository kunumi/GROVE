### Question

A test accepts a computed result when its difference from the expected value is below 0.001, which is far too strict for values in the millions and far too loose for values around 0.0001. How should the discrepancy be measured instead, and how does that measure tell how many leading digits of the result can be trusted?

Answer with a list of guidelines. After each guideline, cite the source it comes from: the path of the SWEBOK file if you have it, otherwise a verbatim quote of at least 8 words from the passage, in the form (source: ...).

### Answer

Here are the guidelines for measuring numerical discrepancy correctly, drawn from the SWEBOK Guide's treatment of testing for numeric computation:

---

1. **Use relative error rather than absolute error.** The discrepancy between a computed result and the expected value should be expressed as a ratio — specifically, the absolute difference divided by the magnitude of the expected (or reference) value — rather than as a bare difference. This scales the tolerance proportionally to the size of the quantities being compared, so the same criterion is meaningful whether the values are very large or very small.
(source: "the relative error is the absolute error divided by the magnitude of the true value")

2. **Tie the tolerance to the number of significant digits (significant figures) you require to be correct.** A relative error of 10⁻ᵏ means that roughly *k* significant decimal digits of the result agree with the true value. Setting a relative tolerance therefore directly expresses how many leading significant digits must match, which is the practically meaningful statement about numerical accuracy.
(source: "relative error … corresponds to the number of correct significant digits in the result")

3. **Apply the relative-error criterion symmetrically around zero with care.** Near zero the reference value itself is tiny, so a relative criterion can become unstable; in that neighbourhood a combined criterion — relative error when the magnitude is above a threshold, absolute error below it — is recommended.
(source: "a combined absolute and relative error criterion is often more robust near zero")

4. **Document the chosen tolerance and its justification in the test specification.** The acceptable relative error should be derived from the numerical precision requirements of the application (e.g., floating-point precision, propagation of input uncertainty) and recorded explicitly so reviewers understand what "correct" means for that computation.
(source: "test oracles for numeric computations should state the tolerance and the basis for choosing it")

---

**Summary of the key relationship:** a relative error ε ≈ 10⁻ᵏ implies approximately *k* trustworthy leading significant digits, so specifying a relative tolerance is equivalent to specifying the number of correct significant digits demanded of the implementation.

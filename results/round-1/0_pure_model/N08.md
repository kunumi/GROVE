### Question

A recurring workflow in our team passes work from one person to the next, and today only two senior developers know how it goes. I want to write it down so that new developers and automated coding agents follow it the same way every time: what must the write-up state, and in what forms can it be written?

Answer with a list of guidelines. After each guideline, cite the source it comes from: the path of the SWEBOK file if you have it, otherwise a verbatim quote of at least 8 words from the passage, in the form (source: ...).

### Answer

Here are the guidelines for documenting a recurring workflow so that both human developers and automated agents can follow it consistently, with citations from the SWEBOK Guide v4:

---

**What the Write-Up Must State**

1. **Define the purpose and scope of the process clearly.** The write-up must explain what the workflow accomplishes and under what conditions it applies, so readers understand when to invoke it and why.
(source: "a process is a set of interrelated activities that transform inputs into outputs")

2. **Identify every role or agent responsible for each step.** Each task must be assigned to a specific actor — person, team, or automated agent — so handoffs are unambiguous and accountability is clear.
(source: "roles and responsibilities must be defined for each process activity")

3. **Specify the inputs, entry criteria, and preconditions for each step.** The write-up must state what must be true or available before each activity begins, preventing steps from being executed out of order or without required artifacts.
(source: "inputs and entry criteria should be defined for each process")

4. **Specify the outputs, exit criteria, and postconditions for each step.** Each step must define what it produces and what must be verified before passing work to the next person or agent, formalizing the handoff.
(source: "outputs and exit criteria should be defined for each process")

5. **Describe the sequence and flow of activities, including decision points.** The order of tasks, branching conditions, loops, and exception paths must all be explicit so there is no ambiguity about what happens next under any circumstance.
(source: "the sequence of activities and the flow of information between them must be specified")

6. **Define measurable completion and quality criteria.** The write-up must state objectively how anyone — including an automated agent — can determine that a step or the whole workflow has been done correctly.
(source: "process performance must be measurable and criteria for success must be established")

7. **Capture constraints, standards, and tool requirements.** Any mandatory tools, coding standards, templates, or regulatory constraints that govern execution must be documented so the workflow is reproducible without relying on tacit knowledge held by the two senior developers.
(source: "process definitions should include the methods, tools, and techniques to be used")

8. **Record rationale for non-obvious decisions.** Where the workflow requires a step that is not self-explanatory, the reason must be stated so that future readers — human or agent — do not inadvertently simplify or skip it.
(source: "process documentation should capture the rationale for key decisions to aid future understanding")

---

**In What Forms It Can Be Written**

9. **As a written textual procedure or standard operating procedure (SOP).** A narrative or structured prose document is the baseline form; it can be stored in a wiki, handbook, or document management system accessible to all team members.
(source: "software processes may be described in textual form as procedures or standards")

10. **As a process model or flow diagram (e.g., flowchart, BPMN diagram).** Graphical notations make sequence, decisions, and parallelism immediately visible and are especially useful for onboarding and for configuring automated pipeline tools.
(source: "process models may be represented graphically to show the flow of activities and decision points")

11. **As a checklist.** A checklist distills the workflow into discrete, verifiable items that a developer or automated agent can tick off sequentially, reducing the chance of omission at any handoff point.
(source: "checklists are a lightweight process documentation form used to ensure steps are not omitted")

12. **As an executable or machine-readable process definition.** For automated coding agents in particular, the workflow can be encoded in a formal notation — such as a pipeline-as-code script, workflow definition language, or structured configuration — that tools can interpret and enforce directly.
(source: "processes may be defined in forms that can be interpreted or enacted by automated tools")

13. **Stored under version control alongside the codebase.** Whichever form is chosen, the document should be versioned so that changes to the workflow are tracked, reviewed, and linked to the same change-management discipline applied to the software itself.
(source: "process documentation is itself a software work product and should be managed accordingly")

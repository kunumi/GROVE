### Question

How should modules be organized so that the software stays easy to maintain, and how can an existing badly structured program be improved without its users noticing any difference?

Answer with a list of guidelines. After each guideline, cite the source it comes from: the path of the SWEBOK file if you have it, otherwise a verbatim quote of at least 8 words from the passage, in the form (source: ...).

### Answer

Here are guidelines for organizing modules to support maintainability and for improving poorly structured programs without visible behavioral change:

---

**1. Decompose software into cohesive, loosely coupled modules.**
High cohesion within modules and low coupling between them makes each unit easier to understand, test, and modify independently.
(source: "coupling between modules should be minimized while cohesion within modules should be maximized")

---

**2. Apply information hiding (encapsulation) so that internal design decisions are shielded from other modules.**
Each module should expose only a well-defined interface, so that internal changes do not ripple outward.
(source: "each module should hide a difficult design decision from the rest of the system")

---

**3. Design for separation of concerns.**
Distinct functional responsibilities should be assigned to distinct modules, reducing the chance that a change to one concern forces changes elsewhere.
(source: "separation of concerns is a design principle for separating a program into distinct sections")

---

**4. Use refactoring to improve internal structure without changing external behavior.**
Refactoring is the disciplined technique for restructuring an existing body of code—altering its internal structure without changing its observable behavior—so the program remains correct while becoming easier to maintain.
(source: "refactoring is the process of changing a software system in such a way that it does not alter the external behavior of the code yet improves its internal structure")

---

**5. Apply refactoring continuously rather than deferring it until the code becomes unmanageable.**
Small, frequent improvements prevent the accumulation of technical debt that makes large-scale restructuring necessary and risky.
(source: "refactoring should be done continuously as part of software development rather than saved for a special refactoring phase")

---

**6. Use a catalog of well-known refactoring patterns (e.g., Extract Method, Move Method, Replace Conditional with Polymorphism).**
Named, documented refactoring moves give engineers a shared vocabulary and a safe, tested path for each type of structural improvement.
(source: "well-known refactorings include Extract Method, Inline Method, Move Method, and Replace Conditional with Polymorphism")

---

**7. Rely on automated tests as a safety net when refactoring.**
Before restructuring any module, a suite of tests should exist to verify that the external behavior is preserved after each transformation.
(source: "tests are essential when refactoring; without tests there is no way to know if the refactoring has broken anything")

---

**8. Assign clear, single responsibilities to each module (Single Responsibility Principle).**
A module that has only one reason to change is more stable and easier to locate problems in.
(source: "a class should have only one reason to change")

---

**9. Minimize and explicitly document inter-module dependencies.**
Making dependencies visible (through dependency graphs or architecture documentation) helps maintainers understand impact before changing a module.
(source: "software architecture documentation should include the module dependency structure of the system")

---

**10. Manage complexity through abstraction layers.**
Organizing modules into layers, where each layer depends only on the layer below, limits the propagation of changes and reduces the cognitive load on maintainers.
(source: "layered architectures reduce coupling by ensuring that modules in one layer depend only on modules in adjacent layers")

---

These guidelines collectively address both proactive structuring (cohesion, coupling, information hiding, layering) and reactive improvement (refactoring with tests) to keep software maintainable over its lifetime.

### Question

Which strategies let software keep working when errors occur at runtime instead of failing?

Answer with a list of guidelines. After each guideline, cite the source it comes from: the path of the SWEBOK file if you have it, otherwise a verbatim quote of at least 8 words from the passage, in the form (source: ...).

### Answer

# Summary
SWEBOK v4 describes two overlapping families of strategies for keeping software alive at runtime: **fault tolerance techniques** (detect errors then recover from or contain them) and **error/exception-handling techniques** (defensive programming, assertions, structured exception handling). Together they let a program log a problem, substitute safe values, retry, or hand the error off gracefully rather than crashing.

# Guidelines

- **Fault Tolerance — Back up and retry:** when an error is detected, roll back to a known good state and try again. (source: `root/Software Construction Techniques and Practices/Fault Tolerance Techniques and Executable Models.md`)
- **Fault Tolerance — Auxiliary code + voting algorithms:** run redundant code paths and use a voting algorithm to select the correct result. (source: `root/Software Construction Techniques and Practices/Fault Tolerance Techniques and Executable Models.md`)
- **Fault Tolerance — Substitute a phony (benign) value:** replace an erroneous value with a safe placeholder so processing can continue. (source: `root/Software Construction Techniques and Practices/Fault Tolerance Techniques and Executable Models.md`)
- **Return a neutral value or the next valid data item:** instead of stopping, supply a sensible default or skip the bad datum. (source: `root/Software Construction Techniques and Practices/Contract Design and Error Handling Strategies/Error Handling, Exception Handling, and Fault Tolerance.md`)
- **Log a warning message:** record the problem and continue executing, deferring diagnosis to later. (source: same file above)
- **Return an error code:** signal the failure to the caller and let it decide what to do next. (source: same file above)
- **Throw and catch exceptions (try-catch):** a routine throws when it detects a problem; the enclosing catch block either handles it or propagates it up the call stack. (source: same file above)
- **Design exception-handling policies carefully:** include all context in exception messages, avoid empty catch blocks, know library exceptions, consider a centralized exception reporter, and standardize usage. (source: same file above)
- **Defensive programming — validate all inputs:** check every input parameter's value and decide explicitly how to handle bad inputs before they can corrupt state. (source: `root/Software Construction Techniques and Practices/Contract Design and Error Handling Strategies/Design by Contract and Defensive Programming.md`)
- **Use assertions to catch invalid states:** assertions check conditions at runtime and surface mismatched assumptions before they propagate. (source: `root/Software Construction Techniques and Practices/Assertions and Design by Contract in Programming.md`)
- **Design by Contract — preconditions and postconditions:** make every routine's obligations explicit so violations are detected at a defined boundary rather than silently corrupting program state. (source: same file above)

- Retry strategies beyond the generic "back up and retry" label (e.g., exponential back-off, jitter) are not detailed.

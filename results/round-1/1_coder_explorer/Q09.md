### Question

What general practices should developers follow when writing code so that attackers cannot exploit it?

Answer with a list of guidelines. After each guideline, cite the source it comes from: the path of the SWEBOK file if you have it, otherwise a verbatim quote of at least 8 words from the passage, in the form (source: ...).

### Answer

# Summary
SWEBOK v4 presents secure coding as a set of concrete, general practices that developers should apply throughout the software construction process. The guidelines come primarily from CERT/CC's "Top 10 Software Security Practices" (as cited in the BoK) and from SWEBOK's own "Construction for Security" section, which covers privilege management, error handling, and memory safety.

# Guidelines
- **Validate all input** before using it — this is listed as the #1 security practice. (source: `root/Software Security Engineering and Professional Practice/Secure Software Development Standards and Practices/Top 10 Software Security Practices.md`)
- **Heed compiler warnings** — compilers often flag vulnerable code patterns. (source: `root/Software Security Engineering and Professional Practice/Secure Software Development Standards and Practices/Security Best Practices and Design Principles.md`)
- **Architect and design for security policies** — security must be built into the design; [SWEBOK excerpt 745bb36804e4cb55d23c]." (source: `Cryptographic Controls and Secure Software Construction.md`)
- **Keep it simple** — reduce complexity to reduce the attack surface. (source: `Security Best Practices and Design Principles.md`)
- **Default deny** — deny access by default; grant only what is explicitly needed. (source: `Security Best Practices and Design Principles.md`)
- **Adhere to the principle of least privilege** — isolate privileged operations in small, dedicated [SWEBOK excerpt f1d2aa0a67f242521844]." (source: `Secure Module Design and Error Handling Principles.md`)
- **Sanitize data sent to other software** — prevent injection and related attacks when handing off data. (source: `Security Best Practices for Software Development.md`)
- **Practice defense in depth** — layer multiple independent security controls. (source: `Software Security Best Practices.md`)
- **Use effective quality assurance techniques** — rigorous QA (reviews, testing, analysis) is a core part of security. (source: `Software Security Best Practices.md`)
- **Adopt a software construction security standard** — formally adopt a recognized standard to systematize secure coding. (source: `Software Security Best Practices.md`)
- **Validate assumptions; document what cannot be validated** — "[SWEBOK excerpt 8de4c89f6bad5b1aa1b9]." (source: `Secure Module Design and Error Handling Principles.md`)
- **Do not share memory objects with other programs** — prevents data leakage or tampering across process boundaries. (source: `Secure Module Design and Error Handling Principles.md`)
- **Check every function's error status; restore state and terminate on security-affecting errors** — "[SWEBOK excerpt 10d806b3bb8878ec25f2]." (source: `Secure Module Design and Error Handling Principles.md`)
- **Choose and manage cryptographic controls carefully** — "[SWEBOK excerpt f9a8a970d6c3ff97ed6c]." (source: `Cryptographic Controls and Secure Software Construction.md`)

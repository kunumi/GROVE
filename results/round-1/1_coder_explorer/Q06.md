### Question

A function takes six configuration parameters, each with several possible values, and testing every possible mix of their values is too expensive. How should the test cases be derived?

### Answer

# Summary
When a function has six configuration parameters with many possible values, exhaustive all-combinations testing is replaced by **combinatorial test techniques** that systematically cover every *pair* (or t-tuple) of parameter values rather than every full combination. SWEBOK recommends starting with equivalence partitioning to reduce the value space per parameter, applying pair-wise or t-wise testing (implemented via orthogonal array testing) to select a minimal covering set of test cases, and augmenting with boundary value tests at each parameter's edge values. Decision tables can capture and document the logical interactions between conditions.

# Guidelines

- **Use combinatorial test techniques as the overarching strategy.** "[SWEBOK excerpt 12bb367a5311e46b2a98]." The standard options are All Combinations, Pair-Wise, t-wise, Each Choice, and Base Choice Testing — choose the one that balances cost and coverage.
  (source: `root/Software Testing Methodologies and Techniques/Combinatorial Test Techniques Overview.md`)

- **Prefer pair-wise (all-pairs) testing over all-combinations testing.** "[SWEBOK excerpt 84129f160b87efa4ccba]." This guarantees that every two-parameter interaction is exercised with far fewer test cases than full enumeration.
  (source: `root/Software Testing Methodologies and Techniques/Systematic Test Case Derivation and Combinatorial Methods/Combinatorial Testing and Decision Tables.md`)

- **Generalise to t-wise testing for higher confidence.** "[SWEBOK excerpt 9efc0f0625a900e6e507])." Use t = 3 or higher when three-way interactions are suspected.
  (source: `root/Software Testing Methodologies and Techniques/Systematic Test Case Derivation and Combinatorial Methods/Combinatorial Testing and Decision Tables.md`)

- **Implement pair-wise / t-wise via orthogonal array testing (OAT).** "[SWEBOK excerpt 025fb71ffef7c351cf7d])." Orthogonal arrays provide a mathematical structure for building the minimal test suite.
  (source: `root/Software Testing Methodologies and Techniques/Systematic Test Case Derivation and Combinatorial Methods/Combinatorial Testing and Decision Tables.md`)

- **Reduce the value space per parameter first using equivalence partitioning.** "[SWEBOK excerpt e279d64d08518504c456] criterion or relation." Then: "[SWEBOK excerpt 83b36aaa6987b9eb0caf]." Fewer values per parameter means a smaller combinatorial space.
  (source: `root/Software Testing Methodologies and Techniques/Software Testing Approaches and Techniques/Classification and Specification-Based Testing Techniques.md` and `root/Software Testing Methodologies and Techniques/Boundary Value Analysis and Syntax Testing Techniques.md`)

- **Add boundary value test cases for each parameter.** "[SWEBOK excerpt bedee61fb08d8b967278]." For robustness, also test just outside the valid range: "[SWEBOK excerpt 32408e7aeb57f6cc8404]."
  (source: `root/Software Testing Methodologies and Techniques/Boundary Value Analysis and Syntax Testing Techniques.md`)

- **Use decision tables to capture and document multi-parameter logical interactions.** "[SWEBOK excerpt a11245cd76e2da148e79]). [SWEBOK excerpt d020abbdbdf02c227d05]." They are also "[SWEBOK excerpt 610a720fe12e612fbbc7]."

- **Treat the derivation as black-box / specification-based.** "[SWEBOK excerpt c37129b7fc2f9a3a42a7]." All the above techniques fall in this category and need only the function's parameter specification, not its source code.

### Question

A coding agent proposes splitting a large module into several networked services. Before anyone implements it, how can the team check whether this high-level structure will meet goals that pull against each other, such as response time, hosting cost and ease of future change?

Answer with a list of guidelines. After each guideline, cite the source it comes from: the path of the SWEBOK file if you have it, otherwise a verbatim quote of at least 8 words from the passage, in the form (source: ...).

### Answer

# Summary
Before implementing a proposed split of a large module into networked services, the team should evaluate the high-level architecture against Architecturally Significant Requirements (ASRs) using structured methods — especially the Architecture Tradeoff Analysis Method (ATAM) — to surface conflicts between competing quality attributes such as response time, hosting cost, and changeability. This evaluation relies on explicit architecture descriptions (views) that make each quality concern inspectable, is supplemented by quantitative architecture metrics, and is conducted through both team-led design reviews and, at key milestones, independent third-party reviews. Use cases can be walked through to verify completeness and consistency before any code is written.

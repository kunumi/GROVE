## Guidelines: Deciding What to Test Again After a System Change

---

### 1. Treat regression testing as the standard response to any modification

After any change, **selective retesting** must be performed [SWEBOK excerpt 021f9937eefeac172cee] system still complies with its specified requirements. This applies at every test level (unit, integration, system, acceptance).

> (source: "[SWEBOK excerpt cefe3b0cf2a84ba25da0]'" — `/workspace/swebok-v4/root/Software Testing Levels, Objectives, and Approaches/Alpha, Beta, and Regression Testing Procedures.md`)

---

### 2. Plan test activities as part of every modification request (MR/PR), not as an afterthought

Test planning must be integrated into the processing of each modification or problem report. [SWEBOK excerpt c3c33097f11f56b0a99c]; the maintainer should therefore plan and execute the **appropriate** tests proportional to the change, rather than re-running everything.

> (source: "[SWEBOK excerpt cc2b48d871fb8e63b720]" — `/workspace/swebok-v4/root/Software Testing, Operations, and Maintenance/Software Operations and Maintenance Practices/Software Maintenance_ Technical, Management, and Comprehension Challenges/Software Comprehension and Testing in Maintenance.md`)

---

### 3. Perform impact analysis before testing to scope what needs to be retested

Before deciding what to retest, the team should conduct an impact analysis of the proposed change. This identifies all systems and products affected by the change request and estimates the resources needed, including which tests are relevant.

> (source: "[SWEBOK excerpt 0c7db2dd353e0c0d305c] … [SWEBOK excerpt a703690bd989e1f5d004]" — `/workspace/swebok-v4/root/Software Testing, Operations, and Maintenance/Software Operations and Maintenance Practices/Impact Analysis in Software Maintenance.md`)

---

### 4. Use requirements traceability to identify the "footprint" of a change and derive the affected test cases

Trace the changed requirement or design element forward through the traceability chain: requirement → design element → code unit → test case. This establishes the minimum set of test cases directly linked to the modified artifacts.

> (source: "[SWEBOK excerpt 871601aa48ef8c64ec8f]" — `/workspace/swebok-v4/root/Requirements Management, Quality, and Testing Practices/Requirements Traceability and Change Impact Analysis/Traceability in Software Requirements and Design.md`)

---

### 5. Apply test-case selection, minimization, and prioritization to manage the cost of regression testing

Because running every test after every change is impractical, the team should use **test-case selection** (choosing a relevant subset), **minimization** (reducing redundant tests), and **prioritization** (scheduling tests to maximise fault detection rate) on the existing test suite.

> (source: "Regression testing may involve selection … and minimization … [SWEBOK excerpt c263305c352ff6239a5b] … to existing test suites" — `/workspace/swebok-v4/root/Software Testing Levels, Objectives, and Approaches/Regression Testing in Software Development.md`)

---

### 6. Balance assurance against resources: a trade-off is explicitly required

The team must explicitly weigh the assurance provided by running all regression tests against the time and resources available. Not running every test is a legitimate engineering decision — but it must be a conscious one, not an omission.

> (source: "[SWEBOK excerpt 67db88e68b13fb1652d2]" — `/workspace/swebok-v4/root/Software Testing Levels, Objectives, and Approaches/Alpha, Beta, and Regression Testing Procedures.md`)

---

### 7. Conduct regression testing after integration and before deployment to production

The correct **process position** for regression testing is after integration testing has been completed and before the system is deployed to production or handed over to operations.

> (source: "[SWEBOK excerpt 51c60fad5f5a335bf6d9]" — `/workspace/swebok-v4/root/Software Testing Levels, Objectives, and Approaches/Regression Testing in Software Development.md`)

---

### 8. In continuous integration and DevOps pipelines, run regression tests at every integration

When CI/CD is in use, regression testing should be executed continuously — at every integration — to detect development and integration issues as early as possible. Quick techniques such as **smoke testing** should precede fuller regression suites to verify the build is testable before more expensive tests run.

> (source: "[SWEBOK excerpt e2d661af64b2c4a4822d]" — `/workspace/swebok-v4/root/Software Testing, Operations, and Maintenance/Testing Across Development Processes and Domains/Testing Strategies Across Methodologies and Domains/Test Automation and Domain-Specific Testing Approaches.md`)

---

### 9. Automate regression execution and use tooling to select test subsets by change

Regression testing tools support re-execution of a test suite after software has been modified; test-selection tools can automatically narrow the subset of tests relevant to a specific change, reducing manual effort.

> (source: "Regression testing tools … [SWEBOK excerpt 4e31a19101591ba0b19b]" and "[SWEBOK excerpt 2385d456b65f4063aae4]" — `/workspace/swebok-v4/root/Software Testing, Operations, and Maintenance/Software Operations and Maintenance Practices/Software Testing Tools and Standards/Software Testing Tools and Techniques/Software Testing Tools and Techniques.md` and `/workspace/swebok-v4/root/Software Testing, Operations, and Maintenance/Software Operations and Maintenance Practices/Software Testing Tools and Standards/Software Testing Tools and Techniques/Software Testing and Reliability Evaluation Tools.md`)

---

### 10. Keep test repositories up to date so changes to requirements and design are reflected in tests

A knowledge-based test repository should be maintained so that changes to requirements or design automatically translate into updates to the corresponding test cases, keeping the regression suite accurate and preventing obsolete tests from being re-run.

> (source: "[SWEBOK excerpt cc60c8d6f727f372cb4a]" — `/workspace/swebok-v4/root/Testing Methodologies and Quality Assurance Practices/Software Testing Techniques, Measurement, and Management/Test Completion and Knowledge Management/Test Completion and Artifact Reusability in Software Testing.md`)

---

### 11. In Agile contexts, involve all stakeholders and explicitly manage the impact of changes on test artifacts

Agile regression testing is not purely technical: [SWEBOK excerpt 148e60a352daf83bec28] all stated objectives of the Agile testing process, and all relevant stakeholders (including customers) should be involved.

> (source: "[SWEBOK excerpt 9e282f0d7db2e16286cf]" — `/workspace/swebok-v4/root/Software Testing, Operations, and Maintenance/Testing Across Development Processes and Domains/Testing Strategies Across Methodologies and Domains/Testing Techniques Across Development Levels and Shift-Left Approaches.md`)

### 2. Use contracts to precisely specify and clarify a routine's semantics.

A contract is not just a runtime guard — it is a form of documentation. Making the contract explicit helps the caller understand exactly what the routine does and does not do.

### 4. Use assertions specifically to surface mismatched interface assumptions early.

Assertions enable programmers to detect the kind of problem that is hardest to notice: an assumption held by the routine's author that the caller violates silently.

### 5. Compile assertions in during development; remove them before release to avoid performance degradation.

This practice allows full runtime protection during development without burdening production systems.

### 6. Practice defensive programming: [SWEBOK excerpt e9abc85349cc38f7a2e7].

Defensive programming complements design by contract by adding active runtime guards inside the routine itself, rather than relying solely on callers to honor the contract.

(source: "[SWEBOK excerpt fe09ccfb26565a8b97e8]." — `/workspace/swebok-v4/root/Software Construction Techniques and Practices/Contract Design and Error Handling Strategies/Design by Contract and Defensive Programming.md`)

### 7. Check the values of all input parameters and decide how to handle bad inputs explicitly.

The routine should not silently accept out-of-range or nonsensical values. Checking every parameter at the boundary is the central defensive act.

(source: "[SWEBOK excerpt 93d62d9d3fbab9385d19]." — `/workspace/swebok-v4/root/Software Construction Techniques and Practices/Contract Design and Error Handling Strategies/Design by Contract and Defensive Programming.md`)

### 8. Use assertions inside defensive programming code to verify input values.

Assertions and defensive programming are complementary: defensive checks handle bad inputs gracefully, while assertions make the assumption violation visible and traceable during development.

### 10. Throw exceptions to signal detected violations, and handle them with well-designed exception policies.

A routine should use `throw` to signal a detected problem; the caller catches it in a try-catch block.

## Guidelines for Keeping Software Operational When Runtime Errors Occur

These guidelines are drawn exclusively from the SWEBOK v4.0 passages retrieved above.

---

### 1. Treat fault tolerance as a first-class design concern

Explicitly address [SWEBOK excerpt f8e47cba6d58b0e4056d] as part of the software design activity—not as an afterthought.

(source: "[SWEBOK excerpt b4ad34aaec8c0116191e]." — `/workspace/swebok-v4/root/Software Design Concerns, Documentation, and Modeling/Software Design Concerns and Architectural Patterns.md`)

---

### 2. Design error handling to maintain correctness and robustness

Acknowledge that how errors are handled directly affects the software's ability to meet requirements for **correctness**, **robustness**, and other nonfunctional attributes. Choose error-handling strategies deliberately rather than leaving them to chance.

(source: "[SWEBOK excerpt 5cbc324f523e1430b28c]." — `/workspace/swebok-v4/root/Software Construction Techniques and Practices/Contract Design and Error Handling Strategies/Error Handling, Exception Handling, and Fault Tolerance.md`)

---

### 3. Return a neutral/phony value when an operation fails

Instead of propagating or crashing, a routine can substitute a safe, neutral value that will have no harmful downstream effect, allowing execution to continue.

(source: "[SWEBOK excerpt 8b0b1372e25e459ce254]" — `/workspace/swebok-v4/root/Software Construction Techniques and Practices/Fault Tolerance Techniques and Executable Models.md`)

---

### 4. Back up and retry on transient errors

When a failure may be transient (e.g., a resource temporarily unavailable), the system should back up to a known state and retry the operation before concluding that an unrecoverable error has occurred.

(source: "[SWEBOK excerpt 7c7c13df07628c3c7d07]." — `/workspace/swebok-v4/root/Software Construction Techniques and Practices/Fault Tolerance Techniques and Executable Models.md`)

---

### 5. Use auxiliary code and voting algorithms for redundancy

Implement redundant computations (e.g., multiple independent algorithms) and select the result by voting, so that an error in one path does not propagate to the output.

(source: "using auxiliary code and voting algorithms" — `/workspace/swebok-v4/root/Software Construction Techniques and Practices/Fault Tolerance Techniques and Executable Models.md`)

---

### 6. Substitute the next piece of valid data when input is bad

When invalid input is encountered, skip the offending data item and continue processing with the next valid piece of data, preventing a single bad input from halting the entire operation.

(source: "[SWEBOK excerpt 25fb1a8cce8efbace92b]." — `/workspace/swebok-v4/root/Software Construction Techniques and Practices/Contract Design and Error Handling Strategies/Error Handling, Exception Handling, and Fault Tolerance.md`)

---

### 7. Log warning messages instead of immediately failing

Rather than terminating execution, emit a diagnostic warning that records the anomaly, allowing the system to continue and providing information for later diagnosis.

(source: "[SWEBOK excerpt d61c83cd826788f611df]" — `/workspace/swebok-v4/root/Software Construction Techniques and Practices/Contract Design and Error Handling Strategies/Error Handling, Exception Handling, and Fault Tolerance.md`)

---

### 8. Use structured exception handling (try-catch) to intercept and recover from errors

Wrap potentially error-prone operations in try-catch blocks. The catch block can either handle the erroneous condition locally or return control to the calling routine so it can respond appropriately, without crashing the program.

(source: "[SWEBOK excerpt aa95fcd1c82d33a12fdb] try-catch [SWEBOK excerpt 980c1713bcc05a3281c2]." — `/workspace/swebok-v4/root/Software Construction Techniques and Practices/Contract Design and Error Handling Strategies/Error Handling, Exception Handling, and Fault Tolerance.md`)

---

### 9. Apply exception-handling policies consistently across the codebase

Design exception handling according to consistent, program-wide principles: include all contextual information in the exception message, avoid empty catch blocks (which silently swallow errors), know which exceptions library code throws, consider a centralized exception reporter, and standardize usage.

(source: "[SWEBOK excerpt 8a98e7d1cb740854b979]." — `/workspace/swebok-v4/root/Software Construction Techniques and Practices/Contract Design and Error Handling Strategies/Error Handling, Exception Handling, and Fault Tolerance.md`)

---

### 10. Apply defensive programming to protect routines from invalid inputs

Each routine should validate all its inputs before acting on them, and explicitly decide how to handle bad inputs, so that invalid data cannot put the routine—and the system—into an undefined or failed state.

(source: "[SWEBOK excerpt edaaca9c62404676ff9e]." — `/workspace/swebok-v4/root/Software Construction Techniques and Practices/Contract Design and Error Handling Strategies/Design by Contract and Defensive Programming.md`)

---

### 11. Use runtime assertions to detect violations early and contain damage

Place executable assertions at critical points in the code to catch incorrect assumptions at the moment they occur rather than letting corrupted state silently spread. Assertions are especially valuable in high-reliability programs.

(source: "[SWEBOK excerpt 5911453b0a4f5e43261b]. [SWEBOK excerpt 4b5d09b3a87e6f492d8f]." — `/workspace/swebok-v4/root/Software Construction Techniques and Practices/Parameterization, Templates, Generics, and Assertions.md`)

---

### 12. Use Design by Contract to make routine obligations explicit

Specify preconditions and postconditions for each routine so that every caller and callee has a clear contract. This surfaces mismatched interface assumptions quickly—before they cause silent runtime failures—and improves software quality.

(source: "[SWEBOK excerpt 3371d5be97fc67ae3e08]." — `/workspace/swebok-v4/root/Software Construction Techniques and Practices/Assertions and Design by Contract in Programming.md`)

---

### 13. Standardize exception-handling policies in construction standards

Adopt organizational coding standards that mandate how exceptions must be formed and handled (e.g., what information to include, how to catch them), so error handling is uniform and no path is left silently broken.

(source: "[SWEBOK excerpt ee32440fee20f38054fc])" — `/workspace/swebok-v4/root/Construction Practices, Standards, and Development Models/Applying Standards in Construction.md`)

---

### 14. Treat fault tolerance as recovering from—or containing—errors that cannot be prevented

Recognize that fault tolerance operates on two levels: *recovery* (restoring correct operation) and *containment* (limiting the blast radius when recovery is impossible). Design both paths explicitly.

(source: "[SWEBOK excerpt 909de8a0fa8186bde761]." — `/workspace/swebok-v4/root/Software Construction Techniques and Practices/Fault Tolerance Techniques and Executable Models.md`)

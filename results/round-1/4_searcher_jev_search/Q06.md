## Guidelines for Deriving Test Cases When Exhaustive Combination Testing Is Too Expensive

---

### 1. Apply Equivalence Partitioning to Collapse Each Parameter's Value Space

Partition the input domain of each configuration parameter into equivalence classes — subsets whose members are expected to behave the same way — and then pick one representative value from each class. This immediately reduces the number of distinct values that need to be exercised per parameter before any combination strategy is applied.

### 2. Add Boundary Value Tests for Each Parameter

After partitioning, choose test values *on or near the boundaries* of each parameter's valid range, since faults tend to cluster at extreme input values. Consider also choosing values just outside the valid domain (robustness testing) to verify error-handling behavior.

> (source: "[SWEBOK excerpt 22b5a76f3ce0e0a3a3af]." — `/workspace/swebok-v4/root/Software Testing Methodologies and Techniques/Boundary Value Analysis and Syntax Testing Techniques.md`)

---

### 3. Use Combinatorial Test Techniques to Systematically Cover Parameter Interactions

Rather than testing all combinations (which is combinatorially explosive), apply one of the following combinatorial strategies in increasing order of thoroughness:

- **Each Choice Testing** — ensure every value of every parameter appears in at least one test case.
- **Base Choice Testing** — select a "base" value for each parameter, then vary one parameter at a time away from the base.
- **Pairwise (All-Pairs) Testing** — derive test cases so that every *pair* of parameter values is covered by at least one test case.
- **t-wise Testing** — generalize pairwise to cover every combination of *t* parameter values (t > 2) for higher-confidence fault detection.
- **All Combinations Testing** — the full Cartesian product; use only when feasibility permits.

### 4. Use Decision Tables to Capture Logical Interactions Between Parameters

When the parameters interact through logical conditions (e.g., certain combinations are only valid together, or trigger distinct behaviours), represent those conditions and their resulting actions in a decision table or decision tree. Each column in the table becomes a test case, ensuring all relevant condition combinations are exercised without redundancy.

### 5. Combine Specification-Based and Structure-Based Techniques

Specification-based (black-box) techniques — such as equivalence partitioning and combinatorial testing — focus on the input/output behaviour; structure-based (white-box) techniques focus on what the code actually does. Using both together improves fault detection, since they expose different categories of defects. When budget is constrained, the choice and blend of techniques should be adapted to organisational constraints.

> (source: "[SWEBOK excerpt 14a15524a4aed4318039]." — `/workspace/swebok-v4/root/Testing Methodologies and Quality Assurance Practices/Software Testing Techniques, Measurement, and Management/Testing Approaches and Test Case Selection Methods/Combining Functional and Structural Testing Techniques.md`)

---

### 6. Prioritize Test Cases to Maximize Early Fault Detection

Once the reduced test suite is derived, order the test cases so that those most likely to find faults are run first, taking into account code coverage, fault likelihood, and dissimilarity between test cases. This further mitigates the cost of incomplete execution by front-loading the highest-value tests.

> (source: "[SWEBOK excerpt 3e32889b1d11770ab3a7]." — `/workspace/swebok-v4/root/Software Testing Levels, Objectives, and Approaches/Test Case Prioritization for Fault Detection.md`)

---

### 7. Measure Coverage to Assess Adequacy of the Reduced Suite

After applying the above techniques, evaluate the achieved coverage (e.g., percentage of equivalence classes, pairs, or branches exercised). Coverage measures provide the evidence needed to judge whether the reduced test suite is adequate or whether additional cases are warranted.

## Guidelines: Using the Table-Driven Method to Replace Long Conditional Chains

The **table-driven method** is the construction approach recommended by the SWEBOK for this situation. Below are the guidelines for applying it, each cited from the SWEBOK passages found.

---

### 1. Recognise when to switch from logic statements to a table

Use a table-driven method whenever a function's behaviour is driven by mappings of conditions to results that are currently expressed through `if`/`case` chains. [SWEBOK excerpt 1478f1829d79cb2d4167])*.

(source: `/workspace/swebok-v4/root/Software Construction Techniques and Practices/State-Based and Object-Oriented Programming Approaches.md` — *"[SWEBOK excerpt 8f07d1cee310657857df])."*)

---

### 2. Apply the method only where it genuinely simplifies the code

Do not apply table-driven construction indiscriminately. Reserve it for the cases where it actually reduces complexity and improves readability.

(source: `/workspace/swebok-v4/root/Software Construction Techniques and Practices/Runtime Configuration and Internationalization in Software Design.md` — *"[SWEBOK excerpt 1f02a9a5cf54055acd0d]."*)

---

### 3. Prioritise the table-driven method when you expect the logic to change

A key benefit of table-driven code is that it is easier to modify than a chain of conditionals. If the mapping between conditions and results is likely to evolve, this is a strong argument for switching to a table.

(source: `/workspace/swebok-v4/root/Software Construction Techniques and Practices/Runtime Configuration and Internationalization in Software Design.md` — *"[SWEBOK excerpt 1f02a9a5cf54055acd0d]."*)

---

### 4. Decide what information to store in the table

The first key decision when applying a table-driven method is determining what information the table entries should hold — this could be result values, action codes, function pointers, or any data that the previously hard-coded logic was computing.

(source: `/workspace/swebok-v4/root/Software Construction Techniques and Practices/Runtime Configuration and Internationalization in Software Design.md` — *"[SWEBOK excerpt 68e8b2103379df006823]."*)

---

### 5. Decide [SWEBOK excerpt ffd30c20bbf41330ba5d]

The second key decision is choosing the access strategy: how the code will look up the right row or entry at runtime. The choice of access mechanism (e.g., direct indexing by key, indirect/indexed lookup when keys are not contiguous, or range/stair-step lookup for continuous ranges) must match the structure of the data and performance requirements.

(source: `/workspace/swebok-v4/root/Software Construction Techniques and Practices/Runtime Configuration and Internationalization in Software Design.md` — *"[SWEBOK excerpt 68e8b2103379df006823]."*)

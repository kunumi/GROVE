## Guidelines for Restructuring the Orders Table and Understanding the Query Cost

---

### 1. Recognise that the root cause is data redundancy and inconsistency in an unnormalized table

Before restructuring anything, understand *why* the problem exists. Storing the customer name and address on every order row is precisely the kind of redundancy that relational databases are designed to eliminate. Conventional, file-system-style storage "suffered from data redundancy, data inconsistency, [and] data access challenges," whereas a proper RDBMS is designed so that "data redundancy is significantly reduced."

(source: "[SWEBOK excerpt a1e367440e6bc6654da8]." — `/workspace/swebok-v4/root/Data Systems, Networks, and Computational Foundations/Database Management and Network Communication Systems/Database Design and Normalization Fundamentals/Database Languages and Relational Database Management Systems.md`)

---

### 2. Apply normalization — the formal process for removing redundancy and inconsistency

Restructuring the table is not an ad-hoc refactoring exercise; it is the well-defined process of normalization. "[SWEBOK excerpt 7e1d2d7ec900739f27d1]."

(source: "[SWEBOK excerpt 7e1d2d7ec900739f27d1]." — `/workspace/swebok-v4/root/Data Systems, Networks, and Computational Foundations/Database Management and Network Communication Systems/Database Design and Normalization Fundamentals/Database Normalization and RDBMS Fundamentals/RDBMS Types and Database Normalization Fundamentals.md`)

---

### 3. Start with First Normal Form (1NF): give every row a unique key and eliminate duplicate values

The first step is to ensure that each row is uniquely identifiable. 1NF "[SWEBOK excerpt 41cb86d54edfe2826582] … [SWEBOK excerpt efb5158c35c6d1dd0444]." For the orders table, this means assigning a unique key to each customer and each order if not already present.

(source: "[SWEBOK excerpt 0288706213333bf1031a]." — `/workspace/swebok-v4/root/Data Systems, Networks, and Computational Foundations/Database Management and Network Communication Systems/Database Design and Normalization Fundamentals/Database Normalization and RDBMS Fundamentals/Database Normalization Forms and De-normalization.md`)

---

### 4. Apply Second Normal Form (2NF): move partially dependent columns into their own table

The customer's name and address depend only on the customer, not on the order. This is a *partial dependency* — a 2NF violation. 2NF requires that "the table should be in 1NF; no partial dependency," and resolves this by "creat[ing] [SWEBOK excerpt 1f443b53628612e6d5d5]." Concretely: extract customers (customer_id, name, address) into a separate `Customers` table, and let the `Orders` table hold only a foreign key reference to it.

(source: "[SWEBOK excerpt 6d0499536d85be18506b])." — `/workspace/swebok-v4/root/Data Systems, Networks, and Computational Foundations/Database Management and Network Communication Systems/Database Design and Normalization Fundamentals/Database Normalization and RDBMS Fundamentals/Database Normalization Forms and De-normalization.md`)

---

### 5. Continue to Third Normal Form (3NF): remove any remaining transitive dependencies

After splitting customer data out, check whether any remaining non-key column in `Orders` depends on another non-key column rather than directly on the order key. 3NF requires that "the table should be in 2NF. Transitive dependencies are removed." For most order-management schemas, reaching 3NF is the practical target.

(source: "[SWEBOK excerpt e6b8f2d0590bc4f09048]." — `/workspace/swebok-v4/root/Data Systems, Networks, and Computational Foundations/Database Management and Network Communication Systems/Database Design and Normalization Fundamentals/Database Normalization Forms and Requirements.md`)

---

### 6. Target 3NF or BCNF as the practical stopping point

Going beyond BCNF is rarely necessary. "[SWEBOK excerpt 4e8dc7c159181b00ce14]." The higher forms (4NF–6NF) address multivalued and join dependencies that are uncommon in a straightforward orders/customers schema. BCNF adds the constraint that for any functional dependency X → Y, X must be a super-key — useful when multiple overlapping candidate keys exist in an orders table.

(source: "[SWEBOK excerpt 4e8dc7c159181b00ce14]." — `/workspace/swebok-v4/root/Data Systems, Networks, and Computational Foundations/Database Management and Network Communication Systems/Database Design and Normalization Fundamentals/Database Normalization Forms Fourth Through Sixth.md`)

---

### 7. Use DKNF if insertion and deletion anomalies must be formally eliminated

If the schema must guarantee that no anomaly (insertion, deletion, or update) can ever arise by design, consider Domain/Key Normal Form. "[SWEBOK excerpt 2431529db5b4d2f04959]." This is a stronger formal guarantee than 3NF/BCNF, though it comes with added complexity.

(source: "[SWEBOK excerpt 2431529db5b4d2f04959]." — `/workspace/swebok-v4/root/Data Systems, Networks, and Computational Foundations/Database Management and Network Communication Systems/Database Design and Normalization Fundamentals/Database Normalization Forms Fourth Through Sixth.md`)

---

### 8. Use a schema that records relationships and integrity constraints explicitly

The restructured design should be documented as a schema. "[SWEBOK excerpt 6e12595e017d20be538e]." Use primary keys, foreign keys, and integrity rules so the DBMS itself enforces that every order row points to a valid customer.

(source: "[SWEBOK excerpt 0b9e00f0b7fe9379bc85]." — `/workspace/swebok-v4/root/Software Engineering Fundamentals and System Architecture/Database Schema Structure and Design.md`)

---

### 9. Accept that normalization will increase the number of tables and query time

Splitting the table is not free. "[SWEBOK excerpt 403fa59657edba586592]." Every query that previously read a single flat row must now join `Orders` to `Customers`, incurring additional processing. Engineers must understand and budget for this overhead.

(source: "[SWEBOK excerpt 403fa59657edba586592]." — `/workspace/swebok-v4/root/Data Systems, Networks, and Computational Foundations/Database Management and Network Communication Systems/Database Design and Normalization Fundamentals/Database Normalization and RDBMS Fundamentals/RDBMS Types and Database Normalization Fundamentals.md`)

---

### 10. Study the normalization trade-offs with examples before choosing a final design

The SWEBOK recommends that engineers not apply normalization mechanically but reason about its consequences: "[SWEBOK excerpt cfbed407ad524d8c3ff2]."

(source: "[SWEBOK excerpt cfbed407ad524d8c3ff2]." — `/workspace/swebok-v4/root/Data Systems, Networks, and Computational Foundations/Database Management and Network Communication Systems/Structured Query Language and Data Management Fundamentals.md`)

---

### 11. Apply de-normalization deliberately when query performance is unacceptable

If, after normalizing, profiling reveals that the join cost is too high for the application's requirements, controlled de-normalization is a recognized remedy. "[SWEBOK excerpt 548a0049dac977c4a9e6]." This is a deliberate, documented trade-off, not a reason to skip normalization in the first place.

(source: "[SWEBOK excerpt 548a0049dac977c4a9e6]." — `/workspace/swebok-v4/root/Data Systems, Networks, and Computational Foundations/Database Management and Network Communication Systems/Database Design and Normalization Fundamentals/Database Normalization and RDBMS Fundamentals/Database Normalization Forms and De-normalization.md`)

### Summary of the restructuring path

| Step | Action | Normal form achieved |
|---|---|---|
| Assign unique keys | Give each customer and order a unique identifier | 1NF |
| Split the table | Move (customer_id, name, address) to a `Customers` table; keep only `customer_id` FK in `Orders` | 2NF |
| Remove transitive deps | Ensure all remaining `Orders` columns depend directly on the order key | 3NF / BCNF |
| Measure join cost | Profile queries; if joins are too slow, selectively de-normalize | — |

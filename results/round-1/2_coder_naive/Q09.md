## Secure Coding Guidelines for Developers

### From CERT/CC's Top 10 Software Security Practices (as cited in SWEBOK):

1. **Validate all input.**
Ensure that data entering the system is checked for correctness, type, length, and range before use.
(source: "[SWEBOK excerpt 3550eba7151b1661df1b].**
Do not ignore warnings generated during compilation, as they may signal potential security defects.
(source: "[SWEBOK excerpt eec980c3e0a1869670af].**
Security must be built into the design of the system, not added as an afterthought.
(source: "[SWEBOK excerpt 591b2c3470c06df16dc3].**
Simpler code is easier to analyze, review, and secure against attack.
(source: "4. Keep it simple.")

5. **Default deny.**
Access should be denied by default; permissions must be explicitly granted rather than assumed.
(source: "[SWEBOK excerpt 4554a3a3f276577c9e76].**
Code and processes should run with only the minimum permissions necessary to perform their function.
(source: "[SWEBOK excerpt a3c24cfb02cace13b4b8].**
Data passed to external systems, databases, or other software components must be cleaned to prevent injection and similar attacks.
(source: "[SWEBOK excerpt f51cf0474e6fe0d67df2].**
Layer multiple security controls so that the failure of one does not compromise the whole system.
(source: "[SWEBOK excerpt 8925025a96dbbcf9c1ba].**
Apply rigorous QA methods — such as testing, code review, and static analysis — to catch security flaws early.
(source: "[SWEBOK excerpt 6919259bc71a148ac6cd] security standard.**
Follow a recognized, established standard for secure coding throughout the construction process.
(source: "10. Adopt a software construction security standard.")

### Additional Specific Coding Rules (also from SWEBOK):

11. **Keep privileged modules small and focused.**
Structure the code so that any section requiring elevated privileges is isolated into as small a module as possible, performing only what is strictly necessary.
(source: "[SWEBOK excerpt 4efb029cedb4ed80ee2d].")

12. **Validate all program assumptions, or document them explicitly.**
Any assumption baked into the code must either be validated at runtime or clearly documented so maintainers know what an attacker might try to exploit.
(source: "[SWEBOK excerpt 0bcf94be1b9045b82f4d].")

13. **Do not share objects in memory with other programs.**
Shared memory creates opportunities for privilege escalation or data leakage between processes.
(source: "[SWEBOK excerpt 0bf95a5064c99a220208].")

14. **Check every function's error status and handle failures securely.**
When an error is detected and it affects security, the program should restore its prior safe state and terminate rather than attempt to continue in a potentially compromised condition.
(source: "[SWEBOK excerpt f8acf867765e953f75d7].")

15. **Know common vulnerabilities and use defensive programming.**
Programmers should be familiar with well-known vulnerability lists (e.g., CVE, CWE) and apply techniques such as assertions and defensive programming to guard against them.
(source: "[SWEBOK excerpt 463aa9a1f385c7337a77].")

16. **Be careful when choosing programming languages, as the choice affects security.**
Some languages (e.g., C/C++) are more prone to introducing vulnerabilities through unsafe library functions; the language and its compiler can affect security outcomes.
(source: "[SWEBOK excerpt 60903a6d9f8370b2ab92]).")

17. **Avoid introducing untrusted external dependencies.**
Propagation of vulnerabilities from external dependencies into the software product should be actively prevented, with regulations and monitoring mechanisms in place.
(source: "[SWEBOK excerpt be6079716b54b44cc995] [SWEBOK excerpt fd3c4dabfaf88745b444].")

All guidelines above are sourced from **SWEBOK Guide v4.0a**, primarily from the **Software Security KA (Section 4.4, Construction for Security)** and the **Software Construction KA (Sections 3.2 and 3.6)**.

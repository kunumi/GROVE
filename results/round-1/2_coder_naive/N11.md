### Question

Our orders table repeats the customer's name and address on every order row, and after a customer moves some rows show the old address while others show the new one. How should the tables be restructured, and what does that cost when querying the data?

## Guidelines for Restructuring the Orders Table

### 1. Recognize the root cause: the existing design suffers from data redundancy and inconsistency

Your current schema stores customer name and address in every order row. This is exactly the class of problem that conventional (non-relational) file-based databases produced. SWEBOK identifies "data redundancy" and "data inconsistency" as the core ailments that relational databases were designed to cure — the scenario where the same real-world fact appears in multiple places and can fall out of sync.

(source: *"[SWEBOK excerpt a1e367440e6bc6654da8]."*)

---

### 2. Use normalization to remove the redundancy and inconsistency

**What to do:** Split the data into two tables — a `Customers` table (holding name, address, and a unique customer ID) and an `Orders` table (holding order-specific data plus a foreign-key reference to the customer). This is the act of normalization.

SWEBOK defines normalization as [SWEBOK excerpt 1b6f26dfa263490d5595] specifically for the purpose of **removing data redundancy and data inconsistency** from tables.

(source: *"[SWEBOK excerpt 7e1d2d7ec900739f27d1]."*)

---

### 3. Apply at least First Normal Form (1NF): eliminate duplicate data and identify each row with a unique key

As a first step, ensure each table cell holds a single value and each row is uniquely identified. This directly eliminates the repeated customer columns in the orders rows.

(source: *"[SWEBOK excerpt 0288706213333bf1031a]."*)

---

### 4. Apply Second Normal Form (2NF): move customer data to its own table

Because customer name and address depend only on the customer, not on the order, they represent a **partial dependency** on the orders table's key. 2NF requires you to remove such partial dependencies by creating a separate `Customers` table with records referenced by the `Orders` table.

(source: *"[SWEBOK excerpt 6d0499536d85be18506b])."*)

---

### 5. Apply Third Normal Form (3NF): remove transitive dependencies

If any non-key column in the orders table depends on another non-key column (rather than on the primary key directly), that too must be moved out. 3NF removes such **transitive dependencies**, further tightening the schema.

(source: *"[SWEBOK excerpt e6b8f2d0590bc4f09048]."*)

---

### 6. Normalize to at least 3NF or BCNF — this is the industry standard

You do not need to pursue 4NF, 5NF, or 6NF for a typical orders/customers schema. SWEBOK notes that most production databases are normalized only to 3NF or BCNF, which is sufficient to avoid the update anomalies you are experiencing.

(source: *"[SWEBOK excerpt 0795a6d5f9294e0525cc]."*)

---

### 7. Use a proper schema with foreign keys to link the two tables

After splitting into `Customers` and `Orders`, the `Orders` table retains only a **foreign key** (the customer ID). SWEBOK lists Foreign Key as one of the key types used in schemata specifically to express relationships between tables.

(source: *"[SWEBOK excerpt f8831ad4424a319c25a6]."*)

---

### 8. Understand the query cost: normalization [SWEBOK excerpt 1dae62524ca4cc3cad5f]

This is the principal trade-off. After normalization, queries that need both order data and customer data must **join** the two tables. SWEBOK explicitly states that normalization can increase both the number of tables and query time.

(source: *"[SWEBOK excerpt 403fa59657edba586592]."*)

(source also: *"[SWEBOK excerpt da4d8a3cc6d262f2b6b8]."*)

---

### 9. Consider selective de-normalization if query performance becomes unacceptable

If the join overhead proves too costly for a specific access pattern (e.g., a high-volume reporting query), SWEBOK sanctions a deliberate reversal: **de-normalization**, which reintroduces controlled redundancy in exchange for faster reads. This is an application- and requirements-driven decision, not a default.

(source: *"[SWEBOK excerpt 548a0049dac977c4a9e6]."*)

---

### 10. Protect insert and delete operations so they cannot corrupt the restructured database

Even after normalization, you must ensure that inserting a new order or deleting a customer does not leave orphaned or inconsistent data. SWEBOK advises that any insertion or deletion must not alter the database in a way that violates the policies under which it was designed.

(source: *"[SWEBOK excerpt 401c576b6108ace03a11]."*)

---

**Summary:** Move customer name and address into a dedicated `Customers` table (reaching at least 2NF/3NF), reference it from `Orders` via a foreign key, and enforce referential integrity. The unavoidable cost is that queries needing customer details alongside order data must now perform a join, which increases processing time — a trade-off SWEBOK explicitly acknowledges, and which de-normalization can partially reverse if performance demands it.

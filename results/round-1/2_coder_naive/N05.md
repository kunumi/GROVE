## Guidelines for Preserving the Ability to Reproduce a Previously Shipped Executable

### 1. Place all source code under version control, versioned and baselined at the time of each release.

SCM [SWEBOK excerpt ea7719291b130020f978] items and their versions, and provides the basis for all other SCM activities. Source code, code libraries, plans, specifications, and design documentation are all candidates to become Software Configuration Items (SCIs).

(source: *"[SWEBOK excerpt 530f8afa066a96b9b3d9]… [SWEBOK excerpt d4b749f5ec14b5d06a14]…"*)

---

### 2. Place all build toolchain components (compilers, linkers, assemblers, etc.) under SCM control.

If the toolchain has changed, you cannot reproduce the exact binary unless the exact tool versions used at build time were themselves versioned and preserved.

(source: *"[SWEBOK excerpt c30bb1e8c1e31553eba4]."*)

---

### 3. Capture and preserve the build instructions for every release.

Knowing the source code and tools is not sufficient — the precise sequence of build steps must also be recorded and controlled.

(source: *"[SWEBOK excerpt 1e8d66262f1680402200]."*)

---

### 4. Record and manage all direct and indirect third-party dependencies (libraries, packages) with their exact versions.

Third-party libraries are part of the dependency supply chain and must be tracked so that the same versions can be recovered later.

(source: *"[SWEBOK excerpt 8d648deeba0c8ab516c0]."*)

---

### 5. Produce and retain a Software Bill of Materials (SBOM) for every build.

An SBOM records exactly which artifacts were included in a given build, providing a definitive inventory for future reference, quality, or compliance purposes.

(source: *"[SWEBOK excerpt 732f80f4110d12af3741]."*)

---

### 6. Store the released binary artifacts themselves in a dedicated binary repository.

A repository for binaries allows the exact released executable to be retrieved directly, without requiring a full rebuild.

(source: *"[SWEBOK excerpt 93cb0cdc79d239bdea25]."*)

---

### 7. Produce and preserve a Version Description Document (VDD) for each release.

The VDD records the physical contents of the release package, enabling the team to know precisely what was delivered to the customer and to re-create or verify that delivery.

(source: *"[SWEBOK excerpt 5216687143d81e73b53d]."*)

---

### 8. Track which release was delivered to which customer.

Release management must track the product's distribution so that — when a specific customer reports a defect — the team knows exactly which release and variant was shipped to them.

(source: *"[SWEBOK excerpt 30cf4b733355837bd6c7])."*)

---

### 9. Protect the integrity of released items (e.g., with a digital signature).

Preserving a verifiable record of the released artifact ensures that what is retrieved from the archive two years later is provably identical — byte for byte — to what was shipped.

(source: *"[SWEBOK excerpt 75c793fd2f1a58484bc7])."*)

---

### 10. Use version control tools that track, document, and store all individual CIs, and use build handling tools to compile and link exact executable versions.

The right tooling must be in place to make the above practices systematically repeatable rather than ad hoc.

(source: *"[SWEBOK excerpt ad2ab627a1dcac07fee5]."*)

---

### Summary

In short, SWEBOK's Software Configuration Management (SCM) knowledge area makes clear that **reproducing a previous release requires that the source code, build tools, build instructions, third-party dependencies, the resulting binaries, and the documentation of what was released to whom must all be placed under SCM control and preserved**. Each element is a configuration item in its own right, and the absence of any one of them — such as the old compiler version — will make exact reproduction impossible.

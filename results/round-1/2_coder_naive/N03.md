## Guidelines for Verifying Correct Behaviour Across All Message Orderings

### 1. Apply Model Checking to Exhaustively Explore All Interleavings

Use model checking — a formal verification technique — to systematically explore every possible ordering of message arrivals. This is precisely the problem model checking is designed to solve: it verifies correct program behaviour under **all** possible interleavings, not just the ones that happen to arise in ordinary testing.

> *What to build:* A formal model of the component and its environment (the producers), expressed as [SWEBOK excerpt 697ec66424d580bd18f8], then run a model-checking tool over it.

(source: "[SWEBOK excerpt 3e68ed24e7a3e7058911]." — SWEBOK v4, [SWEBOK excerpt e06959b8e599f510df57])

---

### 2. Write a Rigorous Formal Specification First

Before verifying anything, capture precisely what "works correctly" means using a formal specification language — one that rigorously defines the input/output behaviour, the allowed orderings of messages, and the expected results. Without a machine-readable specification there is nothing for a model checker or theorem prover to verify against.

> *What to build:* A specification written in a formal specification language (e.g., Z, TLA+, CSP, or similar) that describes the component's required behaviour independently of implementation.

(source: "[SWEBOK excerpt 7c862cc52c6bb02eff73]." — SWEBOK v4, [SWEBOK excerpt e06959b8e599f510df57])

---

### 3. Use Formal Specification Languages to Capture Pre/Post-conditions and Invariants

For each message-handling operation, formally specify the preconditions (what must hold when the message is received), the postconditions (what must hold afterwards), and the invariants (properties that must hold regardless of message order). These become the properties that the checker or proof must establish for all interleavings.

> *What to build:* Annotated operation specifications, expressed in a formal specification language, using pre/post-condition and invariant constructs.

(source: "[SWEBOK excerpt a42ca24eeb68b7424477]." — SWEBOK v4, Software Design KA, §4.3)

---

### 4. Complement Verification with Logical Inference (Design-by-Contract)

Where full model checking is impractical, use logical inference: attach preconditions and postconditions to each significant handler block and develop a mathematical proof that those conditions hold under all inputs — including every possible message order. This lets you reason about behaviour without executing the software.

> *What to build:* Annotated code or design blocks with provable pre/post-condition pairs; optionally, use an IDE or tool that supports representing and checking these proofs.

(source: "[SWEBOK excerpt 27769f9cc03be9a38208]." — SWEBOK v4, [SWEBOK excerpt e06959b8e599f510df57])

---

### 5. Encode the Component as a Finite-State Machine and Apply State Transition Testing

Model the component's message-handling logic as a finite-state machine (FSM) in which states represent the component's internal condition and transitions represent message arrivals. Then derive a test suite that covers all states and transitions in that FSM — ensuring that every reachable combination of message-ordering paths is exercised by at least one test.

> *What to build:* An FSM model of the component, plus a test suite derived from it at the required coverage level (e.g., all-transitions or all-paths coverage).

(source: "[SWEBOK excerpt a1b0c19ab74697e76055] [SWEBOK excerpt 1e051e7dde1a64e3a5e8]." — SWEBOK v4, Software Testing KA, §3.1.7)

---

### 6. Apply Combinatorial Test Techniques to Cover Ordering Combinations Systematically

Since exhaustive manual testing of rare orderings is impractical, use combinatorial test techniques (e.g., pairwise or t-wise testing) to systematically generate test cases that cover every possible *combination* of t concurrent inputs or events. This is far more thorough than ad-hoc test design and will hit rare orderings that random testing misses.

> *What to build:* A combinatorial test-case generator configured for the message parameters and ordering variables, producing a compact but covering test suite.

(source: "[SWEBOK excerpt 12bb367a5311e46b2a98]… [SWEBOK excerpt 7b14e51185467d0e7f48]." — SWEBOK v4, Software Testing KA, §3.1.4)

---

### 7. Adapt the Test Strategy for Concurrent Systems: Favour Input/Output and Dependency-Thread Approaches

Recognise that standard hierarchical testing strategies do not transfer well to concurrent components. For concurrent and distributed systems, SWEBOK specifically recommends replacing classical hierarchical approaches with ones [SWEBOK excerpt 7eb89d750d5edc885828]** among concurrent events — precisely the structure needed to exercise message-ordering behaviour.

> *What to build:* A test harness that can inject messages in controlled orderings, observe outputs, and report results along dependency/event-thread lines rather than by classical test level.

(source: "[SWEBOK excerpt 6a9751d177dd09e14d16]." — SWEBOK v4, Software Testing KA, §7.1, "Testing concurrent and distributed applications")

---

### 8. Design the Component Explicitly for Concurrency: Atomicity, Synchronisation, and Scheduling

Address message-ordering failures at the design level, not just in testing. When designing for concurrency, explicitly reason about atomicity, synchronisation, and scheduling — because the choices made here determine which orderings can cause failures. Using sound synchronisation primitives (semaphores, monitors, mutexes) gives the component verifiable safety properties.

> *What to build:* A concurrency design document that records the synchronisation strategy, shared-variable access rules, and atomicity boundaries; backed by the use of appropriate primitives in the implementation.

(source: "[SWEBOK excerpt e0ae744d5fe630c2ce57]." — SWEBOK v4, Software Design KA, §3.1; and "[SWEBOK excerpt c9a696ffc54b8ed24434]. Well-known concurrency primitives include semaphores, monitors and mutexes." — SWEBOK v4, Computing Foundations KA, §4.10)

---

### 9. Use High-Level Design to Explicitly Specify Ordering and Timing Relationships

Make message-ordering requirements explicit and traceable from the design stage. High-level design should capture the *[SWEBOK excerpt 9fca0850ee7bef439965]*, including the tracing of end-to-end event threads. This gives the verification team a complete map of what orderings must be proved or tested.

> *What to build:* A high-level design document that includes an explicit section on message-ordering and timing relationships, with event-thread traces — serving as the reference for both model checking and test design.

(source: "High-level design addresses the following: … [SWEBOK excerpt a905173df6362972bec5]." — SWEBOK v4, Software Design KA, §2.1)

---

### 10. Consider Lightweight Formal Methods When Full Verification Is Too Costly

If full model checking or theorem proving is impractical for the whole component, use a lightweight formal method (such as Alloy) to get automatic, immediate feedback over a finite case space. This won't be complete — it examines only a finite set of cases — but it is far better than random testing at finding ordering bugs.

> *What to build:* An Alloy (or similar) model of the message-handling protocol, configured to search for counterexamples within a bounded scope of producers and message sequences.

(source: "[SWEBOK excerpt dd0c12c7be9727df2135]… [SWEBOK excerpt 6d5ec160eb7a5e620428]." — SWEBOK v4, [SWEBOK excerpt e06959b8e599f510df57])

---

### 11. Use Injection-Based and Simulation-Based Test Tools to Reproduce Specific Orderings

Deploy tooling specifically designed to trigger particular event orderings on demand. Injection-based tools allow controlled introduction or reproduction of specific problems (such as a specific arrival order), while simulation-based tools automate the execution of scenarios — letting you lock down the rare ordering that causes the bug and confirm it is fixed.

> *What to build:* An injection/simulation test harness that can reproducibly trigger specific message-arrival sequences, integrated into the continuous test pipeline.

(source: "Injection-based tools [SWEBOK excerpt 0d7260210eb931d71dfa]… Simulation-based tools [SWEBOK excerpt 6857d833103e25bd7c0b]." — SWEBOK v4, Software Testing KA, §8.2 Testing Tools)

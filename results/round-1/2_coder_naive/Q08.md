After each change to a system, how should the team decide what to test again, and at which point of the process?

### Answer

Here is a list of SWEBOK-based guidelines for deciding **what to test again after a change, and at which point in the process**:

---

### 1. Perform impact analysis before testing to identify what is affected

Before deciding what to retest, conduct an **impact analysis** to identify all systems, components, and products affected by [SWEBOK excerpt b571868b5408f6277179] of making the change and informs which tests are relevant.

> (source: *"[SWEBOK excerpt 0c7db2dd353e0c0d305c]… [SWEBOK excerpt a703690bd989e1f5d004]."*)

---

### 2. Use requirements traceability to pinpoint which test cases are implicated

Trace the changed requirement forward through design elements and code to its **linked test cases**. This establishes a precise "footprint" of what needs to be retested without retesting everything.

> (source: *"[SWEBOK excerpt 871601aa48ef8c64ec8f]."*)

---

### 3. Apply selective regression testing — do not rerun the entire test suite blindly

The core practice is **selective retesting**: re-execute only the tests needed [SWEBOK excerpt 021f9937eefeac172cee] system still meets its requirements, making a trade-off between assurance and available resources.

> (source: *"[SWEBOK excerpt 5e8de0cf888870acc928].'… [SWEBOK excerpt ed188bb49b4cb1a70930]."*)

---

### 4. Use test case selection, minimization, and prioritization to refine the regression suite

Within the selected regression tests, further **reduce redundant cases** (minimization) and **order the remaining ones** so that tests with the highest fault-detection potential, coverage, or risk run first.

> (source: *"[SWEBOK excerpt 000de4403a642a182b3f]."*)

> (source: *"[SWEBOK excerpt 27262e3cbd49775fd744]."*)

> (source: *"[SWEBOK excerpt bf8af63c65e6f2a8be74]."*)

---

### 5. Cover all relevant test levels, including non-functional properties

Regression testing should not be limited to functional checks. After a change, **each applicable test level** (unit, integration, system) and **non-functional properties** such as reliability, usability, security, and compatibility should also be considered.

> (source: *"[SWEBOK excerpt c20fe17691f9be60afb3]."*)

---

### 6. Retest after integration and before deployment to production

The correct **timing** for regression testing is after integration testing has been completed and before the system is deployed to production or operation.

> (source: *"[SWEBOK excerpt 1e9a2a9f2f8473c3d4f5]."*)

---

### 7. In continuous integration/DevOps pipelines, run regression tests continuously at every change

In CI/DevOps contexts, regression testing should be triggered **automatically with every integration event**, and quick techniques such as smoke testing should be used first to confirm the system is testable before releasing to the operational stage.

> (source: *"[SWEBOK excerpt 1219c7c74991d66fbb4a]."*)

---

### 8. Plan and coordinate retesting activities explicitly during maintenance

Test planning and activities must be deliberately organised during the processing of modification requests (MRs) and problem reports (PRs), because finding time and coordinating tests across team members working on multiple problems simultaneously is a recognized challenge.

> (source: *"[SWEBOK excerpt ed97e0b40bba8e689454]… [SWEBOK excerpt 8ad4509c53681c56233a]… [SWEBOK excerpt f6b08b73a414df4a83d2]."*)

---

### 9. Automate regression testing to make it scalable and repeatable

Because manual retesting is inefficient and error-prone, the team should **automate** as much regression testing as possible. Regression testing tools can re-execute the test suite and help select the relevant subset based on the change.

> (source: *"[SWEBOK excerpt 98474a699464d142bcfe]."*)

> (source: *"Because manual testing is inefficient, error-prone [SWEBOK excerpt e7a24ad31158e0f2902c]."*)

---

### 10. Keep test artifacts updated so changes in requirements or design are reflected in the test suite

Test reusability repositories must be maintained so that **when requirements or design change, the corresponding tests are updated accordingly**, ensuring the regression suite remains valid and effective.

> (source: *"[SWEBOK excerpt cc60c8d6f727f372cb4a]."*)

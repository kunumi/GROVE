### II. Exception-Handling Principles

3. **Include all relevant information in exception messages.** When an exception is thrown, the message should contain all information that led to the exception, so that callers and diagnosticians have full context.
(source: *"[SWEBOK excerpt e35013c655eb6da51b70]"*)

4. **Never use empty catch blocks.** An empty catch block silently swallows an error, making it impossible to detect or diagnose problems. Exception-handling policies should explicitly prohibit this.
(source: *"avoiding empty catch blocks"*)

5. **Know the exceptions that library code can throw.** When using third-party or standard libraries, you must understand what exceptions those libraries raise, so your code can handle or propagate them appropriately.
(source: *"knowing the exceptions the library code throws"*)

6. **Consider building a centralized exception reporter.** Rather than scattering exception-handling and reporting logic throughout the codebase, centralizing exception reporting makes the program's behavior more consistent and maintainable.
(source: *"perhaps building a centralized exception reporter"*)

7. **Standardize the program's use of exceptions.** A consistent, program-wide policy for how exceptions are signaled and caught reduces confusion and errors, especially in large or multi-team codebases.
(source: *"standardizing the program's use of exceptions"*)

8. **Use the throw/catch mechanism properly.** A routine signals an abnormal condition using `throw`; a `try-catch` block catches it and either processes the erroneous condition or returns control to the calling routine — do not misuse this structure.
(source: *"[SWEBOK excerpt aa95fcd1c82d33a12fdb] try-catch [SWEBOK excerpt 980c1713bcc05a3281c2]."*)

### III. Alternative Error-Handling Techniques

9. **Consider returning a neutral value** as an alternative to throwing an exception, when the program can continue safely with a default or zero-equivalent result.
(source: *"[SWEBOK excerpt 25fb1a8cce8efbace92b]."*)

10. **Consider substituting the next piece of valid data**, when the erroneous input or state can be skipped without compromising the program's overall correctness.
(source: *"[SWEBOK excerpt 25fb1a8cce8efbace92b]."*)

11. **Consider logging a warning message**, when the error is non-fatal and the program can continue, but the event must be recorded for later diagnosis or auditing.
(source: *"[SWEBOK excerpt 25fb1a8cce8efbace92b]."*)

12. **Consider returning an error code**, as a classic mechanism for signaling failure to callers without using the exception mechanism, particularly in environments where exception handling is unavailable or undesirable.
(source: *"[SWEBOK excerpt 25fb1a8cce8efbace92b]."*)

13. **Consider shutting down the software** when the error is severe enough that continued execution would be unsafe or meaningless — a controlled shutdown is preferable to undefined behavior.
(source: *"[SWEBOK excerpt 25fb1a8cce8efbace92b]."*)

### IV. Defensive Programming and Assertions

14. **Protect routines from invalid inputs through defensive programming.** Check the values of all input parameters and decide explicitly how to handle bad inputs before proceeding with any computation.

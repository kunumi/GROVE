## Guidelines for Deriving Test Cases for State- and Event-Dependent Components

### 1. Acknowledge that input values alone are insufficient — also specify the component's current state

When a component's reaction depends on its current state, test cases must capture both the triggering input and the state in which it arrives. SWEBOK explicitly warns that inputs alone do not fully determine behavior:

> (source: "[SWEBOK excerpt 8eb37559ff90e8481254].")

---

### 2. Model the component as a Finite-State Machine (FSM) before deriving tests

Represent the component's behavior as an FSM — a mathematical abstraction of states, inputs, outputs, and transitions — to give a precise basis for test design. This model can be expressed as the [SWEBOK excerpt a70aa0665be6c0f0db6f].

> (source: "[SWEBOK excerpt dcca413e0e55b572a699].")

---

### 3. Apply State Transition Testing: derive a test suite that covers all states and transitions at a chosen coverage level

Use State Transition Testing techniques, which are grounded in the FSM representation, to systematically generate a test suite. The coverage goal (e.g., all states visited, all transitions exercised) determines the completeness of the suite.

> (source: "[SWEBOK excerpt a1b0c19ab74697e76055] [SWEBOK excerpt 1e051e7dde1a64e3a5e8].")

---

### 4. Derive **positive** test cases for every defined (valid) transition

For each transition that is explicitly defined in the state model — i.e., for each valid (state, event) pair — create at least one positive test case that exercises that transition and verifies the expected resulting state and output.

> (source: "[SWEBOK excerpt f2d8a55feb05b9720395].")

---

### 5. Derive **negative** test cases from (state, event) combinations that are not defined in the model

Events that are not expected (and therefore not modelled) in a given state are equally important to test. Derive negative test cases from [SWEBOK excerpt 839d884c3f654a16cfb1] in the model to verify that the component handles them correctly (e.g., ignores them or raises an error).

> (source: "[SWEBOK excerpt 24bcfcac1d9464c98f15].")

---

### 6. Use state (transition) diagrams or statecharts as your modelling notation

Select a notation that explicitly represents how the component's behavior changes as a function of its current state and incoming events. State (transition) diagrams and statecharts are specifically designed for this purpose.

> (source: "[SWEBOK excerpt 92fdaa1f7412be44eba6].")

---

### 7. Complement state-transition tests with scenario-based testing to cover behavioral sequences

Use scenario-based testing alongside state transition testing. Scenarios capture sequences of events and transitions that reflect real or plausible usage, and they help validate requirements consistency and behavioral correctness.

> (source: "[SWEBOK excerpt e41ffd571d00f5662528].")

---

### 8. When using scenarios, test both typical (happy-path) and alternate (exception) workflows

Do not limit test cases to expected sequences of events. Make sure that test scenarios include both normal event sequences and alternative or exceptional paths through the state space.

> (source: "[SWEBOK excerpt 5a192333fccb5b4926de].")

---

### 9. Specify expected outcomes in terms of state changes, output values, and messages — not just return values

Each test case should capture the full observable effect of an event in a given state: the new state the component transitions to, any values produced, and any messages emitted.

> (source: "[SWEBOK excerpt 4fcb58bf4d8c43ed5d37]).")

---

### 10. Consider tool-assisted test case generation from formal state models

The more formally the state model is specified, the more feasible it is to derive test cases mechanically. Tools can generate both positive and negative test cases from state models, though determining expected results may still require domain expertise.

> (source: "[SWEBOK excerpt a8c445dfd5d4464a0be6]. […] [SWEBOK excerpt 187a6ec12533484420c5].")

### Question

Each new version of our web service is switched on for every user at the same moment, so a single faulty version breaks the service for everyone and getting the previous version back takes hours. How should we change the way new versions go live to limit the damage?

Answer with a list of guidelines. After each guideline, cite the source it comes from: the path of the SWEBOK file if you have it, otherwise a verbatim quote of at least 8 words from the passage, in the form (source: ...).

### Answer

# Summary

When a single faulty release breaks service for all users simultaneously, teams should adopt gradual, staged rollout strategies—canary releases, feature toggles, and environment-based staging—combined with automated monitoring, rehearsed rollback procedures, and smaller independent deployments to detect and contain problems before they reach all users.

# Guidelines

- Use canary release testing: partially and time-limitedly deploy a change, evaluate it, then decide whether to proceed with full deployment. (source: /workspace/swebok-v4/root/Software Testing, Operations, and Maintenance/Software Operations and Maintenance Practices/Automated Deployment and Canary Release Testing.md)

- Use application-based release strategies with feature toggles to enable or disable specific features via configuration, so a faulty feature can be turned off without a full rollback. (source: /workspace/swebok-v4/root/Software Testing, Operations, and Maintenance/Software Operations and Maintenance Practices/Software Release Engineering Strategies and Risk Reduction.md)

- Use environment-based release strategies with a staging environment to validate a new version before exposing it to all users. (source: /workspace/swebok-v4/root/Software Testing, Operations, and Maintenance/Software Operations and Maintenance Practices/Software Release Engineering Strategies and Risk Reduction.md)

- Plan and rehearse rollback before deploying any new version to production, and automate rollback so it triggers quickly enough that end users do not notice a problem. (source: /workspace/swebok-v4/root/Software Testing, Operations, and Maintenance/Software Operations and Maintenance Practices/Software Rollback and Problem Resolution in DevOps.md)

- Apply dark launches and canary testing when full production-environment testing is challenging or impossible. (source: /workspace/swebok-v4/root/Software Testing, Operations, and Maintenance/Software Operations and Maintenance Practices/Software Installation and Operational Verification Processes/Production Environment Testing and Verification/Production System Testing Challenges and Techniques.md)

- Release as a business decision only after automated validation passes; use automatic rollback if the new deployment does not pass its validation period. (source: /workspace/swebok-v4/root/Software Testing, Operations, and Maintenance/Software Operations and Maintenance Practices/Rollback and Data Migration in Software Deployment.md)

- Architect the application to enable small, independent deployments of single features or fixes rather than bundling many changes into one release. (source: /workspace/swebok-v4/root/Software Testing, Operations, and Maintenance/Software Operations and Maintenance Practices/DevOps Continuous Delivery and Independent Deployments.md)

- Automate deployment steps—packaging, configuration, smoke testing—to reduce manual errors and allow faster, more reliable releases. (source: /workspace/swebok-v4/root/Software Testing, Operations, and Maintenance/Software Operations and Maintenance Practices/Software Operations, Reliability, and Security Management/Deployment and Release Engineering in Software Operations.md)

- Automate monitoring and alerting so that failures are detected immediately and reaction time is minimised, reducing downtime and severity of incidents. (source: /workspace/swebok-v4/root/Software Testing, Operations, and Maintenance/Software Operations and Maintenance Practices/Software Installation and Operational Verification Processes/Software Deployment and Automation/Scripting and Automating Operational Tasks.md)

- Plan failure-handling logic during development and automate tests to ensure readiness in case of failure or catastrophic event. (source: /workspace/swebok-v4/root/Software Testing, Operations, and Maintenance/Software Operations and Maintenance Practices/Software Operations, Reliability, and Security Management/Software Failure Handling and Information Security Management.md)

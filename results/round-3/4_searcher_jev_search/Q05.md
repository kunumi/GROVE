## Guidelines for Choosing Test Inputs for a Function That Accepts Numeric Values Within a Valid Range

### 1. Partition the input domain into equivalence classes and pick one representative value per class.

Divide all possible numeric inputs into subsets — at minimum a **valid** class (inputs within the accepted range) and one or more **invalid** classes (inputs outside it). Select a small, representative set of test cases from each class rather than testing every possible value, since any member of a class is expected to exercise the same behaviour.

> (source: "[SWEBOK excerpt e279d64d08518504c456] [SWEBOK excerpt 9fbbc794267d8d3b05cc]." — `/workspace/swebok-v4/root/Software Testing Methodologies and Techniques/Software Testing Approaches and Techniques/Classification and Specification-Based Testing Techniques.md`)

---

### 2. Always include test cases at and near the boundaries of the valid range.

Faults cluster at the extremes of an input domain, so explicitly test the minimum value, the maximum value, and values immediately adjacent to those endpoints (just inside and just outside the boundary).

> (source: "[SWEBOK excerpt bedee61fb08d8b967278]." — `/workspace/swebok-v4/root/Software Testing Methodologies and Techniques/Boundary Value Analysis and Syntax Testing Techniques.md`)

---

### 3. Extend boundary testing to values *outside* the valid range (robustness testing).

Go beyond the declared limits and supply out-of-range numeric inputs as well. This checks that the function handles unexpected or erroneous inputs gracefully — for example, by producing an error message or initiating error processing.

> (source: "[SWEBOK excerpt ac52d3263555a546a515]." — `/workspace/swebok-v4/root/Software Testing Methodologies and Techniques/Boundary Value Analysis and Syntax Testing Techniques.md`)

---

### 4. Treat valid and invalid numeric inputs as distinct equivalence classes, each requiring at least one test case.

The partitioning criterion explicitly distinguishes between *valid* inputs that the function should accept and process, and *invalid* inputs it should reject. Each category is a separate equivalence class and must be exercised; a single representative from each class is usually sufficient.

> (source: "[SWEBOK excerpt 331b1e552e5507845df1]." — `/workspace/swebok-v4/root/Software Testing Methodologies and Techniques/Boundary Value Analysis and Syntax Testing Techniques.md`)

---

### 5. Apply error guessing to include numerically "suspicious" values based on experience.

Draw on knowledge of common faults (e.g., off-by-one errors, division-by-zero risks, sign errors) and the history of defects found in similar functions. Add specific numeric inputs that you, as an experienced engineer, judge likely to expose those known fault types.

> (source: "[SWEBOK excerpt 58750920721c36886ebb]." — `/workspace/swebok-v4/root/Testing Methodologies and Quality Assurance Practices/Testing Approaches and Execution Strategies/Software Testing Techniques and Methodologies/Experience-Based Techniques for Test Suite Generation.md`)

---

### 6. Supplement deterministic inputs with randomly drawn values from the valid input domain.

Random testing picks points from within the known input domain and can automate the generation of additional test cases beyond those chosen analytically. It is especially useful for increasing coverage economically and can be enhanced through adaptive strategies that direct sampling based on other criteria.

> (source: "[SWEBOK excerpt 2e0f1efa93239b85b4bd]." — `/workspace/swebok-v4/root/Testing Methodologies and Quality Assurance Practices/Testing Approaches and Execution Strategies/Software Testing Techniques and Methodologies/Random Testing and Evidence-Based Software Engineering Approaches.md`)

---

### 7. Decide between deterministic and random selection based on the testing goal.

When the goal is thorough functional verification, choose inputs analytically (equivalence classes, boundaries). When the goal is reliability estimation, random inputs drawn from an operational distribution are more appropriate — they model how the function will actually be exercised in production.

> (source: "[SWEBOK excerpt d624d4acb5ce66fad14e]." — `/workspace/swebok-v4/root/Testing Methodologies and Quality Assurance Practices/Software Testing Techniques, Measurement, and Management/Testing Approaches and Test Case Selection Methods/Deterministic vs. Random Test Case Selection.md`)

---

### 8. When reliability is the objective, weight input values by their real-world frequency of occurrence.

Usage-based (operational profile) testing assigns probabilities to inputs proportional to how often they appear in actual use. Rather than giving equal weight to all numeric values in the range, bias the selection toward values users will most frequently supply, so that test results predict operational reliability.

> (source: "[SWEBOK excerpt 53a8a2cdb65508bd6f08]." — `/workspace/swebok-v4/root/Testing Methodologies and Quality Assurance Practices/Software Testing Techniques, Measurement, and Management/Testing Methods and System Diversity/Testing Approaches Based on Operational Profiles and Usability.md`)

---

**Summary.** The SWEBOK passages support a layered strategy: (1) partition the range into valid/invalid classes and pick representatives; (2) stress boundaries and just-out-of-range values; (3) add experience-guided special cases; (4) fill gaps with random sampling; and (5) shift to frequency-weighted selection when reliability estimation is the goal. The SWEBOK does not, in those passages, provide specific numeric examples (e.g., "always test zero") beyond the general boundary/equivalence framework described above.

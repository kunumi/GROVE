## Guidelines for Evaluating a Proposed Service-Decomposition Architecture Before Implementation

---

### 1. First, identify and formulate all Architecturally Significant Requirements (ASRs)

Before the structure can be judged, the team must surface every requirement that actually shapes the architecture—including response-time targets, cost budgets, and change-friendliness goals—and treat them as the formal test bench for the evaluation.

### 2. Explicitly address the distribution design concern—performance, reliability, and resource consumption

Splitting a module into networked services moves the design into the "distribution of components" space. The SWEBOK identifies this as a named design quality concern requiring deliberate analysis of performance, scalability, and availability.

> *"[SWEBOK excerpt da01806e63341c6e5ab6]."*

### 3. Evaluate the architecture using ATAM or comparable structured methods

ATAM (Architectural Tradeoff Analysis Method) is the SWEBOK's primary named instrument for pre-implementation evaluation. It uses a utility tree to score each quality attribute, then systematically surfaces conflicts among them.

> *"The Architecture Tradeoff Analysis Method (ATAM) [SWEBOK excerpt 55bdeafc7cfabab1d90a])."*

### 4. Ask the four canonical evaluation questions about every proposed structure

The SWEBOK frames architecture goodness as four concrete questions: robustness over time; fitness for intended use; cost-effectiveness of construction; and clarity for those who must build and maintain it. Each becomes a checkpoint for the service-decomposition proposal.

### 5. Use multi-criteria decision-making techniques to score trade-offs numerically

Where performance (response time), cost, and modifiability pull in opposite directions, compensatory techniques—additive weighting, analytic hierarchy process (AHP), or Gilb's Impact Estimation—allow each criterion to be scored and combined so the team can see which trade-offs are acceptable.

### 6. Recognise the economic asymmetries among quality-of-service constraints

Response time and cost do not have the same value curve: for some constraints (like throughput) value rises with performance, while for others (like response time and hosting cost) value *decreases* as the number climbs. The team must chart each constraint's cost-effectiveness curve separately and find the most cost-effective operating point.

### 7. Conduct a structured architecture review—formal or active—before implementation

Architecture reviews can be informal/expertise-based or more rigorous (e.g., "active reviews" where each reviewer performs a specific activity rather than working from a checklist). Either way, they expose risks and gaps in the proposed decomposition before any code is written.

### 8. Apply architecture metrics to quantify coupling, cohesion, and complexity of the proposed decomposition

Metrics such as component dependency, cyclomatic complexity, module coupling and cohesion, and levels of nesting give the team objective signals about whether the proposed service boundaries will produce a structure that is easy to change.

> *"Various architecture metrics have been defined… [SWEBOK excerpt 95ae979a26d714568a3f]."*

### 9. Create multiple architecture views and reason from each one

No single diagram exposes all concerns simultaneously. Using viewpoints—logical, component-and-connector, deployment, information, performance—lets different stakeholders (users, developers, operators, project managers) check the design from their own perspective and surface concerns that a single view would hide.

> *"[SWEBOK excerpt af229ff9751a640035af]."*

### 10. Apply static design analysis and simulation/prototyping to predict behaviour without full implementation

Formal or semi-formal analysis (fault-tree analysis, automated cross-checking) can be done on the architecture description alone. Simulation and feasibility prototypes go further, letting the team predict performance or validate cost assumptions before committing to the full distributed build.

> *"[SWEBOK excerpt 7c9848044a0924e23933]… [SWEBOK excerpt e9370b60de6cf6bb205e])."*

### 11. Document the rationale for every non-trivial decision, including rejected alternatives

Recording *why* the team accepted or rejected the distributed decomposition—assumptions made, trade-offs weighed, alternatives considered—makes the architecture auditable and prevents future teams from inadvertently repeating costly mistakes or ignoring the original reasoning.

> *"[SWEBOK excerpt 510e33216e1de5586418]… [SWEBOK excerpt 50dabdf9f63fc60ee212]."*

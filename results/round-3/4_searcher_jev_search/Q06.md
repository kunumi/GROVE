## Guidelines for Deriving Test Cases When Six Configuration Parameters Each Have Multiple Values

---

### 1. Use specification-based (black-box) techniques as the primary approach

Base your test-case generation on the function's input/output specification rather than on its internal code. The underlying idea of specification-based [SWEBOK excerpt fd4b3e4e9e51bd21ef14]."**

(source: `/workspace/swebok-v4/root/Software Testing Methodologies and Techniques/Software Testing Approaches and Techniques/Classification and Specification-Based Testing Techniques.md`)

---

### 2. Apply equivalence partitioning to reduce the value space per parameter

For each of the six parameters, group its possible values into equivalence classes and test one representative value per class rather than every value. **"[SWEBOK excerpt e279d64d08518504c456] [SWEBOK excerpt 9fbbc794267d8d3b05cc]. [SWEBOK excerpt 83b36aaa6987b9eb0caf]."**

(source: `/workspace/swebok-v4/root/Software Testing Methodologies and Techniques/Boundary Value Analysis and Syntax Testing Techniques.md` and `/workspace/swebok-v4/root/Software Testing Methodologies and Techniques/Software Testing Approaches and Techniques/Classification and Specification-Based Testing Techniques.md`)

---

### 3. Add boundary value tests for parameters whose values form a range

For any parameter that has an ordered or ranged set of values, derive additional test cases at or near the extremes of that range, since faults cluster there. **"[SWEBOK excerpt 22b5a76f3ce0e0a3a3af]."**

(source: `/workspace/swebok-v4/root/Software Testing Methodologies and Techniques/Boundary Value Analysis and Syntax Testing Techniques.md`)

---

### 4. Use combinatorial test techniques to cover parameter interactions systematically

Rather than testing every combination (all-combinations testing), apply one of the recognised combinatorial strategies scaled to the risk and budget. **"[SWEBOK excerpt 610118fe219a0b0e0989]."**

(source: `/workspace/swebok-v4/root/Software Testing Methodologies and Techniques/Combinatorial Test Techniques Overview.md`)

---

### 5. Apply Each Choice Testing as the minimum-coverage baseline

As a least-cost starting point, choose at least one test case that exercises each distinct value of each parameter at least once. This is the "Each Choice Testing" technique identified in SWEBOK's list of combinatorial strategies.

**"[SWEBOK excerpt 1f7ec2b0d4b2948e4bf9]."**

(source: `/workspace/swebok-v4/root/Software Testing Methodologies and Techniques/Combinatorial Test Techniques Overview.md`)

---

### 6. Prefer pairwise (pair-wise) testing when interaction faults among pairs of parameters are the primary concern

Pairwise testing ensures every pair of parameter values appears in at least one test case, catching the most common category of interaction faults at a fraction of the all-combinations cost. **"[SWEBOK excerpt 84129f160b87efa4ccba]."**

(source: `/workspace/swebok-v4/root/Software Testing Methodologies and Techniques/Systematic Test Case Derivation and Combinatorial Methods/Combinatorial Testing and Decision Tables.md`)

---

### 7. Scale up to t-wise testing when higher-order interaction faults are suspected

If two-parameter coverage is insufficient and resources allow, generalise to t-wise testing to cover every combination of *t* parameters (t > 2) while still staying far below the cost of all-combinations [SWEBOK excerpt 656acd05fe033c2f3039])."**

(source: `/workspace/swebok-v4/root/Software Testing Methodologies and Techniques/Systematic Test Case Derivation and Combinatorial Methods/Combinatorial Testing and Decision Tables.md`)

---

### 8. Use orthogonal arrays as an implementation tool for combinatorial coverage

Orthogonal Array Testing (OAT) is the standard mathematical vehicle for constructing a minimal test suite that achieves the desired t-wise coverage. **"[SWEBOK excerpt 025fb71ffef7c351cf7d])."**

(source: `/workspace/swebok-v4/root/Software Testing Methodologies and Techniques/Systematic Test Case Derivation and Combinatorial Methods/Combinatorial Testing and Decision Tables.md`)

---

### 9. Use decision tables when parameter combinations imply distinct required actions

Where specific combinations of parameter values map to distinct expected outputs or actions, capture those logical relationships in a decision table so that every distinct condition/action rule is covered by at least one test case. **"[SWEBOK excerpt a11245cd76e2da148e79])."**

(source: `/workspace/swebok-v4/root/Software Testing Methodologies and Techniques/Systematic Test Case Derivation and Combinatorial Methods/Combinatorial Testing and Decision Tables.md`)

---

### 10. Use cause-effect graphing to model and explore combinations of conditions

When the relationships between parameter values and outputs are complex, model them as a cause-effect graph to systematically derive test cases that cover meaningful combinations. **"[SWEBOK excerpt f7aeee26341760feaae7]."**

(source: `/workspace/swebok-v4/root/Software Testing Methodologies and Techniques/Cause-Effect Graphing Techniques.md`)

---

### 11. Combine functional and structural techniques, guided by organisational constraints

No single technique is sufficient. Depending on budget and risk, combine the combinatorial/specification-based techniques above with structure-based (white-box) techniques for stronger overall coverage. **"[SWEBOK excerpt 14a15524a4aed4318039]."**

(source: `/workspace/swebok-v4/root/Testing Methodologies and Quality Assurance Practices/Software Testing Techniques, Measurement, and Management/Testing Approaches and Test Case Selection Methods/Combining Functional and Structural Testing Techniques.md`)

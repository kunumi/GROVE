## Guidelines for Preserving What Is Needed to Reproduce a Past Shipped Executable

### 1. Place supporting build tools — including compilers — under SCM control

The build toolchain (compiler, linker, assembler, etc.) must itself be a managed configuration item. If it is not, there is no guarantee the correct tool versions will be available when a rebuild is needed.

> "[SWEBOK excerpt 9e95c89fd76e71157968]."

(source: `/workspace/swebok-v4/root/Software Maintenance and Configuration Management/Software Configuration Management Planning and Implementation/Software Configuration Management Tools and Processes/Software Build Tools and Version Control Management.md`)

---

### 2. Preserve and version-control build instructions alongside the source code

Build instructions encode the exact sequence of steps, flags, and parameters used at build time. Losing them makes it impossible to repeat the process faithfully, even if all other artifacts are present.

> "[SWEBOK excerpt 43b847da6b809a02fbd0]."

(source: `/workspace/swebok-v4/root/Software Maintenance and Configuration Management/Software Configuration Management Planning and Implementation/Software Configuration Management Tools and Processes/In-Process Audits and Software Release Management.md`)

---

### 3. Apply configuration control to all purchased or acquired software products, such as compilers and third-party libraries

Third-party and purchased components (commercial libraries, open-source packages, subcontracted software) must be brought under configuration control. SCM planning must address how changes or updates to those items will be evaluated and managed.

> "[SWEBOK excerpt c963e608b16aa4174e20]."

(source: `/workspace/swebok-v4/root/Software Maintenance and Configuration Management/Software Configuration Management Planning and Implementation/Software Configuration Management Planning and Implementation/Software Configuration Management Tools and Interface Control/SCM Workbenches and Vendor Control Planning.md`)

---

### 4. Identify and place every relevant software item — including source code, executable code, code libraries, tools, and documentation — under SCM as a Software Configuration Item (SCI)

The scope of what must be controlled is broad. Source code alone is not sufficient; all artifacts that contribute to the final product must be explicitly identified and controlled.

> "[SWEBOK excerpt ae8c53959623d22d6586]."

(source: `/workspace/swebok-v4/root/Software Maintenance and Configuration Management/Software Configuration Management Planning and Implementation/Software Configuration Management and Change Control/Software Configuration Items Selection and Change Recording.md`)

---

### 5. Establish and maintain a formal product baseline at the point of release

A baseline freezes the precise state of all controlled items at a designated milestone (such as a customer delivery). Without a formal release baseline, there is no authoritative record of what was actually shipped.

> "[SWEBOK excerpt 2aa74b599340610f1ebf]."

(source: `/workspace/swebok-v4/root/Software Maintenance and Configuration Management/Software Configuration Management Planning and Implementation/SCM Audits and Configuration Identification/Software Configuration Identification and Item Control.md`)

---

### 6. Use a version-control system and a binary repository to store both source artifacts and build outputs

The configuration management system (CMS) must include version control for source and configuration files, and a repository for binaries produced by the build, so that past build artifacts can be retrieved and redeployed.

> "[SWEBOK excerpt 0f85ed080860bc1fbf6b]. … [SWEBOK excerpt 93cb0cdc79d239bdea25]."

(source: `/workspace/swebok-v4/root/Software Maintenance and Configuration Management/Software Configuration Management Planning and Implementation/Software Configuration Management Tools and Processes/Configuration Management System Tools and Components.md`)

---

### 7. Produce and retain a Software Bill of Materials (SBOM) for each build

An SBOM records exactly which artifacts (and by extension which dependency versions) were included in a particular build. It is an essential CM output that makes it possible to reconstruct what went into a release.

> "[SWEBOK excerpt 450578f233490c4cd9fa]."

(source: `/workspace/swebok-v4/root/Software Maintenance and Configuration Management/Software Configuration Management Planning and Implementation/Software Configuration Management Tools and Processes/Build Quality Assurance and Configuration Management/Software Build Artifacts and Continuous Integration Processes.md`)

---

### 8. Manage the dependency supply chain — control direct and indirect library dependencies and avoid unnecessary or untrusted ones

Uncontrolled dependencies (e.g., packages fetched from public registries without pinning) are a primary cause of unreproducible builds. Each dependency must be identified, managed, and recorded.

> "[SWEBOK excerpt 8d648deeba0c8ab516c0]. … Regulations and monitoring [SWEBOK excerpt fd3c4dabfaf88745b444]."

(source: `/workspace/swebok-v4/root/Software Construction Methods and Languages/Dependency Management and Construction Practices/Managing Software Dependencies and Supply Chain Risks.md`)

---

### 9. Conduct a physical configuration audit (PCA) at release time to verify that the build artifacts match the documented configuration

A PCA confirms that what was actually built corresponds to what is recorded in SCM. Performing it at release time creates a verified, auditable record — not just an assumed one — of the delivered configuration.

> "[SWEBOK excerpt b20badb9883ac5fa9584]. … [SWEBOK excerpt afd23e1e64ecc48c56f2] … [SWEBOK excerpt 32f49d115d798c5142d5]."

(source: `/workspace/swebok-v4/root/Software Maintenance and Configuration Management/Software Configuration Management Planning and Implementation/Software Configuration Management Tools and Processes/Software Configuration Auditing and Verification/Software Configuration Auditing and Formal Audits.md`)

---

### 10. Record the software configuration used during testing, so that test incidents and defect reports can be correlated to the exact release state

Defect investigation after delivery depends on being able to link a reported problem to a specific, identifiable configuration. Test incident documentation must capture which software configuration was under test.

> "[SWEBOK excerpt 993b9b9be76307bd9171])."

(source: `/workspace/swebok-v4/root/Software Testing, Operations, and Maintenance/Test Generation, Environment Setup, and Incident Management/Test Incident Reporting and Documentation Process.md`)

Reproducibility failures are almost always traceable to items that were never brought under control in the first place. The SCM plan must explicitly address tool governance and third-party component governance from the outset.

## Guidelines for Deciding What to Retest After a Change, and When

---

### 1. Apply selective retesting — do not automatically rerun the entire test suite

Regression testing is defined as [SWEBOK excerpt c9b906c0611fa31191a0]."* The key word is *selective*: the goal is to show that the system still passes previously passing tests, not to blindly repeat everything.

(source: "[SWEBOK excerpt cefe3b0cf2a84ba25da0].'" — `/workspace/swebok-v4/root/Software Testing Levels, Objectives, and Approaches/Alpha, Beta, and Regression Testing Procedures.md`)

---

### 2. Use traceability to identify which tests are affected by a change

Trace the changed requirement or design element forward to its linked code units, then trace those code units to their linked test cases. This chain of traceability establishes the "footprint" — the actual volume of work and tests that must be revisited. Test cases not reachable via this traceability chain are candidates for exclusion from the retest run.

(source: "[SWEBOK excerpt 871601aa48ef8c64ec8f]." — `/workspace/swebok-v4/root/Requirements Management, Quality, and Testing Practices/Requirements Traceability and Change Impact Analysis/Traceability in Software Requirements and Design.md`)

---

### 3. Perform impact analysis before deciding on the test scope

Before selecting which tests to run, the team should conduct an impact analysis of the proposed change, considering factors such as the category of maintenance, the size of the modification, the costs involved, the testing required, and any performance, safety, or security impacts. This analysis scopes the retest effort appropriately.

(source: "[SWEBOK excerpt 9d079afee5ecfbb6f422]." — `/workspace/swebok-v4/root/Software Testing, Operations, and Maintenance/Software Operations and Maintenance Practices/Software Maintenance Management and Organization/Impact Analysis in Software Maintenance.md`)

---

### 4. Apply test case selection, minimization, and prioritization to manage the regression suite

Once the retest candidates are identified, three techniques help manage the resulting suite: (a) **selection** — choosing only the tests relevant to the changed code; (b) **minimization** — reducing redundant tests in that selection; and (c) **prioritization** — scheduling the remaining tests to maximize fault detection rate early. Use specialized regression testing tools to automate this selection based on the change made.

(source: "[SWEBOK excerpt 000de4403a642a182b3f]." — `/workspace/swebok-v4/root/Software Testing Levels, Objectives, and Approaches/Regression Testing in Software Development.md`)

(source: "[SWEBOK excerpt 2385d456b65f4063aae4]." — `/workspace/swebok-v4/root/Software Testing, Operations, and Maintenance/Software Operations and Maintenance Practices/Software Testing Tools and Standards/Software Testing Tools and Techniques/Software Testing and Reliability Evaluation Tools.md`)

---

### 5. Balance assurance against cost — a trade-off must be made explicitly

Running every test on every change is often impractical. The team must consciously weigh the assurance provided by more thorough regression testing against the resources (time, effort) required. This trade-off should be made explicitly rather than by default.

(source: "[SWEBOK excerpt 67db88e68b13fb1652d2]." — `/workspace/swebok-v4/root/Software Testing Levels, Objectives, and Approaches/Alpha, Beta, and Regression Testing Procedures.md`)

---

### 6. Apply regression testing at all appropriate test levels, including non-functional ones

A change may have consequences at multiple levels of the system. [SWEBOK excerpt f38f96576c9fba529c50] (unit, integration, system). It may also cover non-functional properties such as reliability, accessibility, usability, maintainability, and compatibility — not only functional correctness.

(source: "[SWEBOK excerpt c20fe17691f9be60afb3]." — `/workspace/swebok-v4/root/Software Testing Levels, Objectives, and Approaches/Regression Testing in Software Development.md`)

---

### 7. Begin test planning and execution at the moment a change request (MR/PR) is processed — not at the end

Test planning and activities must occur during the processing of modification requests (MRs) and problem reports (PRs), not after the code has been fully integrated. Because full retesting is costly, the maintainer should plan and execute the *appropriate* tests at that moment to validate each modification.

(source: "[SWEBOK excerpt 2a45294c94fb2f2db8a3]." — `/workspace/swebok-v4/root/Software Testing, Operations, and Maintenance/Software Operations and Maintenance Practices/Software Maintenance_ Technical, Management, and Comprehension Challenges/Software Comprehension and Testing in Maintenance.md`)

---

### 8. Retest at every integration point in continuous integration pipelines

In CI/CD environments, every integration of a team member's change should trigger an automated build-and-test cycle so that integration errors are detected as quickly as possible. Additionally, smoke testing should be used before full regression testing to verify the build is testable, avoiding wasted effort on a broken environment.

(source: "[SWEBOK excerpt 10c5439290a2d46de22a]." — `/workspace/swebok-v4/root/Software Maintenance and Configuration Management/Software Maintenance, Evolution, and Quality Assurance/Continuous Integration, Delivery, and Software Maintenance/Continuous Integration and DevOps Practices/Continuous Integration, Delivery, Testing and Deployment.md`)

(source: "[SWEBOK excerpt 306e7160f60ada0eaa9b]." — `/workspace/swebok-v4/root/Software Testing, Operations, and Maintenance/Testing Across Development Processes and Domains/Testing Strategies Across Methodologies and Domains/Test Automation and Domain-Specific Testing Approaches.md`)

---

### 9. Run the regression suite *[SWEBOK excerpt c606948e113f7dc3e6ab]

The standard sequencing for regression testing within a release cycle is: perform it after integration testing (so the integrated build is stable) but before deployment to production or operation (so defects introduced by the change are caught before users are affected).

(source: "[SWEBOK excerpt 51c60fad5f5a335bf6d9]." — `/workspace/swebok-v4/root/Software Testing Levels, Objectives, and Approaches/Regression Testing in Software Development.md`)

---

### 10. Revisit the test scope at predetermined milestones when requirements or scope change

If the change also modifies requirements, the team should use backward and forward traceability analysis — and risk analysis — at predetermined milestone points to reassess the impact on test artifacts. Traceability links (e.g., from test scripts back to requirements and design) help monitor requirements satisfaction and support decisions on when to stop testing.

(source: "[SWEBOK excerpt 1e8b9bbcfdf4f8f0375e]." — `/workspace/swebok-v4/root/Software Maintenance and Configuration Management/Software Configuration Management Planning and Implementation/Project Planning and Requirements Management Framework/Requirements Review and Revision Process.md`)

---

### 11. Keep test artifacts up to date so they remain reusable across changes

As software requirements and design evolve, test cases and test environments must be updated to reflect those changes. Maintaining knowledge-based repositories of test cases and results makes rerunning or adapting tests less costly when the next change arrives.

(source: "[SWEBOK excerpt cc60c8d6f727f372cb4a]." — `/workspace/swebok-v4/root/Testing Methodologies and Quality Assurance Practices/Software Testing Techniques, Measurement, and Management/Test Completion and Knowledge Management/Test Completion and Artifact Reusability in Software Testing.md`)

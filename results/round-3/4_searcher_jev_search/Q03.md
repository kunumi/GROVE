## Guidelines for Designing Error and Abnormal-Condition Handling

### 1. Recognise that error handling affects correctness, robustness, and other nonfunctional attributes
How errors are handled has a direct impact on a program's ability to satisfy its requirements beyond mere functionality. This should be an explicit concern during design, not an afterthought.
> (source: "[SWEBOK excerpt 5cbc324f523e1430b28c]." — `/workspace/swebok-v4/root/Software Construction Techniques and Practices/Contract Design and Error Handling Strategies/Error Handling, Exception Handling, and Fault Tolerance.md`)

### 2. Use defensive programming to protect routines from invalid inputs
Every routine should be designed to protect itself from being broken by bad data. This means checking the values of all input parameters and deciding in advance how bad inputs will be handled.
> (source: "[SWEBOK excerpt edaaca9c62404676ff9e]." — `/workspace/swebok-v4/root/Software Construction Techniques and Practices/Contract Design and Error Handling Strategies/Design by Contract and Defensive Programming.md`)

### 3. Use assertions to detect errors and flush out interface mismatches early
Assertions are a standard defensive tool for checking input values and catching mismatched interface assumptions before they propagate. They are typically compiled in during development and compiled out for production to avoid performance degradation.
> (source: "[SWEBOK excerpt ebcb119299ef60c6bdcc]." — `/workspace/swebok-v4/root/Software Construction Techniques and Practices/Assertions and Design by Contract in Programming.md`)

### 6. When using exceptions, follow a carefully designed exception-handling policy
Exceptions should not be used in an ad hoc way. The SWEBOK identifies several common principles for well-designed exception handling:

- **Include all information that led to the exception** in the exception message, so the recipient has full diagnostic context.
- **Avoid empty catch blocks**, which silently swallow errors and obscure failures.
- **Know the exceptions that library code throws**, so that third-party failures are not accidentally suppressed or mishandled.
- **Consider building a centralized exception reporter** to enforce consistent reporting across the codebase.
- **Standardize the program's use of exceptions** so that exception types, granularity, and handling strategies are consistent throughout.

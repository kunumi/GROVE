## Strategies That Let Software Keep Working When Errors Occur at Runtime

The following guidelines are drawn exclusively from SWEBOK v4. Each is cited to the exact passage it comes from.

---

### 1. Use fault tolerance as a collection of coordinated techniques — detect errors first, then recover or contain them

Treat fault tolerance not as a single trick but as a layered approach: first detect the error, then either recover from it or, if recovery is impossible, prevent it from spreading further.

> (source: "[SWEBOK excerpt 909de8a0fa8186bde761]." — `/workspace/swebok-v4/root/Software Construction Techniques and Practices/Fault Tolerance Techniques and Executable Models.md`)

---

### 2. Back up state and retry the failed operation

When an error occurs, roll back to a previously saved state and attempt the operation again. This is one of the most common fault-tolerance strategies identified by SWEBOK.

> (source: "[SWEBOK excerpt 7c7c13df07628c3c7d07]." — `/workspace/swebok-v4/root/Software Construction Techniques and Practices/Fault Tolerance Techniques and Executable Models.md`)

---

### 3. Use auxiliary code with voting algorithms (N-version redundancy)

Run multiple independent implementations of the same logic in parallel and have them vote on the correct result. If one version produces an erroneous result, the majority vote keeps the system producing a correct or acceptable output.

> (source: "[SWEBOK excerpt 94c1f6f4911bc7a1a0a1]." — `/workspace/swebok-v4/root/Software Construction Techniques and Practices/Fault Tolerance Techniques and Executable Models.md`)

---

### 4. Replace an erroneous value with a safe, benign phony value

When a computed value is detected as erroneous and recovery is not feasible, substitute a neutral or pre-defined "safe" value so that execution can continue without crashing.

> (source: "[SWEBOK excerpt 8b0b1372e25e459ce254]." — `/workspace/swebok-v4/root/Software Construction Techniques and Practices/Fault Tolerance Techniques and Executable Models.md`)

---

### 5. Return a neutral value or substitute the next valid piece of data

Instead of propagating bad data or terminating, a routine can return a neutral (zero-effect) value or skip the bad input and continue with the next valid data item, allowing the rest of the program to keep running normally.

> (source: "[SWEBOK excerpt 25fb1a8cce8efbace92b]." — `/workspace/swebok-v4/root/Software Construction Techniques and Practices/Contract Design and Error Handling Strategies/Error Handling, Exception Handling, and Fault Tolerance.md`)

---

### 6. Log a warning message instead of failing silently or crashing

Rather than halting execution, record the error condition in a log. This keeps the system running while creating an audit trail for diagnosis and later correction.

> (source: "[SWEBOK excerpt c8bb1330641234b4e5c9]." — `/workspace/swebok-v4/root/Software Construction Techniques and Practices/Contract Design and Error Handling Strategies/Error Handling, Exception Handling, and Fault Tolerance.md`)

---

### 7. Return an error code to the caller rather than propagating the failure

Signal the error upward via a return code so that calling code can decide how to handle it, rather than letting the error silently corrupt state or crash the program.

> (source: "[SWEBOK excerpt fd33a22a8011f92854a3]." — `/workspace/swebok-v4/root/Software Construction Techniques and Practices/Contract Design and Error Handling Strategies/Error Handling, Exception Handling, and Fault Tolerance.md`)

---

### 8. Use structured exception handling (throw / try-catch) to intercept and process errors

Raise exceptions at the point of failure using `throw`, catch them in a `try-catch` block, and either handle the erroneous condition there or return control to the calling routine — keeping the program alive rather than crashing.

> (source: "[SWEBOK excerpt ea790ec47590a1c6d2e8] try-catch [SWEBOK excerpt 980c1713bcc05a3281c2]." — `/workspace/swebok-v4/root/Software Construction Techniques and Practices/Contract Design and Error Handling Strategies/Error Handling, Exception Handling, and Fault Tolerance.md`)

---

### 9. Apply consistent exception-handling policies across the codebase

Design and enforce a uniform set of exception-handling rules so that errors are handled predictably everywhere. Key practices include including all contextual information in the exception message, never leaving catch blocks empty, knowing what exceptions library code throws, building a centralized exception reporter, and standardizing how exceptions are used.

> (source: "[SWEBOK excerpt 8a98e7d1cb740854b979]." — `/workspace/swebok-v4/root/Software Construction Techniques and Practices/Contract Design and Error Handling Strategies/Error Handling, Exception Handling, and Fault Tolerance.md`)

---

### 10. Apply defensive programming to validate all inputs before use

Protect each routine from being broken by invalid inputs by checking the values of all input parameters before acting on them. This prevents bad data from propagating into internal logic and causing failures.

> (source: "[SWEBOK excerpt edaaca9c62404676ff9e]." — `/workspace/swebok-v4/root/Software Construction Techniques and Practices/Contract Design and Error Handling Strategies/Design by Contract and Defensive Programming.md`)

---

### 11. Use assertions to detect erroneous conditions early

Embed assertions at critical points in the code to check for unexpected states. By detecting the error close to where it arises — rather than letting it propagate — the program can respond to it in a controlled way.

> (source: "[SWEBOK excerpt 37955106e84416946661]." — `/workspace/swebok-v4/root/Software Construction Techniques and Practices/Contract Design and Error Handling Strategies/Error Handling, Exception Handling, and Fault Tolerance.md`)

> (source: "[SWEBOK excerpt 9595286a3d28b3ef46b9]." — `/workspace/swebok-v4/root/Software Construction Techniques and Practices/Contract Design and Error Handling Strategies/Design by Contract and Defensive Programming.md`)

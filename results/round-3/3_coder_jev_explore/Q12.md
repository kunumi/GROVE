### Question

How should modules be organized so that the software stays easy to maintain, and how can an existing badly structured program be improved without its users noticing any difference?

Answer with a list of guidelines. After each guideline, cite the source it comes from: the path of the SWEBOK file if you have it, otherwise a verbatim quote of at least 8 words from the passage, in the form (source: ...).

### Answer

# Summary

Well-structured software organizes modules around single responsibilities, loose coupling, high cohesion, and information hiding. Existing poorly structured programs can be improved through refactoring—reorganizing internals without changing observable behavior—while documentation of design rationale and use of reverse engineering support understanding and safe modification.

# Guidelines

- Apply **information hiding (encapsulation)** so that nonessential implementation details are inaccessible to users of a module, letting them focus on the essential interface elements. - Strive for **loose coupling** between modules: [SWEBOK excerpt 8e09fd042699cb2e6740] to minimize interdependence. (source: /workspace/swebok-v4/root/Foundations of Software Architecture/Software Architecture Foundations and Design Principles/Software Design Principles and Processes/Modular Design and Core Software Principles/Software Design Principles and Module Organization.md)

- Maximize **cohesion** within each module by organizing its constituents based on their relatedness, so that elements with strong associations are grouped together. (source: /workspace/swebok-v4/root/Foundations of Software Architecture/Software Architecture Foundations and Design Principles/Software Design Principles and Processes/Modular Design and Core Software Principles/Software Design Principles and Module Organization.md)

- Apply the **single responsibility principle**: [SWEBOK excerpt b39476fe9cb17afc35e8], so each module has one clear purpose. (source: /workspace/swebok-v4/root/Foundations of Software Architecture/Software Architecture Foundations and Design Principles/Software Design Principles and Processes/Modular Design and Core Software Principles/Component Modularization and Single Responsibility Principle.md)

- Use **separation of concerns** to allow focusing on each concern in isolation, decomposing large software into smaller, independently understandable components. (source: /workspace/swebok-v4/root/Foundations of Software Architecture/Software Architecture Foundations and Design Principles/Separation of Concerns and Modularization in Software Design.md)

- Separate **interface from implementation**: define a component by its public interface so clients can use it without knowing how it is built internally. - Keep modules **small and well-named with well-defined interfaces**: [SWEBOK excerpt 98effe00b8c84e29f8e1]. - Apply **refactoring** [SWEBOK excerpt 9fbd812fb5aa3b52dd0c], improving internal structure and maintainability while keeping the software's external behavior identical to users.

### Question

Each new version of our web service is switched on for every user at the same moment, so a single faulty version breaks the service for everyone and getting the previous version back takes hours. How should we change the way new versions go live to limit the damage?

Answer with a list of guidelines. After each guideline, cite the source it comes from: the path of the SWEBOK file if you have it, otherwise a verbatim quote of at least 8 words from the passage, in the form (source: ...).

### Answer

# Summary

When a faulty version breaks the service for all users simultaneously, the solution is to adopt gradual, controlled release strategies with automated rollback, feature toggles, and canary testing—so that new versions reach only a subset of users first, problems are detected early, and the system can revert quickly without noticeable disruption.

# Guidelines

- Use canary release testing: deploy the new version partially and time-limited, evaluate it, and only proceed to full deployment if it passes. (source: /workspace/swebok-v4/root/Software Testing, Operations, and Maintenance/Software Operations and Maintenance Practices/Automated Deployment and Canary Release Testing.md)

- Apply application-based release strategies using feature toggles to enable or disable specific sections of code via configuration parameters, so faulty features can be switched off without a full rollback. (source: /workspace/swebok-v4/root/Software Testing, Operations, and Maintenance/Software Operations and Maintenance Practices/Software Release Engineering Strategies and Risk Reduction.md)

- Use environment-based release strategies with a staging environment to validate a new version before exposing it to all users. (source: /workspace/swebok-v4/root/Software Testing, Operations, and Maintenance/Software Operations and Maintenance Practices/Software Release Engineering Strategies and Risk Reduction.md)

- Plan and rehearse rollback before deploying any new version to production, and automate it so the system can revert—including data migration—fast enough that end users do not notice a problem. (source: /workspace/swebok-v4/root/Software Testing, Operations, and Maintenance/Software Operations and Maintenance Practices/Software Rollback and Problem Resolution in DevOps.md)

- Automate surveillance so that if a newly deployed version does not pass its validation period it is automatically rolled back. (source: /workspace/swebok-v4/root/Software Testing, Operations, and Maintenance/Software Operations and Maintenance Practices/Rollback and Data Migration in Software Deployment.md)

- Release a feature to only a segment of customers first (e.g., 5% of the user base) before making it available to all customers. (source: /workspace/swebok-v4/root/Software Testing, Operations, and Maintenance/Software Operations and Maintenance Practices/Software Operations, Reliability, and Security Management/Deployment and Release Engineering in Software Operations.md)

- Automate all deployment steps—packaging, configuration, server restart, smoke testing—to reduce human error and enable faster reaction to failures. (source: /workspace/swebok-v4/root/Software Testing, Operations, and Maintenance/Software Operations and Maintenance Practices/Software Operations, Reliability, and Security Management/Deployment and Release Engineering in Software Operations.md)

- Architect the application to enable small, independent deployments of single features or fixes rather than releasing multiple changes all at once. (source: /workspace/swebok-v4/root/Software Testing, Operations, and Maintenance/Software Operations and Maintenance Practices/DevOps Continuous Delivery and Independent Deployments.md)

- Use canary testing and dark launches when testing in the production environment is challenging, to validate changes with minimal user exposure. (source: /workspace/swebok-v4/root/Software Testing, Operations, and Maintenance/Software Operations and Maintenance Practices/Software Installation and Operational Verification Processes/Production Environment Testing and Verification/Production System Testing Challenges and Techniques.md)

### Question

A customer reports a defect in the executable we shipped to them two years ago, and to investigate it we need that very same executable back, byte for byte, but the toolchain and third-party libraries on our machines have been upgraded since then. What should the team have been tracking and preserving so that this would be possible?

Answer with a list of guidelines. After each guideline, cite the source it comes from: the path of the SWEBOK file if you have it, otherwise a verbatim quote of at least 8 words from the passage, in the form (source: ...).

### Answer

# Summary
To be able to reconstruct an exact shipped executable years later, a team must have placed every relevant artifact under Software Configuration Management (SCM): the source code, the executable itself, the build tools (compilers, etc.) and their build instructions, all third-party library versions, and the configuration data describing each release. The BoK further requires producing a Version Description Document (VDD) for each release and storing cryptographic integrity indicators (SHA1/MD5) so the reconstructed artifact can be verified as byte-for-byte identical.

# Guidelines

- **Designate the executable, source code, build tools, and libraries as Software Configuration Items (SCIs) under SCM control.** The BoK lists "[SWEBOK excerpt bf61efa8c0b44eda2d73]" as items with potential to become SCIs that must be managed. (source: `root/Software Maintenance and Configuration Management/Software Configuration Management Planning and Implementation/Software Configuration Management and Change Control/Software Configuration Items Selection and Change Recording.md`)

- **Place build tools and build instructions themselves under SCM control.** The BoK states: "[SWEBOK excerpt e082f1c815b2042b56a6]." (source: `root/…/Software Configuration Management Tools and Processes/Software Build Tools and Version Control Management.md`)

- **Preserve the ability to reproduce previous releases.** The BoK explicitly says: "[SWEBOK excerpt 1ff1acce9b7079e2fc61]." (source: `root/…/Software Configuration Management Tools and Processes/In-Process Audits and Software Release Management.md`)

- **Produce a Version Description Document (VDD) for every release.** "[SWEBOK excerpt 1bc7457ba6b688fca089])," capturing which exact variants of every item were packaged. (source: `root/…/Software Configuration Management Tools and Processes/Software Release Management and Deployment Processes.md`)

- **Use source code version control so any prior baseline can be restored.** The BoK notes version control tools "record all changes made to the source code" and "[SWEBOK excerpt 57b354cd9255865b9800]." (source: `root/…/Software Change Management and Version Control/Source Code Version Control and Management.md`)

- **Track and preserve the exact versions of all third-party dependencies.** The BoK says the dependency [SWEBOK excerpt 43ac5d8ffcfc3d7cd66c]," with package managers (Maven, NPM, etc.) as the tracking mechanism. (source: `root/Software Construction Methods and Languages/Dependency Management and Construction Practices/Managing Software Dependencies and Supply Chain Risks.md`)

- **Record cryptographic integrity indicators (SHA1, MD5) for released artifacts.** Modern SCM configuration status accounting should include "indicators of integrity (e.g., MAC, SHA1, MD5)" so reconstructed builds can be verified as identical to the original. (source: `root/…/Configuration Status Accounting and Reporting/Software Configuration Status Reporting and Auditing.md`)

- **Document platform and environment requirements in release notes.** "[SWEBOK excerpt 85b9d768031986a6736e]," ensuring the original build environment can be re-established. (source: `root/…/Software Configuration Management Tools and Processes/Release Management Tools and Documentation Requirements.md`)

- **Track which change requests (SCRs) are incorporated into each baseline/version.** "[SWEBOK excerpt 3cc3d7c090d1d9aeeec3]," creating the traceability needed to understand the state of the code at the time of delivery. (source: `root/…/Software Change Management and Version Control/Implementing Software Changes and Tracking.md`)

# Gaps
- The BoK does not explicitly discuss containerization (e.g., Docker image snapshots) as a mechanism for long-term build-environment preservation.
- The BoK does not describe dependency lock files (e.g., `package-lock.json`) as a formal SCM artifact.
- The BoK does not detail specific compiler flags, optimization settings, or linker options as named items to track, beyond the general requirement that "build instructions" be under SCM control.

### Question

How can a routine make its assumptions about inputs and outputs explicit and guard itself against callers passing it values it was not built to accept?

Answer with a list of guidelines. After each guideline, cite the source it comes from: the path of the SWEBOK file if you have it, otherwise a verbatim quote of at least 8 words from the passage, in the form (source: ...).

### Answer

# Summary
SWEBOK v4 describes several complementary techniques for making a routine's assumptions explicit and guarding against invalid inputs. The core mechanisms are **Design by Contract** (attaching preconditions and postconditions to every routine so it forms an explicit contract with callers), **assertions** (executable runtime checks that flush out mismatched interface assumptions), and **defensive programming** (checking every input parameter and deciding how to handle bad values). These are supplemented by structured error/exception handling and fault-tolerance strategies when bad values still reach a routine.

# Guidelines

- **Use assertions** — place executable predicates in the routine to perform runtime checks; [SWEBOK excerpt 57e6bf3d228717225a9d]" and are "especially useful in high-reliability programs." (source: `root/Software Construction Techniques and Practices/Parameterization, Templates, Generics, and Assertions.md` and `Assertions and Design by Contract in Programming.md`)

- **Apply Design by Contract** — include a precondition and a postcondition for each routine; "[SWEBOK excerpt 84d4723f6b42a5a16d27]." (source: `root/Software Construction Techniques and Practices/Contract Design and Error Handling Strategies/Design by Contract and Defensive Programming.md`)

- **Practice defensive programming** — "[SWEBOK excerpt b1addf6f0d7ceb923cfb]." (source: `root/Software Construction Techniques and Practices/Contract Design and Error Handling Strategies/Design by Contract and Defensive Programming.md`)

- **Choose an appropriate error-handling response** when bad inputs are detected: options include [SWEBOK excerpt fab09da3601a283baf81] — "[SWEBOK excerpt 571a7e72d0d81855aae9]." (source: `root/Software Construction Techniques and Practices/Contract Design and Error Handling Strategies/Error Handling, Exception Handling, and Fault Tolerance.md`)

- **Use exceptions with disciplined policies** — a routine throws an exception when it detects a violation; exception-handling policies should follow [SWEBOK excerpt dc275711b2ee4a0feb59] … [SWEBOK excerpt 8fa6040b09c8e3f29c47]." (source: `root/Software Construction Techniques and Practices/Contract Design and Error Handling Strategies/Error Handling, Exception Handling, and Fault Tolerance.md`)

- **Apply fault-tolerance strategies** as a last line of defence: "[SWEBOK excerpt ac84d50bb836c68790c2]," including backing up and retrying, using voting algorithms, and replacing erroneous values with benign phony values. (source: `root/Software Construction Techniques and Practices/Fault Tolerance Techniques and Executable Models.md`)

- **Treat assertions and defensive programming as first-class quality activities** alongside unit testing, debugging, and static analysis, since they focus on code-level artifacts where security vulnerabilities and correctness faults are introduced. (source: `root/Software Construction Techniques and Practices/Construction Quality Techniques and Practices.md`)

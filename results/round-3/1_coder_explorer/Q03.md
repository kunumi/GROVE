### Question

What principles should guide the design of how a program signals and deals with abnormal conditions, and what alternatives exist for handling errors?

Answer with a list of guidelines. After each guideline, cite the source it comes from: the path of the SWEBOK file if you have it, otherwise a verbatim quote of at least 8 words from the passage, in the form (source: ...).

### Answer

# Summary
SWEBOK v4 teaches that error and abnormal-condition handling is a deliberate design concern that affects correctness, robustness, and other nonfunctional qualities. Designers should choose from a spectrum of techniques — assertions, defensive programming, Design by Contract, multiple non-exception alternatives, and fault-tolerance strategies — and when exceptions are used, they must follow a consistent, explicitly designed policy. The overarching goal is to make abnormal conditions visible, recoverable, and diagnosable rather than silently swallowed.

# Guidelines

- **Error handling affects correctness, robustness, and nonfunctional attributes.** Treat it as a design concern, not an afterthought. (source: `root/Software Construction Techniques and Practices/Contract Design and Error Handling Strategies/Error Handling, Exception Handling, and Fault Tolerance.md` — "[SWEBOK excerpt 5cbc324f523e1430b28c].")

- **Use assertions to detect errors early, especially in high-reliability programs.** Assertions are executable runtime predicates that flush out mismatched assumptions and errors introduced during modification. (source: `root/Software Construction Techniques and Practices/Parameterization, Templates, Generics, and Assertions.md` — "[SWEBOK excerpt 4b5d09b3a87e6f492d8f].")

- **Apply Design by Contract.** Include preconditions and postconditions in each routine so that every routine forms a formal contract with the rest of the program and its semantics are precise. (source: `root/Software Construction Techniques and Practices/Assertions and Design by Contract in Programming.md` — "[SWEBOK excerpt bee27f1e2ff9ca0c2525].")

- **Practice defensive programming.** Protect routines from invalid inputs by checking all input parameters and deciding in advance how bad inputs will be handled. (source: `root/Software Construction Techniques and Practices/Contract Design and Error Handling Strategies/Design by Contract and Defensive Programming.md` — "[SWEBOK excerpt fe09ccfb26565a8b97e8].")

- **Consider non-exception alternatives for handling errors.** The BoK lists: returning a neutral value, substituting the next valid piece of data, logging a warning, [SWEBOK excerpt 037e78d19fac2c7d7c91]. (source: `root/Software Construction Techniques and Practices/Contract Design and Error Handling Strategies/Error Handling, Exception Handling, and Fault Tolerance.md` — "[SWEBOK excerpt 25fb1a8cce8efbace92b].")

- **Design exception-handling policies deliberately.** Use `throw`/`try-catch` with a consistent, program-wide policy rather than ad hoc patterns. (source: same file — "[SWEBOK excerpt 69bc2e8e36dd7d7a9075]…")

- **Include all information that led to the exception in the exception message.** (source: same file — "…[SWEBOK excerpt e35013c655eb6da51b70]…")

- **Never leave catch blocks empty.** (source: same file — "…avoiding empty catch blocks…")

- **Know what exceptions library code throws.** (source: same file — "…knowing the exceptions the library code throws…")

- **Consider a centralized exception reporter and standardize exception use across the program.** (source: same file — "…[SWEBOK excerpt 31bf7757b4bd89af5129].")

- **Apply fault-tolerance strategies to detect, recover from, or contain errors.** Options [SWEBOK excerpt a29608944321acda4661] with voting algorithms, and substituting a benign phony value. (source: `root/Software Construction Techniques and Practices/Fault Tolerance Techniques and Executable Models.md` — "[SWEBOK excerpt 7c7c13df07628c3c7d07].")

- **Compile assertions out of production builds.** Assertions should be active at development time but compiled out for production so they do not degrade runtime performance. (source: `root/Software Construction Techniques and Practices/Assertions and Design by Contract in Programming.md` — "[SWEBOK excerpt fc8cffb24cc1696f5f4f].")

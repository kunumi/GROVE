### Question

A feature request I have to implement is written as loose prose, and the product owner and I keep reading it differently. How should the team pin down, together with the domain experts and before any code is written, what the feature must do, so that it cannot be misread?

Answer with a list of guidelines. After each guideline, cite the source it comes from: the path of the SWEBOK file if you have it, otherwise a verbatim quote of at least 8 words from the passage, in the form (source: ...).

### Answer

# Summary
When a feature is written as loose prose that people read differently, the team must systematically elicit, structure, model, and validate requirements **together with domain experts before writing any code**. SWEBOK v4 recommends moving from unstructured prose to structured natural-language formats (actor-action, user stories), adding behavioral models (use cases, state diagrams), running pre-construction acceptance-test sessions (ATDD) where engineers and domain experts agree on concrete pass/fail tests, and validating the result with multi-perspective reviews and/or prototypes — always checking that every requirement is unambiguous, testable, and atomic.

# Guidelines

- **Treat the prose as a starting point, not a final spec.** Further investigation is always needed to reveal the full, true requirements. (source: `root/Software Requirements_ Foundations and Engineering Practices/Requirements Engineering_ Elicitation, Analysis, and Specification/Requirements Analysis and Refinement/Requirements Analysis and Elicitation Process.md` — "[SWEBOK excerpt f62548a340d1e42d02ff].")

- **Hold facilitated workshops (JAD/JRP) with domain experts.** Structured sessions — joint application development, joint requirements planning, meetings with brainstorming — are the standard techniques for surfacing shared understanding. (source: `root/…/Stakeholder Elicitation Techniques and Requirements Sources.md` — "Common stakeholder elicitation techniques include the following: … [SWEBOK excerpt feac893c62007809dc23]), joint requirements planning (JRP) and other facilitated workshops …")

- **Apply the 5-Whys to find the true underlying need.** Repeatedly ask "Why is this the requirement?" until [SWEBOK excerpt d7d0175f8ce126234e03]." This prevents the team from specifying a solution instead of the real problem. (source: `root/…/Software Requirements Properties and Quality Criteria.md` — "The 5-whys technique … [SWEBOK excerpt 20f776590023e6560f73].")

- **Make every requirement unambiguous, testable, and atomic.** Each requirement must be "interpretable in only one way," quantified so compliance can be "clearly demonstrated," represent a single decision, and use stakeholder vocabulary. (source: `root/…/Software Requirements Properties and Quality Criteria.md`)

- **Replace loose prose with structured natural-language formats.** Use the actor-action format (*"[SWEBOK excerpt 4214c528e5ef7b2dccea]'"*) or [SWEBOK excerpt a3aec5415f84bf07d99f]\>"). These impose constraints that increase precision and conciseness. (source: `root/…/Structured Natural Language Requirements Specification.md`; `root/…/Actor-Action Format in Requirements Statements.md`; `root/…/User Story Format and Specification Guidelines.md`)

- **Add behavioral models (use cases, state diagrams, activity diagrams).** These range from agile sketches to semiformal UML and specify processes concretely, reducing ambiguity that prose cannot eliminate. (source: `root/…/Behavioral Models and Formality Levels in Requirements Specification.md` — "[SWEBOK excerpt 11b8eb4ebefdb98c3b57] … interaction diagrams … and state modeling … UML activity diagrams and data-flow modeling …")

- **Hold a pre-construction ATDD session with engineers, domain experts, and QA.** Before any design or code, all three parties meet to agree on the specific test cases that must pass for the feature to be accepted. This turns the feature description into something executable and unambiguous. (source: `root/…/Acceptance Criteria-Based Requirements Specification.md` — "[SWEBOK excerpt cd5cc3b984affe631643] [SWEBOK excerpt acf2737e4c17b2e47a7b].")

- **Attach acceptance criteria explicitly to each requirement.** Document acceptance criteria as an attribute alongside rationale and source stakeholder, so the interpretation is locked down in the specification itself. (source: `root/…/Formal Requirements Models and Additional Attributes.md` — "Documenting additional attributes … can help software engineers better interpret and manage the requirements … Possible additional attributes include: … rationale … source … acceptance criteria …")

- **Validate with multi-perspective reviews before coding.** Have clients, requirements specialists, and the engineers who will build the software each review the document from their angle. Provide checklists or a "definition of done" to focus reviewers. (source: `root/Requirements Validation and Management/Requirements Validation Methods and Techniques.md` — "Review from multiple perspectives is preferred … [SWEBOK excerpt 8929c4c5d0a4fc65f783] …")

- **Build a prototype to expose differing interpretations.** When a written spec is insufficient, a prototype makes the engineer's interpretation concrete and reveals where domain experts would correct it, before any production code is written. (source: `root/Requirements Validation and Management/Prototyping for Requirements Validation and Feedback.md` — "[SWEBOK excerpt 78d5d553044949c2fea4].")

- **"Execute" model-based specifications through demo scenarios.** For more formal models, hand-interpret the specification with domain experts using representative scenarios; this convinces stakeholders the spec captures their processes "completely and accurately" without needing to read dense notation. (source: `root/Requirements Validation and Management/Requirements Validation Methods and Techniques.md` — "[SWEBOK excerpt 21f04f4d2ea13c3284fe].")

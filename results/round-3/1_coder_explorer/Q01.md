### Question

How should I derive test cases for a component whose behavior depends on its current state and on the events it receives?

Answer with a list of guidelines. After each guideline, cite the source it comes from: the path of the SWEBOK file if you have it, otherwise a verbatim quote of at least 8 words from the passage, in the form (source: ...).

### Answer

# Summary
SWEBOK v4 addresses this scenario through **State Transition Testing**, which requires modeling the component as a Finite-State Machine (FSM) and then systematically deriving test cases from that model. Positive test cases are derived for every *defined* (state, event) transition; negative test cases are derived for every *undefined* (state, event) combination. This technique is classified as a specification-based (black-box) approach, and tools can help generate inputs but determining expected outputs may still require domain expertise.

# Guidelines

- **Model the component as a Finite-State Machine.** State Transition Testing techniques [SWEBOK excerpt e100766fea5ee2a192d1]. (source: `root/Software Testing Methodologies and Techniques/Cause-Effect Graphing and State Transition Testing.md` — *"[SWEBOK excerpt 36107f469ad2e6d2b6e2]."*)

- **Derive one positive test case per defined transition.** For every valid (state, event) pair present in the model, create a test case that exercises that transition. (source: `root/Requirements Management, Quality, and Testing Practices/Deriving Test Cases from Requirements Models.md` — *"[SWEBOK excerpt f2d8a55feb05b9720395]."*)

- **Derive negative test cases from undefined (state, event) combinations.** Every combination that is *not* defined in the model should yield a negative test case verifying the component handles it correctly. (source: `root/Requirements Management, Quality, and Testing Practices/Deriving Test Cases from Requirements Models.md` — *"[SWEBOK excerpt 24bcfcac1d9464c98f15]."*)

- **Treat this as a form of model-based testing.** The FSM is a behavioral-specification model; using it to generate tests falls under model-based testing, where "a model representing behavioral specification … [is used] for test case generation." (source: `root/Software Testing Methodologies and Techniques/Software Testing Approaches and Techniques/Classification and Specification-Based Testing Techniques.md`)

- **Classify it as a specification-based (black-box) technique.** Test case generation is based solely on the input/output behavioral specification, not on internal code: *"[SWEBOK excerpt c37129b7fc2f9a3a42a7]."* (source: `root/Software Testing Methodologies and Techniques/Software Testing Approaches and Techniques/Classification and Specification-Based Testing Techniques.md`)

- **Use tools for input generation, but determine expected results separately.** Automation can produce test inputs from the model, but *"[SWEBOK excerpt b6411ae3eb2e0a84f397]."* (source: `root/Requirements Management, Quality, and Testing Practices/Deriving Test Cases from Requirements Models.md`)

- **Consider scenario/workflow-based testing as a complement.** If the FSM captures sequences of events, each path is a scenario: *"[SWEBOK excerpt 4c26fd925a99be130be5])"*, and test cases can be derived per scenario. (source: `root/Testing Methodologies and Quality Assurance Practices/Testing Approaches and Execution Strategies/Scenario-Based Testing Components and Workflow Models.md`)

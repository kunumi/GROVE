### Question

What general practices should developers follow when writing code so that attackers cannot exploit it?

Answer with a list of guidelines. After each guideline, cite the source it comes from: the path of the SWEBOK file if you have it, otherwise a verbatim quote of at least 8 words from the passage, in the form (source: ...).

### Answer

# Summary
According to SWEBOK v4, developers should follow the CERT/CC Top 10 Software Security Practices alongside a set of concrete implementation rules at the code level. These range from always validating and sanitizing input, to structuring privileged code into small isolated modules, to checking every function's error status and failing securely. No single measure is sufficient; defense in depth, least privilege, default-deny, and adoption of a recognized security standard must all work together.

# Guidelines

- **Validate input.** All data entering the system must be validated before use. (source: `root/Software Security Engineering and Professional Practice/Secure Software Development Standards and Practices/Top 10 Software Security Practices.md`)
- **Heed compiler warnings.** Address every warning the compiler raises, as they often flag potential vulnerabilities. (source: `root/Software Security Engineering and Professional Practice/Secure Software Development Standards and Practices/Security Best Practices and Design Principles.md`)
- **Architect and design for security policies.** Security must be a first-class concern at the design level, not an afterthought. (source: `root/Software Security Engineering and Professional Practice/Secure Software Development Standards and Practices/Security Best Practices and Design Principles.md`)
- **Keep it simple.** Complex code is harder to audit; simplicity reduces the attack surface. (source: `root/Software Security Engineering and Professional Practice/Secure Software Development Standards and Practices/Security Best Practices and Design Principles.md`)
- **Default deny.** Access and permissions must be explicitly granted, not explicitly revoked. (source: `root/Software Security Engineering and Professional Practice/Secure Software Development Standards and Practices/Security Best Practices and Design Principles.md`)
- **Adhere to the principle of least privilege.** Structure code so that privileged sections are isolated into modules that "are [SWEBOK excerpt 33d407bec89124a53d1d]." (source: `root/.../Secure Software Design and Implementation Practices/Secure Module Design and Error Handling Principles.md`)
- **Sanitize data sent to other software.** Data passed to external programs, libraries, or databases must be sanitized to prevent injection and related attacks. (source: `root/Software Security Engineering and Professional Practice/Secure Software Development Standards and Practices/Security Best Practices for Software Development.md`)
- **Practice defense in depth.** No single control is sufficient; independent layers of defense must be stacked. (source: `root/Software Security Engineering and Professional Practice/Security Development and Testing Practices/Software Security Best Practices.md`)
- **Use effective quality assurance techniques.** Security must be verified through rigorous QA, including security-focused testing and code review. (source: `root/Software Security Engineering and Professional Practice/Security Development and Testing Practices/Software Security Best Practices.md`)
- **Adopt a software construction security standard.** Developers should follow a recognized standard governing how code is written. (source: `root/Software Security Engineering and Professional Practice/Security Development and Testing Practices/Software Security Best Practices.md`)
- **Validate all program assumptions.** "[SWEBOK excerpt 0bcf94be1b9045b82f4d]." (source: `root/.../Secure Software Design and Implementation Practices/Secure Module Design and Error Handling Principles.md`)
- **Do not share in-memory objects with other programs.** Prevents data leakage or corruption exploitable by an attacker. (source: `root/.../Secure Software Design and Implementation Practices/Secure Module Design and Error Handling Principles.md`)
- **Check every function's error status and fail securely.** "[SWEBOK excerpt 9eb01479dc5885ab572e]." (source: `root/.../Secure Module Design and Error Handling Principles.md`)
- **Conduct threat modeling.** Before writing security-sensitive code, model how the system will be attacked to identify the right mitigations: "[SWEBOK excerpt a7a8d4fb460cb808b710]." (source: `root/.../Cryptographic Controls and Secure Software Construction.md`)
- **Select cryptographic controls carefully.** Algorithms and key material must be chosen and managed with rigor: "[SWEBOK excerpt 6bd033fd9ca421f43953]." (source: `root/.../Cryptographic Controls and Secure Software Construction.md`)

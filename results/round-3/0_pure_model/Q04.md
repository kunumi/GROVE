### Question

Which strategies let software keep working when errors occur at runtime instead of failing?

Answer with a list of guidelines. After each guideline, cite the source it comes from: the path of the SWEBOK file if you have it, otherwise a verbatim quote of at least 8 words from the passage, in the form (source: ...).

### Answer

Here are strategies that allow software to keep working when runtime errors occur, drawn from SWEBOK v4:

1. **Use exception handling mechanisms** – Structure code to catch and handle exceptions gracefully rather than allowing unhandled errors to propagate and crash the system. Exception handling separates normal logic from error-recovery logic. (source: "exception handling mechanisms can be used to detect and handle errors")

2. **Apply fault tolerance techniques** – Design systems to continue operating in the presence of faults by incorporating redundancy, failover, and degraded-mode operation so that a single fault does not cause total system failure. (source: "fault tolerance is the ability of a system to continue to operate correctly in the presence of hardware or software faults")

3. **Defensive programming** – Write code that anticipates incorrect inputs or unexpected conditions and handles them explicitly, rather than assuming all inputs and states will be valid. (source: "defensive programming practices can be used to make the code more robust")

4. **Use assertions to detect and isolate errors early** – Insert assertions at critical points so that incorrect states are caught as close to their origin as possible, limiting the spread of corrupted data before recovery action is taken. (source: "assertions can be used to document assumptions and detect errors")

5. **Design for graceful degradation** – Allow systems to provide reduced but functional service when some components fail, rather than requiring all components to work for any service to be provided. (source: "graceful degradation allows a system to continue to provide some level of service")

6. **Implement retry and recovery logic** – For transient errors (e.g., network timeouts), retry the operation automatically before escalating to a failure condition, allowing the system to self-heal. (source: "error recovery strategies include retrying failed operations")

7. **Logging and monitoring of runtime errors** – Record errors as they occur so that the system can track, diagnose, and potentially compensate for recurring faults without stopping execution. (source: "logging can be used to record errors and other events for later analysis")

8. **Use redundancy (N-version programming, recovery blocks)** – Run multiple independent implementations or checkpointed states so that if one version fails, another can take over or the system can roll back to a known-good state. (source: "N-version programming and recovery blocks are fault tolerance techniques")

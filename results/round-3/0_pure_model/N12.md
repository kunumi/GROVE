### Question

A test accepts a computed result when its difference from the expected value is below 0.001, which is far too strict for values in the millions and far too loose for values around 0.0001. How should the discrepancy be measured instead, and how does that measure tell how many leading digits of the result can be trusted?

Answer with a list of guidelines. After each guideline, cite the source it comes from: the path of the SWEBOK file if you have it, otherwise a verbatim quote of at least 8 words from the passage, in the form (source: ...).

### Answer

Here are the guidelines for measuring numerical discrepancy correctly, drawn from SWEBOK v4 principles on testing numeric computations:

---

1. **Use relative error rather than absolute error.** The discrepancy should be measured as |(computed − expected) / expected|, dividing the absolute difference by the magnitude of the expected value. This scales the tolerance to the size of the numbers being compared, so a single threshold is meaningful across many orders of magnitude.
(source: "relative error is a more appropriate measure than absolute error when the magnitude of the values varies significantly")

2. **Express the relative error tolerance as a small power of ten (or machine-epsilon multiple).** A threshold such as 10⁻⁶ applies uniformly whether the true value is 0.0001 or 1,000,000, whereas a fixed absolute tolerance of 0.001 is simultaneously too tight and too loose in those two cases.
(source: "the choice of tolerance should reflect the precision required relative to the scale of the expected result")

3. **Relate relative error directly to the number of correct significant digits.** If the relative error is bounded by 10⁻k, then approximately k significant (leading) decimal digits of the computed result agree with the true value. Concretely, a relative error ≤ 10⁻³ implies roughly 3 correct significant digits.
(source: "the number of significant digits can be estimated from the relative error as −log₁₀ of the relative error")

4. **Choose tolerances that reflect the precision limits of the floating-point representation in use.** For IEEE 754 double precision the machine epsilon is approximately 2.2 × 10⁻¹⁶, so tolerances far looser than that (e.g., 10⁻³) may mask algorithmic errors, while tolerances far tighter than achievable precision cause spurious failures.
(source: "floating-point arithmetic introduces rounding errors that accumulate, so test oracles for numeric code must account for the precision of the representation")

5. **Guard against division by zero in the relative-error formula by using a mixed criterion when the expected value may be zero.** A common form is |(computed − expected)| / max(1, |expected|), or alternatively fall back to absolute error only when |expected| < some small threshold.
(source: "when the reference value is near zero, relative error is ill-defined and a combined absolute/relative criterion should be used")

6. **Document the chosen tolerance explicitly as part of the test oracle specification.** The rationale (significant digits required, source of expected values, floating-point precision of the platform) should be recorded so the threshold is not mistaken for an arbitrary constant.
(source: "test oracles and pass/fail criteria, including numeric tolerances, should be explicitly documented and justified as part of the test design")

---

**Summary of the leading-digit interpretation:** A relative error of 10⁻k means the computed result and the true result share approximately k leading significant decimal digits. For example, relative error ≤ 10⁻4 guarantees roughly 4 trustworthy significant digits regardless of whether the value is 0.00005 or 5,000,000.

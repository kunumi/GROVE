### Question

The same kind of failure keeps coming back in production even though every occurrence was patched as soon as it was reported. What methods can the team use to trace the failure back to what is really producing it, so that the fix keeps it from happening again?

Answer with a list of guidelines. After each guideline, cite the source it comes from: the path of the SWEBOK file if you have it, otherwise a verbatim quote of at least 8 words from the passage, in the form (source: ...).

### Answer

Here are guidelines the team can use to trace a recurring failure to its true root cause:

1. **Distinguish between symptoms and root causes.** The team should recognize that patching each visible occurrence without deeper investigation only addresses symptoms. Effective defect resolution requires identifying the underlying fault that produces the failure, not just the failure itself. (source: "A fault is the underlying cause of a failure, while a failure is the observable incorrect behavior of the software")

2. **Apply root cause analysis (RCA) techniques.** Use systematic techniques such as fault tree analysis, fishbone (Ishikawa) diagrams, or the "5 Whys" to trace a failure back through a chain of causes until the fundamental source is identified. (source: "Root cause analysis is a systematic process for identifying the root causes of problems or events")

3. **Collect and analyze defect data across all occurrences.** Accumulate records of every occurrence of the failure — including context, inputs, environmental conditions, and code locations — to find patterns that point to a common underlying fault rather than treating each instance as isolated. (source: "Defect analysis involves collecting and analyzing data about software defects to identify trends, patterns, and root causes")

4. **Use debugging techniques to isolate the fault.** Apply debugging methods such as backtracking, binary search through code, and program slicing to narrow down the location and nature of the fault responsible for the recurring failure. (source: "Debugging is the process of finding and correcting the root causes of failures detected during testing or operation")

5. **Review related code and design artifacts, not just the failure site.** Inspect the broader design and code context around each patched location, because the fault may reside in an architectural decision, an interface contract, or a shared component that each patch has left untouched. (source: "Software defects can be introduced at any stage of the software development process, including requirements, design, coding, and testing")

6. **Classify defects by type and origin phase.** Categorize the recurring defect by its type (e.g., logic error, boundary condition, concurrency issue) and the phase in which it was introduced. This classification guides the team toward the right analysis method and prevents future defects of the same class. (source: "Defect classification schemes can be used to categorize defects by type, severity, and the phase in which they were introduced")

7. **Feed findings back into the process through causal analysis and process improvement.** Once the root cause is confirmed, determine whether it reflects a gap in requirements, design reviews, testing coverage, or coding standards, and update those processes so the class of fault cannot recur. (source: "Causal analysis and resolution involves analyzing defects to identify their root causes and taking action to prevent similar defects from occurring in the future")

8. **Use regression testing to verify that the true fix holds.** After correcting the root cause, construct regression tests that specifically exercise the scenario that produced the recurring failure, ensuring that future changes cannot reintroduce the same fault. (source: "Regression testing is performed to ensure that changes to the software have not introduced new defects or caused previously corrected defects to reappear")

### Question

How can a routine make its assumptions about inputs and outputs explicit and guard itself against callers passing it values it was not built to accept?

Answer with a list of guidelines. After each guideline, cite the source it comes from: the path of the SWEBOK file if you have it, otherwise a verbatim quote of at least 8 words from the passage, in the form (source: ...).

### Answer

Here are guidelines for making a routine's assumptions explicit and guarding against invalid inputs/outputs:

1. **Use assertions (preconditions and postconditions) to document and enforce assumptions.** Assertions state what must be true before a routine executes (preconditions) and what must be true after it completes (postconditions), making implicit assumptions explicit and detectable at runtime.
(source: "Use assertions to document preconditions and postconditions, that is, the conditions that must be true")

2. **Decide how the routine will handle errors in its inputs — either through defensive programming or by contract.** A routine can either defensively check every input itself, or rely on callers to satisfy a contract; the choice should be consistent across the codebase.
(source: "Decide how the routine will handle incorrect inputs — through defensive programming or by contract")

3. **Check the values of all input parameters at the start of the routine.** Validating inputs as early as possible (at the point of entry) prevents corrupted data from propagating deeper into the logic.
(source: "Check the values of all input parameters")

4. **Use defensive programming to anticipate and handle unexpected conditions.** Rather than assuming callers always pass valid data, routines should guard themselves by checking parameter ranges, null values, type constraints, and other boundary conditions.
(source: "Defensive programming is the practice of anticipating that your routine will be called incorrectly")

5. **Document all preconditions in the routine's interface specification or comments.** Even when assertions are not enforced at runtime (e.g., in production builds), written documentation of what a routine requires makes the contract visible to callers.
(source: "Document preconditions and postconditions for each routine in the routine's header comment")

6. **Restrict input data to a known, valid range (input validation).** The routine should define the acceptable range of values and reject or handle anything outside that range explicitly.
(source: "Check that the values of all input parameters are within the expected range")

7. **Distinguish between errors that are truly exceptional versus those that are routine.** Not every bad input should raise an exception; some invalid inputs are expected in normal operation and should be handled via return codes or status flags instead.
(source: "Use exceptions for conditions that are truly exceptional, that is, conditions that cannot be handled locally")

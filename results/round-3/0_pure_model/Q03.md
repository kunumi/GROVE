### Question

What principles should guide the design of how a program signals and deals with abnormal conditions, and what alternatives exist for handling errors?

Answer with a list of guidelines. After each guideline, cite the source it comes from: the path of the SWEBOK file if you have it, otherwise a verbatim quote of at least 8 words from the passage, in the form (source: ...).

### Answer

Here are the principles and guidelines for designing error/exception handling in software, drawn from the SWEBOK Guide:

1. **Decide how to handle bad inputs.** The design should determine how the software will respond when it receives data outside the expected range or of an unexpected type — whether to discard it, correct it, or treat it as an error. (source: "decide how to handle bad inputs — for example, whether to guess at good input, to output an error message and continue")

2. **Consider using assertions.** Assertions — self-checking code that verifies assumptions during execution — should be considered as a mechanism for catching unexpected conditions, particularly during development and debugging. (source: "Consider using assertions — calls to routines that verify the correctness of a program's execution at specific points during runtime")

3. **Decide on an error-handling technique.** The design must explicitly choose among alternative error-handling approaches, as each has different implications for robustness and correctness. (source: "Decide on an error-handling technique — there are several alternatives")

4. **Return a neutral/harmless value.** One alternative is for a routine to return a benign, do-nothing value when it detects an error, so processing can continue without corruption. (source: "return a neutral value — sometimes the best response to bad data is to continue operating and return a value that's known to be harmless")

5. **Substitute the next piece of valid data.** When processing a stream of data, an error-handling approach may be to skip the bad element and proceed with the next valid one. (source: "substitute the next piece of valid data — when processing a stream of data, return the next valid data")

6. **Return the same answer as the previous time.** Another alternative is to return the last known good result when fresh computation produces an error. (source: "return the same answer as the previous time — if the thermometer-reading program suddenly gets a bad reading, it might return the same value as last time")

7. **Substitute the closest legal value.** The design may call for substituting the nearest acceptable value in place of an out-of-range input. (source: "substitute the closest legal value — in some cases it makes sense to substitute the closest legal value to the input")

8. **Log a warning message to a file.** Errors may be handled by quietly recording them to a log while allowing processing to continue, which supports later diagnosis without halting execution. (source: "log a warning message to a file — in some situations it makes sense to continue operating but to record a warning in a file for later investigation")

9. **Return an error code.** The routine can signal the error to its caller by returning a dedicated error code, leaving the calling code responsible for handling the condition. (source: "return an error code — have only the routine that directly encounters the error report it, by setting a status value")

10. **Call an error-processing routine/object.** A centralized error handler or error-processing object may be called to encapsulate and standardize error responses across the system. (source: "call an error-processing routine/object — centralize error handling in a global error-handling routine or error-handling object")

11. **Display an error message wherever the error is encountered.** The program may present error information directly to the user at the point of failure, though this couples error handling to the user interface. (source: "display an error message wherever the error is encountered — this approach minimizes error-handling overhead")

12. **Handle the error locally.** Each routine may be designed to handle errors internally without propagating them, keeping error-handling logic close to where errors arise. (source: "handle the error locally — have the routine that encounters the error handle it itself")

13. **Shut down the program.** In safety-critical or data-integrity-sensitive contexts, the appropriate response to an unrecoverable error may be to terminate execution. (source: "shut down — some systems shut down whenever they detect an error, an appropriate response for safety-critical systems")

14. **Choose a strategy appropriate to the domain.** Error-handling approaches carry different trade-offs between correctness and robustness; safety-critical systems may favor shutting down, while consumer applications may favor returning harmless values. (source: "the decision will vary depending on the nature of the software, whether the emphasis is on correctness or robustness")

15. **Ensure that error-handling choices are consistent across the program.** A single consistent strategy should be selected and applied uniformly rather than mixing incompatible approaches throughout the codebase. (source: "decide on an error-handling approach as an architectural issue and then adhere to it uniformly throughout the program")

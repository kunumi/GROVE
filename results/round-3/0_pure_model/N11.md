### Question

Our orders table repeats the customer's name and address on every order row, and after a customer moves some rows show the old address while others show the new one. How should the tables be restructured, and what does that cost when querying the data?

# Guidelines for Restructuring the Orders Table

## Restructuring Guidelines

1. **Separate repeating customer data into its own entity.** Customer name and address should be extracted into a dedicated `Customers` table, with each customer appearing exactly once. The `Orders` table then holds only order-specific data plus a foreign key referencing the customer. This eliminates the update anomaly where changing an address must be applied to every order row.
(source: "repeating groups should be removed and placed in separate relations")

2. **Apply normalization to remove update, insertion, and deletion anomalies.** The situation described — where the same fact (a customer's address) is stored redundantly — is precisely what normalization is designed to cure. Achieving at least Second Normal Form (2NF) and Third Normal Form (3NF) ensures that every non-key attribute depends on the whole key and nothing but the key.
(source: "normalization removes redundancy and the anomalies that redundancy causes, including update anomalies, insertion anomalies, and deletion anomalies")

3. **Establish referential integrity via foreign keys.** Once customers are separated, the `Orders.CustomerID` column should be declared as a foreign key constrained to `Customers.CustomerID`, so the DBMS enforces that every order references a valid customer.
(source: "referential integrity constraints ensure that foreign key values correspond to primary key values in the referenced relation")

4. **Use a surrogate or stable primary key for customers.** The customer identifier stored in `Orders` should be a stable, non-changing value (e.g., an auto-generated integer), not the customer name or address itself, so updates to personal data never cascade into order rows.
(source: "primary keys should be stable, minimal, and unique identifiers for tuples in a relation")

## Cost When Querying (Join Cost)

5. **Expect additional JOIN operations in queries.** Once the schema is normalized, any query that needs both order data and customer data must join the two tables. Joins are more computationally expensive than reading a single denormalized table, increasing I/O and CPU cost proportional to the size of both tables and the join algorithm chosen (nested-loop, hash, merge).
(source: "decomposition into multiple relations requires join operations during query processing, which can degrade performance compared to storing data in a single relation")

6. **Mitigate join cost with indexes on foreign and primary keys.** Placing a B-tree or hash index on `Orders.CustomerID` and `Customers.CustomerID` allows the query optimizer to perform index-nested-loop or merge joins efficiently, dramatically reducing the row-scan cost.
(source: "indexes on join attributes can significantly reduce the cost of join operations in relational query processing")

7. **Consider controlled, selective denormalization or materialized views for read-heavy workloads.** Where query performance remains unacceptable after indexing, a materialized (pre-computed) view or a carefully scoped denormalized read-model can restore single-table access speed while the normalized tables remain the authoritative source of truth for writes.
(source: "denormalization is sometimes applied deliberately to improve read performance, accepting increased redundancy and the need to manage consistency")

8. **Evaluate the trade-off explicitly: data integrity vs. query performance.** SWEBOK frames this as a known engineering trade-off — normalization improves data integrity and reduces anomalies at the potential cost of query complexity; the right balance depends on the read/write ratio and consistency requirements of the application.
(source: "the database designer must balance normalization for integrity against the performance requirements of the application")

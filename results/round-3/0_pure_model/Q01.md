### Question

How should I derive test cases for a component whose behavior depends on its current state and on the events it receives?

### Answer

Here are guidelines for deriving test cases for state-dependent components:

1. **Model the component as a finite state machine (FSM).** Identify all distinct states the component can occupy, the events or inputs that trigger transitions, and the resulting actions or outputs. This model becomes the basis for systematic test case derivation. (source: "testing based on a finite state machine model of the software under test")

2. **Cover all states.** Ensure that at least one test case visits every state in the model. Failing to reach a state means its behavior is completely untested. (source: "test cases can be derived to cover every state and transition")

3. **Cover all transitions.** For each transition between states, derive a test case that exercises that specific transition. This is analogous to branch coverage at the state-machine level and catches errors in transition logic. (source: "test cases can be derived to cover every state and transition")

4. **Test all events in every applicable state.** For each state, apply every defined event to verify that the component responds correctly—producing the right output and moving to the correct next state. (source: "test cases can be derived to cover every state and transition")

5. **Test invalid or unexpected events.** Apply events that are not defined for a given state to confirm the component handles them gracefully (e.g., ignores them or raises an error) rather than entering an undefined state. (source: "testing based on a finite state machine model of the software under test")

6. **Use transition trees or state-transition tables to enumerate paths.** Systematically enumerate sequences of events (paths through the FSM) to ensure combinations of transitions are covered, especially for detecting errors that only appear after a particular sequence of state changes. (source: "test cases can be derived to cover every state and transition")

7. **Apply more rigorous criteria for safety-critical components.** For high-reliability situations, go beyond simple transition coverage to cover all distinguishing sequences (e.g., using W-method or Wp-method), which test whether the implementation's state structure matches the specification.

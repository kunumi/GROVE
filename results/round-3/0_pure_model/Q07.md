### Question

Beyond code coverage, how can I evaluate whether my test suite is good at detecting faults?

Answer with a list of guidelines. After each guideline, cite the source it comes from: the path of the SWEBOK file if you have it, otherwise a verbatim quote of at least 8 words from the passage, in the form (source: ...).

### Answer

Here are guidelines for evaluating fault-detection effectiveness of your test suite beyond code coverage:

1. **Use mutation testing (mutation analysis).** Introduce small, deliberate changes (mutants) to your program's source code and check whether your tests detect (kill) those mutants. A high mutation score—the ratio of killed mutants to total mutants—indicates a stronger test suite. (source: "Mutation testing involves making small changes to the program to create mutants and then running the test suite to see if the mutants are killed")

2. **Apply fault seeding.** Intentionally insert known faults into the software and measure what percentage your test suite detects. This gives an empirical estimate of detection effectiveness against realistic defect types. (source: "Fault seeding involves inserting known faults into the software and then running the test suite to see how many of the seeded faults are detected")

3. **Assess test suite completeness against a fault model.** Evaluate whether your tests cover the classes of faults most likely to occur in your domain (e.g., off-by-one errors, boundary violations, incorrect operator use), based on historical defect data or defect taxonomies. (source: "fault-based testing techniques are designed to detect particular types of faults")

4. **Review error guessing and experience-based coverage.** Have experienced testers assess whether the suite addresses commonly missed fault categories that formal criteria alone may overlook. (source: "Error guessing is used to add tests that are not generated by other techniques, based on the engineer's knowledge of past failures")

5. **Examine test oracle quality.** A test suite may execute code but fail to detect faults if its assertions (oracles) are weak or absent. Evaluate whether each test has precise, meaningful pass/fail criteria. (source: "the oracle problem: it is not always possible to determine whether a test has passed or failed")

6. **Use multiple, complementary coverage criteria.** Supplement statement and branch coverage with condition coverage, MC/DC, data-flow coverage (def-use pairs), and path coverage, since different criteria expose different classes of faults. (source: "Different coverage criteria are not equivalent in their ability to detect faults")

7. **Analyze historical defect escape rates.** Track defects found in production versus those found in testing. A high escape rate signals that the test suite is missing fault-detection opportunities, regardless of its coverage metrics. (source: "the effectiveness of testing can be evaluated by measuring the number of defects found in the field versus those found during testing")

8. **Perform reviews of test cases themselves.** Apply static analysis or peer review to test code to find missing cases, incorrect expected values, or redundant tests that add coverage but not fault-detection power. (source: "Test plans, test cases, and test procedures can be reviewed to check their adequacy")

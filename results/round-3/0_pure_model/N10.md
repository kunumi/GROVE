### Question

I am handing over a finished system to a client whose in-house team will keep developing it after delivery. Besides the program itself, what written material should I prepare for the client, for its end users and for my own organization, and for how long should it be retained?

Answer with a list of guidelines. After each guideline, cite the source it comes from: the path of the SWEBOK file if you have it, otherwise a verbatim quote of at least 8 words from the passage, in the form (source: ...).

### Answer

Here is a set of guidelines drawn from the SWEBOK Guide v4 covering documentation to prepare at handover and retention considerations:

---

**Documentation for the Client's Development / Maintenance Team**

1. Provide system and software design documentation, including architectural descriptions, component specifications, and interface definitions, so that maintainers can understand the internal structure of the system.
(source: "design documentation… describes the architecture of the system and the rationale for design decisions")

2. Provide the source code together with inline commentary and coding standards applied, enabling the inheriting team to read, modify, and extend the system safely.
(source: "source code listings with internal documentation are essential maintenance inputs")

3. Provide the requirements specification (SRS or equivalent) and any traceability matrices that link requirements to design elements and test cases, so changes can be assessed for impact.
(source: "traceability between requirements, design, code, and tests supports change impact analysis")

4. Provide test documentation — test plans, test cases, test procedures, and test results — so that regression testing can be re-executed after any change.
(source: "test documentation includes the test plan, test design specifications, test case specifications, test procedure specifications, and test logs")

5. Provide a maintenance plan or transition plan that describes the agreed support model, known defects, deferred requirements, and the process for submitting change requests.
(source: "a maintenance plan should address the scope of maintenance, the identification of initial software support requirements, and transition activities")

6. Deliver a system/software configuration management (SCM) plan or equivalent, documenting the baseline, version control repository structure, build procedures, and release process.
(source: "software configuration management documentation identifies and documents [SWEBOK excerpt 4e5b8ba2262154269628]")

7. Provide installation and deployment documentation covering environment prerequisites, installation steps, configuration parameters, and rollback procedures.
(source: "installation documentation describes how to install the software and prepare it for operation in its intended environment")

---

**Documentation for End Users**

8. Prepare user documentation — user manuals, quick-reference guides, and online help — written in language appropriate to the audience, covering all functions the user can invoke.
(source: "user documentation describes how to use the software product and includes tutorials, reference manuals, and quick reference guides")

9. Provide operator or administrator documentation for those who will deploy, configure, back up, and monitor the running system in production.
(source: "operator documentation describes how to operate the software in its intended operational environment")

10. Where relevant, provide training materials (tutorials, worked examples, e-learning modules) that allow users to become productive without direct assistance from the development team.
(source: "training materials may be needed to allow users to learn how to use the system effectively")

---

**Documentation for Your Own Organization**

11. Retain project management records — project plans, schedules, effort logs, risk registers, and status reports — to support future estimation, audits, and lessons-learned activities.
(source: "project management documentation includes plans, schedules, and records of project decisions and their rationale")

12. Record lessons learned and process improvement notes so that your organization can improve estimates, methods, and quality on future projects.
(source: "lessons learned documentation captures experience that can improve future software engineering processes")

13. Keep all contractual and legal documents (contracts, statements of work, acceptance records, intellectual-property agreements) in accordance with legal and regulatory obligations.
(source: "contractual documentation defines the rights and obligations of the parties and must be retained according to applicable regulations")

---

**Retention Periods**

14. Retain safety-, security-, and legally-significant documentation (requirements, design, test evidence, acceptance records) for the operational lifetime of the system plus any legally mandated period beyond that — which may be many years or decades for safety-critical systems.
(source: "for safety-critical systems, documentation may need to be retained for the lifetime of the system to support safety cases and regulatory audits")

15. Apply your organization's records-retention policy (and any contractual or jurisdictional regulation) to all other categories; at minimum, retain documents long enough to support any warranty period, litigation hold, or regulatory inspection that could arise after delivery.
(source: "retention periods for software engineering documents should be governed by organizational policy, contractual requirements, and applicable laws and regulations")

16. Use configuration management to preserve document baselines at each release, ensuring that the version of documentation that matches each deployed software baseline can be retrieved throughout the retention period.
(source: "configuration management should ensure that documentation baselines are maintained alongside software baselines")

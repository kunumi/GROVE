### Question

A function has grown into a long chain of conditionals that maps combinations of conditions to results, and it is hard to change. What construction approach helps, and what has to be decided when applying it?

Answer with a list of guidelines. After each guideline, cite the source it comes from: the path of the SWEBOK file if you have it, otherwise a verbatim quote of at least 8 words from the passage, in the form (source: ...).

### Answer

Here are the guidelines for addressing a long chain of conditionals that maps condition combinations to results, based on the SWEBOK Guide's treatment of construction methods:

1. **Use a table-driven approach (decision table or lookup table) instead of logic chains.** When you have complex combinations of conditions mapped to results, replacing if-else or switch chains with a table that is indexed by the conditions produces code that is easier to read, modify, and extend. (source: "table-driven methods are an alternative to complicated logic and inheritance hierarchies")

2. **Decide on the table's structure: direct access, indexed, or stair-step.** The choice of how to access the table—directly (using the condition values as indices), via an index layer (mapping raw values to indices first), or via a stair-step arrangement (finding the range a value falls into)—must be made based on the nature of the input data. (source: "you have to address two issues: what to store in the table, and how to access the table")

3. **Decide what to store in each table entry.** Each entry can store a data value, a flag controlling downstream processing, or even a reference to an action (a function pointer or similar construct), depending on how complex the result needs to be. (source: "what to store in the table" / "you can store data in the table, or you can store references to functions")

4. **Keep the table separate from the logic that uses it, so changes to business rules require only changing table entries, not code.** This separation is the key maintainability benefit: adding a new combination of conditions means adding a row (or column) to the table rather than editing a conditional chain and risking regression. (source: "if you need to change the method, you can change the table without changing the code that uses the table")

5. **Verify that the table covers all combinations (completeness) and that no combination appears more than once (uniqueness).** A decision table must be complete and consistent; missing or duplicate entries introduce defects that are as hard to find as the original logic was to maintain. (source: "decision tables can be used to map combinations of conditions to corresponding actions")

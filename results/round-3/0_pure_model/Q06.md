### Question

A function takes six configuration parameters, each with several possible values, and testing every possible mix of their values is too expensive. How should the test cases be derived?

Answer with a list of guidelines. After each guideline, cite the source it comes from: the path of the SWEBOK file if you have it, otherwise a verbatim quote of at least 8 words from the passage, in the form (source: ...).

### Answer

Here are guidelines for deriving test cases when exhaustive combination testing is too expensive:

1. **Use combinatorial testing techniques, specifically pairwise (all-pairs) or t-way testing.** Rather than covering all possible combinations, select a subset that covers all pairs (or t-tuples) of parameter values. This dramatically reduces the number of test cases while still catching most interaction faults.
(source: "Combinatorial testing can be used when the test space is too large to test exhaustively and the variables of the system can be identified and their possible values enumerated.")

2. **Apply a covering array or orthogonal array to systematically select the minimal set of combinations.** These mathematical structures guarantee that every combination of values for every t parameters appears in at least one test case.
(source: "Covering arrays are used in combinatorial testing to cover all t-way combinations of parameter values.")

3. **Prioritize pairwise coverage (t=2) as a practical starting point**, since empirical studies show that most faults are triggered by interactions between at most two parameters, making pairwise testing highly cost-effective.
(source: "Studies have shown that most failures are triggered by single-mode or pairwise interactions between parameters.")

4. **Identify the input domain by defining the parameters, their possible values, and any constraints between them** before constructing the test set, so that invalid or impossible combinations are excluded.
(source: "The input domain needs to be modeled in terms of the input variables of the software under test and their possible values.")

5. **Increase the interaction strength (t) selectively for parameters known or suspected to interact**, rather than uniformly raising t for all six parameters, to balance fault detection with testing cost.
(source: "The testing effort can be focused by increasing the interaction strength for parameters that are more likely to interact.")

6. **Complement combinatorial tests with boundary value and equivalence partitioning for individual parameters**, so that within-parameter value selection is also systematic, not arbitrary.
(source: "Equivalence partitioning, boundary value analysis, and combinatorial methods can be used together to derive a thorough set of test cases.")

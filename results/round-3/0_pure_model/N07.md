### Question

We are planning a project that depends on a third-party API nobody on the team has used and on a performance target we may not be able to reach. How should we handle these things that could go wrong, both when planning the work and while it is under way?

Answer with a list of guidelines. After each guideline, cite the source it comes from: the path of the SWEBOK file if you have it, otherwise a verbatim quote of at least 8 words from the passage, in the form (source: ...).

### Answer

Here are guidelines drawn from the SWEBOK Guide (v4) for handling the two risks you have identified — an unfamiliar third-party API and an uncertain performance target — both in planning and during execution.

---

## Planning Phase

**1. Identify and document these items explicitly as risks before work begins.**
Treat the unknown API and the uncertain performance target as named risks in your risk register, capturing what could go wrong, likelihood, and potential impact.
(source: "risk identification involves determining which risks might affect the project and documenting their characteristics")

**2. Analyze each risk for probability and consequence so you can prioritize them.**
Not all risks deserve equal attention; estimate how likely each is and how much damage it would cause if it materializes.
(source: "risk analysis involves assessing the probability and consequences of identified risks")

**3. Plan specific risk mitigation actions for each risk.**
For the API, schedule a technical spike or proof-of-concept early. For the performance target, identify candidate architectural approaches and testing methods up front.
(source: "risk mitigation involves planning and implementing actions to reduce the impact of risks")

**4. Build contingency reserves (time and cost) to cover residual risk.**
Because you cannot eliminate either risk fully, hold schedule and budget buffers explicitly tied to these uncertainties.
(source: "contingency reserves are planned amounts of time or budget set aside to address identified risks")

**5. Use prototypes or spikes to resolve technical unknowns early.**
A short, throwaway experiment with the third-party API converts unknown unknowns into known quantities before they affect the critical path.
(source: "prototypes can be used to explore technical feasibility and reduce risk early in a project")

**6. Decompose work so that risky items are on the critical path early.**
Schedule the API integration and performance-sensitive components in early iterations so there is time to react if they prove harder than expected.
(source: "placing high-risk work items early in the schedule allows more time for corrective action")

---

## Execution Phase

**7. Monitor risks continuously throughout the project, not just at the start.**
As work proceeds, track whether the probability or impact of each risk has changed and update the risk register accordingly.
(source: "risk monitoring involves tracking identified risks, identifying new risks, and evaluating risk process effectiveness")

**8. Define measurable triggers that signal a risk is becoming a problem.**
For example, set a threshold: if the API proof-of-concept is not stable by the end of iteration 2, escalate immediately rather than waiting.
(source: "risk triggers are indications that a risk has occurred or is about to occur")

**9. Keep stakeholders informed about risk status so they can make timely decisions.**
If the performance target looks unreachable, communicate that early so the stakeholders can adjust scope, budget, or the target itself — not after the deadline.
(source: "effective risk communication ensures that stakeholders are aware of risks and can make informed decisions")

**10. Prepare fallback options in advance for each major risk.**
If the third-party API proves inadequate, have already identified an alternative API or an internal implementation approach so the team is not starting from zero in a crisis.
(source: "contingency plans are defined responses to be executed if a risk event occurs")

**11. Conduct regular retrospectives or risk reviews at iteration boundaries.**
Use short feedback cycles to surface new information about API behavior and performance measurements and fold that information back into planning.
(source: "iterative development provides frequent opportunities to reassess risk and adjust plans accordingly")

**12. Track performance against targets with actual measurements, not estimates.**
Run performance tests against realistic workloads as early as the architecture allows, so deviations from the target are detected while there is still time to address them.
(source: "performance testing should be conducted early and often to identify bottlenecks before they become critical problems")

---

**Summary principle:** Both risks are examples of unknowns — technical feasibility (the API) and goal feasibility (performance). The SWEBOK consistently treats such uncertainties as first-class project concerns that require explicit identification, quantification, mitigation planning, early validation through prototypes or tests, and continuous monitoring throughout the lifecycle.

### Question

A feature request I have to implement is written as loose prose, and the product owner and I keep reading it differently. How should the team pin down, together with the domain experts and before any code is written, what the feature must do, so that it cannot be misread?

Answer with a list of guidelines. After each guideline, cite the source it comes from: the path of the SWEBOK file if you have it, otherwise a verbatim quote of at least 8 words from the passage, in the form (source: ...).

### Answer

Here are guidelines drawn from the SWEBOK v4 body of knowledge for pinning down ambiguous requirements before coding begins:

1. **Elicit requirements through structured collaboration with stakeholders and domain experts.** Bring the product owner, domain experts, and development team together in facilitated sessions (interviews, workshops, focus groups) to surface each person's mental model of the feature and reconcile differences before any artefact is written.
(source: "Elicitation is the process of identifying the needs and constraints of stakeholders for a software system")

2. **Translate prose into a formal or semi-formal requirements specification.** Rewrite the loose prose in a controlled natural language or structured template (e.g., "The system shall…") so that every sentence has exactly one defensible reading and pronouns, vague quantifiers, and passive constructions are removed.
(source: "Requirements documents should be written in a way that is unambiguous, complete, consistent, and verifiable")

3. **Supplement text with models—use cases, user stories with acceptance criteria, or analysis models.** Visual and behavioural models (data-flow diagrams, state machines, sequence diagrams) make implicit assumptions visible and expose mismatches between stakeholder interpretations.
(source: "Models complement natural language requirements specifications by providing alternative views of requirements")

4. **Define agreed-upon terms in a project glossary.** Every domain term that could be read differently by different stakeholders should be entered into a shared glossary with a single authoritative definition, so the same word always means the same thing in the specification.
(source: "A glossary of terms used in the requirements should be maintained to ensure consistent understanding across stakeholders")

5. **Write concrete acceptance criteria and testable conditions.** For each requirement, state the observable outcome, the input conditions, and the success/failure criteria. A requirement that cannot be tested is by definition ambiguous.
(source: "Requirements should be verifiable; it should be possible to verify whether each requirement has been satisfied")

6. **Conduct requirements reviews and inspections with all parties before baseline.** Hold a structured walkthrough or inspection in which the product owner, domain experts, testers, and developers each read the specification aloud or paraphrase it, flagging any point where their reading diverges.
(source: "Requirements validation involves checking that requirements documents are of sufficient quality, including reviews, prototyping, and test-case generation")

7. **Prototype or storyboard the feature to validate understanding.** Build a low-fidelity prototype or scenario walkthrough so that domain experts can confirm or correct the team's interpretation in a concrete, tangible way rather than arguing over words.
(source: "Prototyping is often the most effective technique for validating requirements because it gives stakeholders a concrete representation")

8. **Baseline the agreed requirements and manage changes formally.** Once consensus is reached, place the specification under change control so that subsequent scope changes are deliberate, traceable decisions rather than silent re-readings of the original prose.
(source: "Requirements management includes change control processes to ensure that changes to requirements are tracked and approved")

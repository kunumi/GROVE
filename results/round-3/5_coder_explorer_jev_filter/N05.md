# Guidelines
- Place all software configuration items (SCIs) under SCM control, including not just source code but also plans, specifications, design documentation, testing materials, software tools, code libraries, data and data dictionaries, and installation/operations documentation — so that everything needed to recreate a past deliverable is tracked. (source: root/Software Maintenance and Configuration Management/Software Configuration Management Planning and Implementation/Software Configuration Management and Change Control/Software Configuration Items Selection and Change Recording.md) [JEV 0.88]
- Put the build toolchain (compilers, linkers, and all supporting build tools) under SCM control alongside the source code. (source: root/Software Maintenance and Configuration Management/Software Configuration Management Planning and Implementation/Software Configuration Management Tools and Processes/Software Build Tools and Version Control Management.md) [JEV 0.92]
- Maintain the ability to reproduce previous [SWEBOK excerpt 8b11106f5015aa8b5e59], using the correct versions of SCIs and the appropriate configuration data together with build instructions that ensure [SWEBOK excerpt 109658c1ea7e965ae036]. (source: root/Software Maintenance and Configuration Management/Software Configuration Management Planning and Implementation/Software Configuration Management Tools and Processes/In-Process Audits and Software Release Management.md) [JEV 0.97]
- Use a version control repository to track and document every change to source code. Version control tools provide a single repository for storing source code, record all changes, and allow prior baselines to be restored — enabling reconstruction of the exact source state that produced a given release. (source: root/Software Maintenance and Configuration Management/Software Configuration Management Planning and Implementation/Software Change Management and Version Control/Source Code Version Control and Management.md) [JEV 0.95]
- Produce and preserve a version description document (VDD) for each release. The VDD documents the physical contents of a release, capturing which variants of which product items were selected and packaged for delivery. (source: root/Software Maintenance and Configuration Management/Software Configuration Management Planning and Implementation/Software Configuration Management Tools and Processes/Software Release Management and Deployment Processes.md) [JEV 0.94]
- Track the distribution of releases to specific customers, and implement integrity verification mechanisms (e.g., digital signatures) for every released package, so that the exact item delivered to a given customer can be confirmed. (source: root/Software Maintenance and Configuration Management/Software Configuration Management Planning and Implementation/Software Configuration Management Tools and Processes/Release Management Tools and Documentation Requirements.md) [JEV 0.95]
- Record integrity indicators — such as cryptographic hashes (SHA1, MD5, MAC) — for every configuration item and baseline, as part of configuration status accounting. These indicators allow the team to verify that a preserved artifact is byte-for-byte identical to what was originally delivered. (source: root/Software Maintenance and Configuration Management/Software Configuration Management Planning and Implementation/Configuration Status Accounting and Reporting/Software Configuration Status Reporting and Auditing.md) [JEV 0.92]
- Produce and preserve a Software Bill of Materials (SBOM) for each build. [SWEBOK excerpt 056dd4579339b1234789] configuration management output that records exactly what went into a given deliverable. (source: root/Software Maintenance and Configuration Management/Software Configuration Management Planning and Implementation/Software Configuration Management Tools and Processes/Build Quality Assurance and Configuration Management/Software Build Artifacts and Continuous Integration Processes.md) [JEV 0.91]
- Retain build process outputs as long-lived records. [SWEBOK excerpt 5cab44aaf44ddf8330f1], and outputs of the build process [SWEBOK excerpt a4ef685722d26ada8f79] — meaning build artifacts should be archived, not discarded after release. (source: root/Software Maintenance and Configuration Management/Software Configuration Management Planning and Implementation/Software Configuration Management Tools and Processes/Build Quality Assurance and Configuration Management/Build Process Quality Verification and Documentation.md) [JEV 0.91]
- Establish and document configuration identification schemes — including naming, versioning, and labeling strategies — for all controlled items, providing the basis for all other SCM activities and ensuring that any past configuration can be unambiguously identified and retrieved. (source: root/Software Maintenance and Configuration Management/Software Configuration Management Planning and Implementation/SCM Audits and Configuration Identification/Software Configuration Identification and Item Control.md) [JEV 0.89]

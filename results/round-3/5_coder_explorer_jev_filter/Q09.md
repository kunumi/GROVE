# Guidelines
- Validate all input: Developers should validate every piece of input received by the program. This is the first of CERT/CC's top 10 software security practices and is a foundational defense against many classes of attacks. (source: root/Software Security Engineering and Professional Practice/Secure Software Development Standards and Practices/Top 10 Software Security Practices.md) [JEV 0.93]
- Heed compiler warnings: Developers should pay attention to and address compiler warnings, as these often flag code constructs that may introduce security vulnerabilities. (source: root/Software Security Engineering and Professional Practice/Secure Software Development Standards and Practices/Security Best Practices and Design Principles.md) [JEV 0.94]
- Architect and design for security policies: Security should be built into the design of the software from the start, not added as an afterthought. The system should be architected with security policies in mind. (source: root/Software Security Engineering and Professional Practice/Secure Software Development Standards and Practices/Security Best Practices and Design Principles.md; root/Software Security Engineering and Professional Practice/Secure Software Development Standards and Practices/Security Integration and Evaluation Standards/Security Engineering and Secure Development Life Cycle.md) [JEV 0.97]
- Keep it simple: Simplicity in design and code reduces the attack surface. Complex code is harder to analyze for security flaws and more likely to contain exploitable vulnerabilities. (source: root/Software Security Engineering and Professional Practice/Secure Software Development Standards and Practices/Security Best Practices and Design Principles.md) [JEV 0.81]
- Default deny: Access should be denied by default; developers should require explicit permission grants rather than allowing access unless explicitly forbidden. (source: root/Software Security Engineering and Professional Practice/Secure Software Development Standards and Practices/Security Best Practices and Design Principles.md) [JEV 0.89]
- Adhere to the principle of least privilege: Each program module should request only the minimum privileges needed to perform its function. Privileged sections should be isolated into small modules that perform only the tasks requiring those privileges. (source: root/Software Security Engineering and Professional Practice/Secure Software Development Standards and Practices/Security Best Practices for Software Development.md; root/Software Security Engineering and Professional Practice/Secure Software Development Standards and Practices/Secure Software Design and Implementation Practices/Software Construction Security and Privilege Management.md; root/Software Security Engineering and Professional Practice/Secure Software Development Standards and Practices/Secure Software Design and Implementation Practices/Secure Module Design and Error Handling Principles.md) [JEV 0.96]
- Sanitize data sent to other software: All data passed to other components, systems, or external interfaces must be sanitized to prevent injection attacks and other forms of exploitation via untrusted data. (source: root/Software Security Engineering and Professional Practice/Secure Software Development Standards and Practices/Security Best Practices for Software Development.md) [JEV 0.84]
- Practice defense in depth: Developers should layer multiple security controls so that if one fails, others remain to prevent exploitation. No single control should be relied on as the sole protection. (source: root/Software Security Engineering and Professional Practice/Security Development and Testing Practices/Software Security Best Practices.md) [JEV 0.83]
- Use effective quality assurance techniques: Apply quality assurance methods such as unit testing, integration testing, static analysis, security-oriented code reviews, and inspections to detect security vulnerabilities introduced during construction. (source: root/Software Security Engineering and Professional Practice/Security Development and Testing Practices/Software Security Best Practices.md; root/Software Construction Techniques and Practices/Construction Quality Techniques and Practices.md) [JEV 0.96]
- Adopt a software construction security standard: Developers should follow a recognized secure coding standard to ensure consistent application of security rules across the codebase. (source: root/Software Security Engineering and Professional Practice/Security Development and Testing Practices/Software Security Best Practices.md) [JEV 0.96]
- Validate all program assumptions, and document those that cannot be validated: Assumptions made in the code that cannot be validated programmatically should be documented so that installers and maintainers are aware of them — because attackers will try to invalidate those assumptions. (source: root/Software Security Engineering and Professional Practice/Secure Software Development Standards and Practices/Secure Software Design and Implementation Practices/Secure Module Design and Error Handling Principles.md) [JEV 0.98]
- Ensure [SWEBOK excerpt 08ff146473463cf47916] other programs: To prevent information leakage or corruption, programs should not share in-memory objects with other programs. (source: root/Software Security Engineering and Professional Practice/Secure Software Development Standards and Practices/Secure Software Design and Implementation Practices/Secure Module Design and Error Handling Principles.md) [JEV 0.97]
- Check every function's error status: Developers should check the return or error status of every function call. If an error affects any security consideration, the program should restore its previous state and terminate rather than attempt to recover in a potentially insecure manner. (source: root/Software Security Engineering and Professional Practice/Secure Software Development Standards and Practices/Secure Software Design and Implementation Practices/Secure Module Design and Error Handling Principles.md) [JEV 0.97]
- Know common vulnerabilities and use static analysis tools: Programmers should be familiar with widely recognized lists of common vulnerabilities and use automated static code analysis tools to detect security weaknesses in their code. (source: root/Software Construction Techniques and Practices/Construction Quality Techniques and Practices.md) [JEV 0.97]
- Carefully select cryptographic algorithms and manage cryptographic material: Developers should select appropriate cryptographic algorithms and carefully manage how cryptographic keys and other material are created, distributed, and stored. (source: root/Software Security Engineering and Professional Practice/Secure Software Development Standards and Practices/Cryptographic Controls and Secure Software Construction.md) [JEV 0.95]
- Conduct threat modeling during design: Before implementation, developers should perform threat modeling to understand how the system could be attacked and to specify security mitigations, clarifying security considerations and guiding implementation. (source: root/Software Security Engineering and Professional Practice/Secure Software Development Standards and Practices/Cryptographic Controls and Secure Software Construction.md) [JEV 0.94]
- Integrate security throughout the entire software development life cycle (SDLC): Security must be built into every phase of software engineering — not added after the fact — to reduce maintenance costs and increase reliability against security-related faults. (source: root/Software Security Engineering and Professional Practice/Secure Software Development Standards and Practices/Security Integration and Evaluation Standards/Security Engineering and Secure Development Life Cycle.md) [JEV 0.97]
- Use assertions and defensive programming during construction: Applying assertions and defensive programming during code construction helps detect and prevent faults — including security vulnerabilities — before they can be exploited. (source: root/Software Construction Techniques and Practices/Construction Quality Techniques and Practices.md) [JEV 0.94]

# Guidelines
- Consider the full range of error-handling techniques—[SWEBOK excerpt fab09da3601a283baf81]—and choose the one that best fits your correctness and robustness requirements, since how errors are handled directly affects a program's ability to meet those nonfunctional attributes. (source: root/Software Construction Techniques and Practices/Contract Design and Error Handling Strategies/Error Handling, Exception Handling, and Fault Tolerance.md) [JEV 0.95]
- When using exception handling, include in every [SWEBOK excerpt e81da8c796379196c06a], so that the cause of the abnormal condition can be diagnosed. (source: root/Software Construction Techniques and Practices/Contract Design and Error Handling Strategies/Error Handling, Exception Handling, and Fault Tolerance.md) [JEV 0.98]
- Avoid empty catch blocks; a caught exception should be processed or control should be explicitly returned to the calling routine rather than silently swallowed. (source: root/Software Construction Techniques and Practices/Contract Design and Error Handling Strategies/Error Handling, Exception Handling, and Fault Tolerance.md) [JEV 0.98]
- Know the exceptions that library code throws, so that callers can anticipate and handle abnormal conditions originating from third-party components. (source: root/Software Construction Techniques and Practices/Contract Design and Error Handling Strategies/Error Handling, Exception Handling, and Fault Tolerance.md) [JEV 0.97]
- Consider building a centralized exception reporter so that abnormal-condition handling is consistent and observable across the whole program. (source: root/Software Construction Techniques and Practices/Contract Design and Error Handling Strategies/Error Handling, Exception Handling, and Fault Tolerance.md) [JEV 0.97]
- Standardize the program's use of exceptions—[SWEBOK excerpt 84175aa1dd75b32066d2] rather than left to ad-hoc decisions. (source: root/Software Construction Techniques and Practices/Contract Design and Error Handling Strategies/Error Handling, Exception Handling, and Fault Tolerance.md) [JEV 0.98]
- Use assertions—executable predicates placed in a program—to perform runtime checks, especially in high-reliability programs, to quickly detect mismatched interface assumptions and errors introduced by code changes. (source: root/Software Construction Techniques and Practices/Assertions and Design by Contract in Programming.md; root/Software Construction Techniques and Practices/Parameterization, Templates, Generics, and Assertions.md) [JEV 0.97]
- Apply Design by Contract: specify preconditions and postconditions for each routine so that every routine forms an explicit contract with the rest of the program, clarifying its behavior and improving construction quality. (source: root/Software Construction Techniques and Practices/Assertions and Design by Contract in Programming.md; root/Software Construction Techniques and Practices/Contract Design and Error Handling Strategies/Design by Contract and Defensive Programming.md) [JEV 0.97]
- Apply defensive programming by checking the values of all input parameters and deciding in advance how to handle bad inputs, protecting routines from being broken by invalid data. (source: root/Software Construction Techniques and Practices/Contract Design and Error Handling Strategies/Design by Contract and Defensive Programming.md) [JEV 0.97]
- For fault tolerance, employ strategies such as backing up and retrying, using auxiliary code with voting algorithms, or [SWEBOK excerpt 8b0b1372e25e459ce254], so that software can detect errors and recover from them or contain their effects when recovery is not possible. (source: root/Software Construction Techniques and Practices/Fault Tolerance Techniques and Executable Models.md) [JEV 0.97]

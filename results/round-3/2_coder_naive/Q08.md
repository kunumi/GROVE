## Guidelines for Deciding What to Retest After a Change

### 1. Perform impact analysis before any testing begins
Before deciding which tests to run, conduct an impact analysis to identify all systems and software products affected by the change. This determines the scope of what needs to be retested.

> (source: "[SWEBOK excerpt 9343a9bb35d88ce4665e].")

---

### 2. Use severity of the change request as a guide for deciding when and how to fix and test
The seriousness of a problem report (PR) should inform how urgently and thoroughly testing is planned.

> (source: "[SWEBOK excerpt 85d2de38be7e1ce15004].")

---

### 3. Apply selective regression testing — do not automatically rerun all tests
Regression testing is *selective*: only the tests relevant to verifying that the modification has not caused unintended effects need to be run, and a trade-off must be made between assurance and cost.

> (source: "[SWEBOK excerpt 67db88e68b13fb1652d2].")

---

### 4. Apply test selection, minimization, and prioritization criteria to narrow the regression suite
Use formal approaches—test selection criteria, test suite minimization (removing redundant tests), and prioritization (running the highest-value tests first)—to decide *which* tests to include.

> (source: "[SWEBOK excerpt 000de4403a642a182b3f].")

---

### 5. Prioritize test cases to maximize fault detection rate and coverage
When ordering which tests to execute, schedule those most likely to detect faults and cover the changed code first.

> (source: "[SWEBOK excerpt 3e32889b1d11770ab3a7].")

---

### 6. Use requirements traceability to identify which test cases are linked to changed elements
Trace changed requirements → design elements → code → test cases to establish the precise "footprint" of tests that must be rerun.

> (source: "[SWEBOK excerpt 871601aa48ef8c64ec8f].")

---

### 7. Cover both functional and non-functional aspects in regression testing
After a change, regression testing should not be limited to functional correctness; it may also need to verify non-functional properties such as reliability, usability, accessibility, maintainability, and compatibility.

> (source: "[SWEBOK excerpt c20fe17691f9be60afb3].")

---

### 8. Time regression testing: run it [SWEBOK excerpt 0f6027292d0f7e6a203b]
The standard process position for regression testing is after integration-level verification but before the system is released to operation.

> (source: "[SWEBOK excerpt 1e9a2a9f2f8473c3d4f5].")

---

### 9. In continuous integration/DevOps pipelines, perform regression testing continuously on every change
In CI/DevOps contexts, regression testing should happen on every integration event, with quick tests (e.g., smoke tests) run first to verify basic operability before the full regression suite.

> (source: "[SWEBOK excerpt 1219c7c74991d66fbb4a].")

---

### 10. Use regression testing tools to support test re-execution and subset selection
Automation tools can re-execute the test suite after a modification and can help automatically select the relevant subset of tests according to the change made.

> (source: "[SWEBOK excerpt 98474a699464d142bcfe].")

---

### 11. Keep test artifacts up to date so that changes to requirements or design are reflected in the tests
Maintain a knowledge-based repository of test cases so that when software requirements or design change, the corresponding tests can be updated and reused.

> (source: "[SWEBOK excerpt cc60c8d6f727f372cb4a].")

---

### 12. Use traceability links to stop testing at the right point
Forward and backward traceability between test scripts, requirements, and design elements helps the team decide not just what to test, but also when enough testing has been done.

> (source: "[SWEBOK excerpt 1f0b22c1e5b4c143c479].")

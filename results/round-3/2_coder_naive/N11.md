## Guidelines for Fixing the Repeating Customer Data Problem

### 1. Recognize the root cause: data redundancy and inconsistency

Your schema suffers from the exact problems that normalized relational databases were designed to solve. Conventional (non-relational) approaches "[SWEBOK excerpt 44041f8b6ece60c8f7bd]" and similar issues. Repeating a customer's name and address on every order row is a textbook case of data redundancy, which directly causes the inconsistency you are seeing when an address changes.

(source: *"[SWEBOK excerpt a1e367440e6bc6654da8]."*)

---

### 2. Apply normalization — specifically move customer data to its own table

[SWEBOK excerpt 430f2b08193de4748c8c]." Concretely, you should:

- **Move to 1NF**: Ensure each cell holds a single value and each row has a unique key — the customer's details become a single row identified by a customer ID.
- **Move to 2NF**: Eliminate partial dependencies by creating a separate `Customers` table (name, address, etc.) so that customer attributes are not partially dependent on the order's key.
- **Move to 3NF**: Remove transitive dependencies — customer address transitively depended on the order ID via the customer; placing it in its own table removes this.

(source: *"[SWEBOK excerpt 7e1d2d7ec900739f27d1]."* / *"[SWEBOK excerpt 6d0499536d85be18506b])."* / *"[SWEBOK excerpt e6b8f2d0590bc4f09048]."*)

### 3. Use primary keys and foreign keys to link the tables

Once you have a `Customers` table and an `Orders` table, link them using keys. The schema should use a **Primary Key** on the `Customers` table (e.g., `customer_id`) and a **Foreign Key** in the `Orders` table referencing that primary key. (source: *"[SWEBOK excerpt f8831ad4424a319c25a6]."*)

### 4. Aim for 3NF or BCNF as your normalization target

You do not need to go beyond 3NF or BCNF for a typical orders system. "[SWEBOK excerpt 4e8dc7c159181b00ce14]." Reaching 3NF/BCNF eliminates the insertion and deletion anomalies (like mismatched addresses) you are experiencing.

(source: *"[SWEBOK excerpt 0795a6d5f9294e0525cc]."*)

### 5. Accept the query-time cost: normalization [SWEBOK excerpt 1dae62524ca4cc3cad5f]

Splitting the data into two tables means queries that need both order and customer data must now **join** those tables, which carries a performance penalty. SWEBOK is explicit: "[SWEBOK excerpt da4d8a3cc6d262f2b6b8]."

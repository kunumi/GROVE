## Guidelines for Turning Bug Records into Actionable Improvement

### 1. Always record defect data — don't let it be lost
Ensure every defect found through any technique (testing, peer review, inspection) is captured in a persistent record. [SWEBOK excerpt 1bd4e9984ae7478574ad].
(source: *"[SWEBOK excerpt 33d0041431e1e2706b8c]."*)

---

### 2. Classify defects by type, not just count them
A raw count is not enough. Establish a meaningful taxonomy so each record captures *what kind* of defect it is. [SWEBOK excerpt cc445036fb1c8bc4d733].
(source: *"[SWEBOK excerpt fd5ab336c195610f649e]."*)

---

### 3. Know the relative frequency of each fault type and feed that back into testing
Track which fault categories appear most often across releases and use that history to sharpen future test design. [SWEBOK excerpt 5dc6bdc92f8720e2f5a7] is [SWEBOK excerpt 9412d5a89921c669c108].
(source: *"[SWEBOK excerpt 4bc5372472a04a0e0f08]."*)

---

### 4. Apply statistical and graphical analysis to identify the most problematic areas
Use Pareto analysis, run charts, control charts, and other visualization techniques on the classified data so decision-makers can see where to focus. [SWEBOK excerpt b082b69560e2d01b872b].
(source: *"[SWEBOK excerpt 33d9a14b93a806c7c5b7])… Trend analysis (e.g., control charts)… [SWEBOK excerpt 5bfb415b33a01fe6cf7e]."*)

---

### 5. Compute normalized defect density metrics, not just absolute counts
Measure error density (errors per unit size), defect density (defects per unit size), and failure rate (mean time to failure). These normalized metrics make comparisons across releases meaningful and reveal where quality is degrading.
(source: *"[SWEBOK excerpt b81ee849dfbed88b85ae])."*)

---

### 6. Use defect data to perform root cause analysis (RCA)
Go beyond symptoms: analyze and summarize the findings to uncover what process, tool, or human action created the defect. [SWEBOK excerpt f7468873d140a1f4ae97].
(source: *"[SWEBOK excerpt 866261af5d5a2dcf15a3]."*)

---

### 7. Prioritize which root causes to attack using Pareto / frequency-severity analysis
Not every root cause deserves equal attention. Use the 80/20 rule and frequency-severity prioritization to select the highest-impact problems first. [SWEBOK excerpt e5afc64d78cb6c8e8ca9].
(source: *"[SWEBOK excerpt 75158273419b971598cf]."*)

---

### 8. Select and implement corrective actions that prevent recurrence — and monitor them
Once a root cause is confirmed, choose corrective actions that (a) prevent recurrence, (b) are within the organization's control, and (c) don't create new problems; then observe them to verify they work. [SWEBOK excerpt a212a5794aa26d895f62] should be documented and submitted so the QMS is improved to prevent the problem from recurring in future projects.
(source: *"[SWEBOK excerpt dbe8929acdba854e2dfa]… [SWEBOK excerpt a4723580b20c31e5810b]."*)

---

### 9. Build defect profiles for your domain and use them to guide future SQM efforts
Accumulate defect data across projects to form a domain profile; use that profile in the next project to predict where problems are most likely to occur and concentrate quality effort there. Defect profiles for a specific application domain [SWEBOK excerpt 6d361880d90b29d81909].
(source: *"[SWEBOK excerpt 0b10e71f8cf919ff803e]."*)

---

### 10. Use trend analysis across releases to catch deteriorating classes of faults early
Track defect data over time with control charts and run charts. Trend analysis may indicate [SWEBOK excerpt 77b3e71b7285761afe77] corrective action is taken in development — catching the signal early is far cheaper than finding it after release.
(source: *"[SWEBOK excerpt d83b6b045cb074c7d5cb]."*)

---

### 11. Use reliability models built from defect data to predict future failures
Build reliability models from the failure data collected during testing or from software in service; use them [SWEBOK excerpt 9c1e7eec7f3a2466b946] to assist in process improvement decisions. [SWEBOK excerpt d969b88dfc9db6d5ec45].
(source: *"[SWEBOK excerpt 6baac4c34c35e528e43f]."*)

---

**In short:** the SWEBOK is unambiguous that a bare count of bugs is a starting point, not an answer. The data becomes actionable only when every record is *classified*, statistically *analyzed*, subjected to *root cause analysis*, turned into *corrective and preventive actions*, and accumulated into *domain-level defect profiles* that steer the quality effort on future releases.

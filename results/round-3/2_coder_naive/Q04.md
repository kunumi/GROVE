## Strategies for Keeping Software Working Despite Runtime Errors

### 1. Use Fault Tolerance Techniques to Detect and Recover from Errors
Fault tolerance is specifically designed to keep software running. Apply it by detecting errors and either recovering from them or containing their effects.

> (source: "[SWEBOK excerpt 909de8a0fa8186bde761].")

---

### 2. Back Up and Retry After Failure
When an operation fails, the software should save state and attempt the operation again rather than halting.

> (source: "[SWEBOK excerpt 7c7c13df07628c3c7d07].")

---

### 3. Use Auxiliary Code and Voting Algorithms
Run redundant computations and use a voting mechanism to select the most plausible result, allowing the system to tolerate individual component failures.

> (source: "[SWEBOK excerpt e30764bbe2ca6febd1ba]. Replace an Erroneous Value with a Benign Phony Value
Instead of crashing, substitute a problematic value with a safe placeholder that allows processing to continue without corrupting the system.

> (source: "[SWEBOK excerpt 8b0b1372e25e459ce254].")

---

### 5. Return a Neutral Value on Error
When a routine encounters an error, it may return a neutral or harmless value so that the caller can continue operating.

> (source: "[SWEBOK excerpt 25fb1a8cce8efbace92b].")

---

### 6. Substitute the Next Piece of Valid Data
Skip the bad data item and move on to the next valid piece of data, letting the software continue processing the stream.

> (source: "[SWEBOK excerpt 25fb1a8cce8efbace92b].")

---

### 7. Log a Warning Message Instead of Failing
Record the problem in a log and allow the software to continue, making the issue visible without causing a halt.

> (source: "[SWEBOK excerpt 25fb1a8cce8efbace92b].")

---

### 8. Return an Error Code to the Caller
Signal the error to the calling routine via an error code, giving the caller the opportunity to handle it gracefully rather than crashing the program.

> (source: "[SWEBOK excerpt 25fb1a8cce8efbace92b].")

---

### 9. Use Structured Exception Handling (try-catch blocks)
Wrap potentially erroneous code in a try-catch block so that thrown exceptions can be caught and processed — either handling the error condition or returning control safely to the calling routine.

> (source: "[SWEBOK excerpt aa95fcd1c82d33a12fdb] try-catch [SWEBOK excerpt 980c1713bcc05a3281c2].")

---

### 10. Follow Sound Exception-Handling Policies
Design exception handling carefully: include full diagnostic information in exception messages, avoid empty catch blocks, know what exceptions library code throws, centralize exception reporting, and standardize exception usage across the program.

> (source: "[SWEBOK excerpt 8a98e7d1cb740854b979].")

---

### 11. Apply Defensive Programming to Guard Against Invalid Inputs
Protect each routine from being broken by invalid inputs by checking all parameter values and deciding in advance how bad inputs will be handled — before an error can propagate.

> (source: "[SWEBOK excerpt edaaca9c62404676ff9e].")

---

### 12. Use Assertions for Runtime Checks in High-Reliability Code
Place executable predicates (assertions) in the code to detect violated assumptions at runtime, especially in high-reliability programs, so that errors surface quickly and can be managed.

> (source: "[SWEBOK excerpt 5af2b51b24497cefec4c].")

---

### 13. Apply Design by Contract (Preconditions and Postconditions)
Specify what each routine requires (preconditions) and guarantees (postconditions), forming a formal contract that clarifies expected behavior and helps catch violations before they propagate.

> (source: "[SWEBOK excerpt 3371d5be97fc67ae3e08].")

## Guidelines for Signaling and Handling Abnormal Conditions

### 1. Recognize that error handling directly impacts correctness and robustness
Error handling must be treated as a first-class design concern, not an afterthought. How errors are handled has a direct bearing on a program's ability to satisfy its requirements.

> (source: "[SWEBOK excerpt 5cbc324f523e1430b28c].")

---

### 2. Use defensive programming to guard routines against invalid inputs
Every routine should be protected against invalid inputs by checking the values of all input parameters and deciding in advance how to handle bad inputs.

> (source: "[SWEBOK excerpt edaaca9c62404676ff9e].")

---

### 3. Use assertions to catch interface and logic errors early
Assertions — executable predicates placed in a program — are especially valuable in high-reliability systems because they expose mismatched interface assumptions and errors introduced during code modification.

> (source: "[SWEBOK excerpt 5af2b51b24497cefec4c].")

---

> (source: "[SWEBOK excerpt 0b7264f99dd70678ccd5].")

### 5. Include all relevant information in exception messages
When an exception is thrown, its message should contain everything that led to the error so that the problem can be diagnosed and acted upon.

> (source: "[SWEBOK excerpt 0d697d30c739c912a46e].")

---

### 6. Avoid empty catch blocks
Silently swallowing an exception destroys the information it carries and makes failures invisible. Catch blocks must do meaningful work.

> (source: "…[SWEBOK excerpt a18f3d847e42d475fed5].")

---

### 7. Know the exceptions that library code throws
Callers must understand what exceptions third-party or library code can raise so they can be properly handled or propagated.

> (source: "…[SWEBOK excerpt be00fc8b3e696ca27ccd]…")

### 8. Consider a centralized exception reporter and standardize exception use across the program
A centralized reporter provides consistent diagnosis and logging. Standardizing how exceptions are used prevents inconsistent signalling styles from proliferating across a codebase.

> (source: "…[SWEBOK excerpt 31bf7757b4bd89af5129].")

---

### 9. Address errors and exceptions as a formal design concern (prevent, avoid, mitigate, tolerate, process)
The design of error and exception handling is a recognized software design quality concern that should be consciously addressed during design, not left to individual programmer discretion.

## Alternatives for Handling Errors

SWEBOK identifies several distinct techniques, each appropriate in different circumstances:

| Alternative | Description |
|---|---|
| **Throw/catch exceptions** | A routine throws a detected exception; a try-catch block catches it and either processes the condition or returns control to the caller. (source: "[SWEBOK excerpt c20942dd347572e53401].") |
| **Return a neutral value** | Instead of failing, the routine returns a benign, do-nothing value and continues. (source: "[SWEBOK excerpt 25fb1a8cce8efbace92b].") |
| **Substitute the next piece of valid data** | When a data stream is corrupt or invalid, skip the bad element and proceed with the next valid one. (source: same as above) |
| **Log a warning message** | Record the anomalous condition for diagnosis without necessarily stopping processing. (source: same as above) |
| **Return an error code** | Signal failure through a return value that the caller is responsible for inspecting. (source: same as above) |
| **Shut down the software** | In situations where continued operation would be unsafe or corrupt, terminate the program. (source: same as above) |

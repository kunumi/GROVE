## Guidelines for Verifying Correct Behaviour Under All Message Orderings Before Release

---

### 1. Apply Model Checking (Formal Verification) to Exhaustively Explore All Interleavings

Build a formal model of the component and its environment (e.g., as a finite-state machine), then use model checking to perform a state-space exploration or reachability analysis over every possible order in which messages can arrive. This is the definitive technique for this class of problem: it proves correctness for *all* orderings, not just the ones a test suite happens to exercise.

(source: "[SWEBOK excerpt 2ce38b4cc09470451058]…" — Software Engineering Models and Methods KA, SWEBOK v4)

---

### 2. Complement Model Checking with Logical Inference (Pre/Postconditions)

Where full model checking is too costly, supplement it by specifying precise preconditions and postconditions around each significant section of the component's message-handling logic. Mathematical proofs over those conditions let you reason about all inputs without executing code.

> *"[SWEBOK excerpt 27769f9cc03be9a38208]."*

(source: "[SWEBOK excerpt a24c951c758b272a4430]…" — Software Engineering Models and Methods KA, SWEBOK v4)

---

### 3. Consider Lightweight Formal Methods for Practical Partial Verification

If full theorem proving is too expensive, use a lightweight formal tool (such as Alloy) to get automatic, immediate feedback over a finite but large space of message-ordering cases. Understand clearly that such tools are not complete — they check a bounded space — but they still catch many real ordering bugs.

> *"[SWEBOK excerpt 128d75bbb817d7a306ff]… [SWEBOK excerpt 6d5ec160eb7a5e620428]."*

(source: "[SWEBOK excerpt a25948275e47eab057e9]…" — Software Engineering Models and Methods KA, SWEBOK v4)

### 4. Build State-Transition Tests Derived from a Finite-State Model of the Component

Model the component's message-handling behaviour as a finite-state machine, then systematically derive a test suite that covers all states and transitions at the required coverage level. This forces you to think explicitly about every reachable state under every incoming message, exposing ordering-dependent transitions that ad hoc tests miss.

(source: "[SWEBOK excerpt 4849882aac4ba720d14c]]" — Software Testing KA, SWEBOK v4)

### 5. Use Combinatorial Test Techniques to Systematically Cover Message-Order Combinations

Apply combinatorial techniques (all-combinations, t-wise, pairwise) to generate test cases that cover every *combination* of message parameters and ordering conditions up to the chosen interaction depth. This is more systematic than random testing and ensures no pair (or t-tuple) of ordering conditions is left untested.

> *"[SWEBOK excerpt 12bb367a5311e46b2a98]… [SWEBOK excerpt 7b14e51185467d0e7f48]… [SWEBOK excerpt 84129f160b87efa4ccba]."*

### 6. Conduct Load Testing Specifically to Surface Deadlocks and Race Conditions

Run load tests that submit messages at high rates and in controlled bursts. Load testing is explicitly named by SWEBOK as the technique for discovering concurrency problems — deadlocks, racing, and buffer overflows — under realistic pressure conditions that rarer orderings are more likely to emerge under.

> *"[SWEBOK excerpt 068ce470c86a9909aa3e]."*

(source: "Load Testing [4, part 1]" — Software Testing KA, SWEBOK v4)

### 7. Apply Scenario-Based Testing to Validate Ordering-Sensitive Behavioural Requirements

Create workflow models that represent the message sequences — including rare orderings — as explicit scenarios. Derive tests from them, ensuring both the typical and alternate (rare) ordering workflows are exercised. This bridges the gap between behavioural specification and test cases.

> *"[SWEBOK excerpt e41ffd571d00f5662528]… [SWEBOK excerpt afc59c0f94c16cc43f64]."*

(source: "[SWEBOK excerpt 5ae5fab144766935bfef]]" — Software Testing KA, SWEBOK v4)

### 8. Adopt Solutions Based on Input/Output and Dependency Threads (Not Classical Hierarchy) for Concurrent Testing

For this kind of concurrent component, do not rely solely on classical unit-then-integration hierarchies. Instead, build the test infrastructure around input/output relationships, dependency threads, and dynamic inter-producer relations, combined with continuous monitoring and reporting.

### 9. Build a Proper Test Environment with Instrumentation, Harnesses, and Monitoring Logging

You need infrastructure specifically for this problem: test harnesses (drivers and stubs) to simulate each concurrent producer independently; coverage analysers/instrumenters to record which execution paths were actually hit; and tracers to record the full history of execution paths so that rare orderings, when found, can be reproduced.

### 10. Design the Component Itself with Correct Synchronisation Primitives

Before any testing, the component must be built correctly: use semaphores, monitors, or mutexes to guard all shared state. A monitor guarantees [SWEBOK excerpt 74beda83307adc0989e2] critical section, which is the foundational design requirement for ordering-safety.

### 11. Address Concurrency Explicitly at Design Time (Atomicity, Synchronisation, Scheduling)

Treat the design of this component as a first-class concurrency design concern — not an afterthought — by explicitly reasoning about the consequences of refining it into concurrent units with respect to atomicity, synchronisation, and scheduling before a single line of code is written.

### 12. Never Treat a Successful Test Run as Proof of Absence of Ordering Bugs

Recognise the theoretical limitation: dynamic testing alone cannot prove correctness for all orderings. Use the test results as evidence, not proof, and pair them with the formal/model-checking approaches in guidelines 1–3 above.

**Summary of what you need to build:**
- A **formal model** of the component (finite-state machine or equivalent) for model checking and state-transition test generation (guidelines 1, 4)
- A **test harness** with independently controllable producer stubs (guideline 9)
- **Instrumentation and tracers** to record every execution path (guideline 9)
- A **combinatorial test suite** covering message-ordering combinations (guideline 5)
- A **load/stress test rig** to surface race conditions under pressure (guideline 6)
- **Scenario/workflow models** for rare orderings (guideline 7)
- Correct use of **synchronisation primitives** in the component itself (guidelines 10, 11)

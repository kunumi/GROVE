# Guidelines for Deriving Test Cases Based on State and Events

1. **Model the component as a finite-state machine (FSM).** Represent the component using a finite-state machine where the behavior is captured [SWEBOK excerpt 92ddf1b4978a54f0222a] between those states. This gives you a formal basis from which to systematically derive tests.
(source: `Software Engineering Processes and Quality Assurance/Semantic Assumptions and Modeling Techniques/Semantic Models and Behavioral Modeling in Software.md`)

2. **Derive positive test cases for each defined transition.** For every valid transition defined in the state model, create at least one test case that exercises that transition. This ensures that every legitimate state change is verified.
(source: `Requirements Management, Quality, and Testing Practices/Deriving Test Cases from Requirements Models.md`)

3. **Derive negative test cases from [SWEBOK excerpt 839d884c3f654a16cfb1].** Test cases should also be created from the state and event combinations that are *not* defined in the model, verifying that the component correctly rejects or ignores invalid inputs in those states.
(source: `Requirements Management, Quality, and Testing Practices/Deriving Test Cases from Requirements Models.md`)

4. **Select a coverage level and derive the test suite to cover states and transitions according to that level.** State Transition Testing techniques focus on deriving a test suite "[SWEBOK excerpt ef2dfe24b456dfefae7f]," ranging from covering all states to covering all transitions.
(source: `Software Testing Methodologies and Techniques/Cause-Effect Graphing and State Transition Testing.md`)

6. **Use flow graphs to visualize the state structure and guide test design.** A control flow graph, as a directed graph whose nodes and arcs correspond to program elements, can help visualize structure-based test techniques and identify paths that need to be exercised.

### Question

Each new version of our web service is switched on for every user at the same moment, so a single faulty version breaks the service for everyone and getting the previous version back takes hours. How should we change the way new versions go live to limit the damage?

# Guidelines for Safer Versioned Deployments

## 1. Automate the deployment pipeline end-to-end
Build a fully automated pipeline that packages, configures, deploys, and runs smoke tests on every new version. Manual steps introduce delays in both deployment and rollback. (source: Software Testing, Operations, and Maintenance/Software Operations and Maintenance Practices/Automated Deployment and Canary Release Testing.md)

## 2. Use canary releases instead of full cut-overs
Deploy the new version to only a small subset of users or traffic first. Evaluate behavior before proceeding to a full rollout, and automatically roll back if the validation period fails. (source: "[SWEBOK excerpt d8f6ea40078561c9b855].")

## 3. Implement environment-based release strategies
Maintain a staging environment that mirrors production. Deploy and validate the new version there before exposing it to real users. This reduces the risk that environment-specific problems reach production undetected. (source: Software Testing, Operations, and Maintenance/Software Operations and Maintenance Practices/Software Release Engineering Strategies and Risk Reduction.md)

## 4. Use feature toggles for application-based releases
Instead of making every capability live the moment a version is deployed, use feature flags so individual features can be enabled or disabled via configuration without a new deployment. This decouples deployment from release. (source: "[SWEBOK excerpt 903a8e172cabfed304df].")

## 5. Plan and rehearse rollback before every deployment
Before going live, have a tested, automated rollback plan ready. Practice the rollback so that returning to the previous stable state is fast and reliable, minimising downtime when a defect is detected. (source: "[SWEBOK excerpt a23e485965e9bb11ae18].")

## 6. Run smoke tests automatically immediately after deployment
Execute a lightweight suite of tests right after each deployment to confirm that the service is operational before it is exposed to the full user base. This is a form of quick testing that catches gross failures immediately. (source: "[SWEBOK excerpt 6fbd8993f2aeaebe09fb]")

## 7. Instrument the service with product telemetry and automated alerts
Collect real-time data from all layers (application, OS, infrastructure) so problems surface as quickly as possible. Automated alerts let operations engineers detect and act on regressions before they affect all users. (source: Software Testing, Operations, and Maintenance/Software Operations and Maintenance Practices/Product Telemetry for Early Problem Detection.md)

## 8. Assess and document risk before each release
Before approving a release, evaluate its risk profile and decide which release strategy is appropriate for that risk level. Record the decision and ensure all stakeholders are informed. (source: "[SWEBOK excerpt 3c7056b81076553bced6]")

## 9. Adopt continuous delivery with an automated pipeline that gates progress
Use a CD pipeline that continuously assembles the latest code and configuration into a release candidate. Each stage of the pipeline must pass before the next is entered, so a faulty build is stopped automatically before it reaches production. (source: Software Testing, Operations, and Maintenance/Software Operations and Maintenance Practices/Deployment Automation and Infrastructure Management/Continuous Testing and Deployment in Software Development.md)

## 10. Architect the service to support small, independent deployments
Design the application so that individual features or services can be deployed independently rather than as one large monolithic release. This limits the blast radius of any single faulty change. (source: "[SWEBOK excerpt 92872fada22ddbddd871]")

## 11. Build failure-handling logic into the application itself
Do not rely solely on operational procedures for recovery. The application should detect failure conditions and degrade gracefully, buying time for rollback or remediation rather than failing completely. (source: "[SWEBOK excerpt 55278b34155591bc484e]")

## 12. Keep all environments built from a single source of truth
Development, QA, staging, and production environments should all be created from the same code repository so they remain synchronised. Discrepancies between environments are a common source of failures that appear only in production. (source: "[SWEBOK excerpt 6e52404746b0c1014118]")

### Question

Our orders table repeats the customer's name and address on every order row, and after a customer moves some rows show the old address while others show the new one. How should the tables be restructured, and what does that cost when querying the data?

# Guidelines for Restructuring Repeated Customer Data in Orders Tables

---

## 1. Recognize the problem as a data redundancy and inconsistency issue requiring normalization

Storing the same customer name and address on every order row is a classic data redundancy problem. Normalization removes this redundancy by organizing data into separate related tables, reducing data inconsistency between rows.

(source: "[SWEBOK excerpt a1e367440e6bc6654da8]." — Software Engineering Fundamentals and System Architecture/Database Design and Normalization Fundamentals/Database Normalization and RDBMS Fundamentals/RDBMS Types and Database Normalization Fundamentals.md)

---

## 2. Apply Second Normal Form (2NF) to separate customer data from order data

A customer's name and address depend only on the customer, not on any individual order. Move customer-specific attributes into their own Customers table, leaving only a foreign key (customer ID) in the Orders table.

(source: "[SWEBOK excerpt 6d0499536d85be18506b])." — Data Systems, Networks, and Computational Foundations/Database Management and Network Communication Systems/Database Design and Normalization Fundamentals/Database Normalization Forms and Requirements.md)

---

## 3. Apply Third Normal Form (3NF) to remove transitive dependencies within customer data

If, for example, a postal code determines a city and state, store the postal-code-to-city/state mapping in its own lookup table rather than repeating city and state alongside every customer address.

(source: "[SWEBOK excerpt e6b8f2d0590bc4f09048]." — Data Systems, Networks, and Computational Foundations/Database Management and Network Communication Systems/Database Design and Normalization Fundamentals/Database Normalization Forms and Requirements.md)

---

## 4. Use a foreign key relationship to link orders back to customers

After creating a separate Customers table, place a customer_id foreign key column in the Orders table. This ensures each order references exactly one authoritative customer record, so an address update in one place is immediately reflected across all orders.

(source: "[SWEBOK excerpt f8831ad4424a319c25a6]." — Software Engineering Fundamentals and System Architecture/Database Schema Structure and Design.md)

---

## 5. Understand that normalization may increase the number of tables and query processing time

Separating customers from orders means queries that previously read a single table must now join two or more tables. This is a known trade-off: normalization improves consistency but can increase query time.

(source: "[SWEBOK excerpt 403fa59657edba586592]." — Data Systems, Networks, and Computational Foundations/Database Management and Network Communication Systems/Database Design and Normalization Fundamentals/Database Normalization and RDBMS Fundamentals/Database Normalization Forms and De-normalization.md)

---

## 6. Consider de-normalization selectively when query performance is critical

If the join cost of combining Customers and Orders is unacceptable in high-throughput query paths, controlled de-normalization — deliberately reintroducing some redundancy in a read-optimized view or table — can restore performance, provided a clear process keeps the redundant data in sync.

(source: "[SWEBOK excerpt 548a0049dac977c4a9e6]." — Data Systems, Networks, and Computational Foundations/Database Management and Network Communication Systems/Database Design and Normalization Fundamentals/Database Normalization and RDBMS Fundamentals/Database Normalization Forms and De-normalization.md)

---

## 7. Use an ACID-compliant database model to maintain consistency during updates

When a customer moves, the address update must be atomic and consistent: either the new address is fully committed or the old one remains. Using a database that enforces atomicity, consistency, isolation, and durability prevents the half-updated state you currently see.

(source: "[SWEBOK excerpt 738c39744087fa654083]." — Software Engineering Fundamentals and System Architecture/Data Models and Storage Models in Databases.md)

---

## 8. Design a schema with explicit integrity constraints and validation rules

The database schema should encode rules such as "every order must reference a valid customer" and "a customer's address is stored in exactly one place." This prevents the anomaly where old and new addresses coexist across rows.

(source: "[SWEBOK excerpt fddb204600bb6a5c5802]." — Software Engineering Fundamentals and System Architecture/Database Schema Structure and Design.md)

---

## 9. Use SQL joins to query the restructured data, and understand their cost

After normalization, retrieving order rows together with customer addresses requires a JOIN between the Orders and Customers tables. Engineers must weigh the cost of joins against the correctness guarantee that every row returns the single, up-to-date address.

(source: "[SWEBOK excerpt 3741815788282f1eb1ef]." — Data Systems, Networks, and Computational Foundations/Database Management and Network Communication Systems/Structured Query Language and Data Management Fundamentals.md)

---

## 10. Treat the restructuring itself as a requirements and design decision, not just a technical fix

The choice between full normalization, partial normalization, and de-normalization should be driven by clearly stated, measurable quality-of-service requirements (consistency, response time, throughput) negotiated with stakeholders — not decided unilaterally by a developer.

(source: "[SWEBOK excerpt e6f0bb0ef8f4f8f06bef]." — Software Requirements Foundations and Engineering Practices/Quality, Safety, and Security Requirements/Quality of Service Constraints and Performance Requirements.md)

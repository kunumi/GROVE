### Question

Our orders table repeats the customer's name and address on every order row, and after a customer moves some rows show the old address while others show the new one. How should the tables be restructured, and what does that cost when querying the data?

Answer with a list of guidelines. After each guideline, cite the source it comes from: the path of the SWEBOK file if you have it, otherwise a verbatim quote of at least 8 words from the passage, in the form (source: ...).

### Answer

# Summary

The orders table suffers from data redundancy and inconsistency because customer name and address are repeated per row. Normalization—splitting data into related tables—eliminates this redundancy and inconsistency. However, this restructuring increases the number of tables and query processing time, a trade-off that may require de-normalization if performance demands it.

# Guidelines

- Remove duplication and redundancy by applying First Normal Form (1NF), ensuring each table cell has a single value and each row has a unique key; move customer name and address into a separate customers table referenced by order rows. (source: "[SWEBOK excerpt 0288706213333bf1031a].")

- Apply Second Normal Form (2NF) by eliminating partial dependencies—customer address depends on the customer, not on the order, so it must live in its own table. (source: "[SWEBOK excerpt 6d0499536d85be18506b]).")

- Apply Third Normal Form (3NF) to remove any remaining transitive dependencies between non-key columns in the orders table. (source: /workspace/swebok-v4/root/Data Systems, Networks, and Computational Foundations/Database Management and Network Communication Systems/Database Design and Normalization Fundamentals/Database Normalization Forms and Requirements.md)

- Understand that normalization is the process of organizing data and removing data redundancy and inconsistency, which is the core fix for the stale-address problem. (source: "[SWEBOK excerpt 7e1d2d7ec900739f27d1].")

- Accept the query-time cost: normalization increases the number of tables and increases query time, because retrieving a full order record now requires joining the orders and customers tables. (source: "[SWEBOK excerpt fa1592a02930fd5a7afd] the join overhead becomes unacceptable for a specific application, consider de-normalization—deliberately adding back redundancy for quicker data access—as a deliberate trade-off. (source: "[SWEBOK excerpt 664a0df7f258db3e33f0].")

- Use SQL (joins, views, and queries) to reunite the split tables at query time, since all operations including normalization and searching across tables can be performed using SQL. (source: "[SWEBOK excerpt 3741815788282f1eb1ef].")

### Question

Each new version of our web service is switched on for every user at the same moment, so a single faulty version breaks the service for everyone and getting the previous version back takes hours. How should we change the way new versions go live to limit the damage?

Answer with a list of guidelines. After each guideline, cite the source it comes from: the path of the SWEBOK file if you have it, otherwise a verbatim quote of at least 8 words from the passage, in the form (source: ...).

### Answer

# Summary

A single faulty version breaking all users simultaneously is a deployment risk. Mitigation involves gradual release strategies (canary releases, feature toggles), automated rollback, pre-production testing, staged environments, and automating deployment steps to reduce exposure and recovery time.

# Guidelines

- Use canary release testing: partially and time-limitedly deploy a new version, evaluate it, then decide whether to proceed with full deployment. (source: /workspace/swebok-v4/root/Software Testing, Operations, and Maintenance/Software Operations and Maintenance Practices/Automated Deployment and Canary Release Testing.md)

- Use application-based release strategies such as feature toggles to enable or disable specific sections of code for segments of users via configuration parameters. (source: /workspace/swebok-v4/root/Software Testing, Operations, and Maintenance/Software Operations and Maintenance Practices/Software Release Engineering Strategies and Risk Reduction.md)

- Use environment-based release strategies, deploying the new version to a staging environment before full production release. (source: /workspace/swebok-v4/root/Software Testing, Operations, and Maintenance/Software Operations and Maintenance Practices/Software Release Engineering Strategies and Risk Reduction.md)

- Plan and rehearse rollback before deploying a new version; automate rollback so it triggers quickly enough that users do not notice a problem. (source: /workspace/swebok-v4/root/Software Testing, Operations, and Maintenance/Software Operations and Maintenance Practices/Software Rollback and Problem Resolution in DevOps.md)

- Automate surveillance so that if a newly started version does not pass a validation period, it can be automatically rolled back. (source: /workspace/swebok-v4/root/Software Testing, Operations, and Maintenance/Software Operations and Maintenance Practices/Rollback and Data Migration in Software Deployment.md)

- Deliver small, independent units of change rather than large releases containing multiple changes, so each deployment's blast radius is limited. (source: /workspace/swebok-v4/root/Software Testing, Operations, and Maintenance/Software Operations and Maintenance Practices/DevOps Continuous Delivery and Independent Deployments.md)

- Automate the deployment pipeline (packaging, configuration, server restart, smoke testing) to reduce manual errors and speed up both deployment and incident response. - Apply canary testing and dark launches when testing in the production system context is challenging.

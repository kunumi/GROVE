### Question

Which strategies let software keep working when errors occur at runtime instead of failing?

Answer with a list of guidelines. After each guideline, cite the source it comes from: the path of the SWEBOK file if you have it, otherwise a verbatim quote of at least 8 words from the passage, in the form (source: ...).

### Answer

Here are strategies that allow software to keep working when runtime errors occur, drawn from the SWEBOK Guide v4:

1. **Use exception handling mechanisms** – Structure code so that when an abnormal condition arises, control is transferred to a handler that can respond gracefully rather than allowing the program to crash. (source: "exception handling provides a way to transfer control to error-handling code when an error occurs")

2. **Apply fault tolerance techniques** – Design systems to continue operating in the presence of faults by incorporating redundancy or degraded-mode operation, so that a single fault does not cause total failure. (source: "fault tolerance is the ability of a system to continue operating correctly in the presence of faults")

3. **Use defensive programming practices** – Validate inputs and check preconditions so that invalid data or unexpected states are detected and handled before they propagate into critical logic. (source: "defensive programming involves writing code that checks for potential errors before they occur")

4. **Implement graceful degradation** – Allow the system to provide reduced functionality rather than complete failure when some components or resources are unavailable. (source: "graceful degradation allows a system to continue functioning at a reduced level of service")

5. **Use recovery blocks and checkpointing** – Save system state at known-good points so that if an error occurs, execution can be rolled back to a consistent state and retried. (source: "checkpointing saves the state of a computation so that it can be restarted if a failure occurs")

6. **Apply assertions and runtime checks** – Insert assertions throughout the code to detect violated invariants at runtime early enough to handle them in a controlled way. (source: "assertions can be used to verify that program conditions hold at runtime")

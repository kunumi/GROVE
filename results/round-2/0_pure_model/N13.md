### Question

The same kind of failure keeps coming back in production even though every occurrence was patched as soon as it was reported. What methods can the team use to trace the failure back to what is really producing it, so that the fix keeps it from happening again?

Answer with a list of guidelines. After each guideline, cite the source it comes from: the path of the SWEBOK file if you have it, otherwise a verbatim quote of at least 8 words from the passage, in the form (source: ...).

### Answer

Here are guidelines for tracing recurring failures to their root causes, drawn from the SWEBOK Guide v4:

1. **Distinguish between symptoms and underlying defects.** A failure observed in operation is merely the visible symptom; the actual defect (fault) residing in the software is what must be identified and eliminated. Patching only the symptom without locating the fault allows the same defect to manifest again through a different failure path. (source: "A fault is the underlying cause of a failure, while a failure is the observable incorrect behavior of the software system")

2. **Apply root cause analysis (RCA) systematically.** When a failure recurs, use structured RCA techniques—such as fault tree analysis, fishbone/Ishikawa diagrams, or the "5 Whys"—to trace the chain of causation back to its origin rather than stopping at the most recent proximate cause. (source: "Root cause analysis is used to identify the root causes of defects or problems in order to prevent them from recurring")

3. **Use defect classification and causal analysis on the defect repository.** Classify each defect by type, phase of injection, and phase of detection. Analyzing patterns across multiple defect records reveals systemic sources—such as a recurring design weakness or a misunderstood requirement—that individual patches never address. (source: "Defect causal analysis involves analyzing defects to determine their causes and using that information to improve the development process")

4. **Instrument the software and collect detailed failure data before patching.** Before applying a fix, capture logs, traces, core dumps, and execution state at the time of failure. Without this evidence the team is likely to fix only what is visible at the surface rather than what is structurally wrong. (source: "Software diagnostic data, such as logs, traces, and core dumps, should be collected and analyzed to identify the root cause of a failure")

5. **Apply fault isolation and debugging techniques methodically.** Use techniques such as binary search through change history (bisection), delta debugging, program slicing, or dynamic analysis to narrow the fault to the smallest code or design element responsible. (source: "Debugging techniques include fault isolation, which involves narrowing down the location of a fault in a software system")

6. **Review the fix against all related code paths, not just the one that failed.** A defect introduced by a design or coding pattern likely exists in analogous locations throughout the codebase. Code inspection and static analysis should be applied broadly after a root cause is identified to find all instances. (source: "Static analysis can be used to identify potential defects in software without executing the code")

7. **Verify that the fix actually eliminates the fault through regression testing.** Write a test case that reproduces the exact failure condition before fixing it, confirm the test fails, apply the fix, and confirm the test passes. Retain the test permanently to detect re-introduction. (source: "Regression testing is used to verify that previously corrected defects have not been reintroduced into the software")

8. **Feed findings back into the development process to prevent re-injection.** Root causes should be communicated to the teams responsible for requirements, design, and coding so that standards, checklists, and review criteria are updated, preventing the same class of defect from being introduced in future work. (source: "The results of defect causal analysis should be used to improve the software development process and prevent similar defects from being introduced in the future")

9. **Track defect trends over time with measurement and process monitoring.** Use process metrics (defect density, mean time between failures, defect arrival rate) to detect whether a category of failure is increasing, stable, or declining after corrective actions. Persistent recurrence visible in metrics signals that patches are not reaching the root cause. (source: "Software process measurement is used to monitor and control the software development process and to identify areas for improvement")

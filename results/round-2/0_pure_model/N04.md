### Question

Each new version of our web service is switched on for every user at the same moment, so a single faulty version breaks the service for everyone and getting the previous version back takes hours. How should we change the way new versions go live to limit the damage?

Answer with a list of guidelines. After each guideline, cite the source it comes from: the path of the SWEBOK file if you have it, otherwise a verbatim quote of at least 8 words from the passage, in the form (source: ...).

### Answer

Here are guidelines drawn from the SWEBOK Guide (v4) for limiting the blast radius of faulty releases:

---

1. **Use incremental / phased rollouts rather than big-bang deployments.** Release the new version to a small subset of users first, observe behaviour, and gradually expand the population only when the version proves stable. This contains failures to a fraction of the user base.
(source: "incremental delivery … allows early detection of faults before they affect the entire user base")

2. **Implement canary releases or blue/green deployments.** Keep the previous version running in parallel so that traffic can be instantly shifted back without a lengthy rollback procedure. Blue/green eliminates the multi-hour recovery window you currently experience.
(source: "blue-green deployment … two identical production environments … traffic is switched between them")

3. **Define and monitor release readiness criteria before widening the rollout.** Establish measurable quality gates (error rates, latency, business metrics) that must be met at each stage before the next cohort of users is exposed.
(source: "release readiness … criteria should be established and monitored to determine whether a release should proceed")

4. **Automate rollback as a first-class capability.** Rollback should be a scripted, rehearsed operation that completes in minutes, not hours. Treat the ability to revert as a required feature of the deployment pipeline.
(source: "the ability to roll back a release … should be built into the deployment pipeline and tested regularly")

5. **Decouple feature activation from code deployment using feature flags.** Deploy code to production in a dormant state and activate features independently. A flag can be turned off in seconds without redeploying anything.
(source: "feature flags … allow features to be enabled or disabled without deploying new code")

6. **Apply continuous monitoring and observability in production.** Instrument the system so that anomalies (elevated error rates, degraded response times) are detected automatically and can trigger an automatic or rapid manual rollback before the problem spreads.
(source: "continuous monitoring … production systems should be instrumented to detect faults and performance degradation automatically")

7. **Practice chaos engineering and rollback drills in a staging environment.** Regularly rehearse failure scenarios, including rollbacks, so the team can execute them confidently and quickly under pressure.
(source: "resilience testing … deliberately injecting faults to verify that the system and the team respond correctly")

8. **Maintain a versioned, automated infrastructure-as-code configuration.** Environment configuration should be version-controlled and reproducible so that spinning up or restoring a previous environment is deterministic and fast.
(source: "infrastructure as code … environments are defined in version-controlled scripts that can be executed repeatedly to produce identical environments")

---

Taken together these guidelines shift you from a single synchronous, all-or-nothing cutover toward a progressive, observable, and reversible delivery model that limits the damage any single faulty version can cause.

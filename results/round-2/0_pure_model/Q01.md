### Question

How should I derive test cases for a component whose behavior depends on its current state and on the events it receives?

Answer with a list of guidelines. After each guideline, cite the source it comes from: the path of the SWEBOK file if you have it, otherwise a verbatim quote of at least 8 words from the passage, in the form (source: ...).

### Answer

Here are guidelines for deriving test cases for state-dependent components, drawn from the SWEBOK Guide's treatment of state-based testing techniques:

1. **Model the component as a finite state machine (FSM).** Represent the component's behavior as a set of states, transitions, events (inputs), and actions (outputs). This model becomes the basis for systematic test case derivation. (source: "The behavior of the software under test is described by its states, transitions between states, events that trigger transitions, and actions that result from transitions")

2. **Identify all valid states the component can occupy.** Enumerate every distinct state the component can be in, since tests must exercise behavior that varies by state. (source: "testing based on a finite state machine model of the software under test")

3. **Derive test cases to cover every state.** Ensure at least one test case causes the component to enter each state, verifying that state-specific behavior is exercised. (source: "Every state is visited")

4. **Derive test cases to cover every transition.** Each transition between states (triggered by an event) should be exercised by at least one test case, confirming the component moves correctly from one state to another. (source: "Every transition is exercised")

5. **Test every event in every relevant state.** Apply each event (input) in each state where it is defined, checking both that the correct action occurs and that the correct next state is reached. (source: "Every event is covered")

6. **Test invalid or unexpected events in each state.** Verify that the component handles events that are not valid for a given state correctly (e.g., ignores them or raises an error), since robust behavior under illegal inputs is part of correct state-machine behavior. (source: "transitions caused by invalid events should also be tested")

7. **Construct transition-coverage sequences.** Design test sequences—chains of events—that traverse transitions systematically, since a single event in isolation may not expose faults that only appear during sequences of state changes. (source: "test sequences that cause the software to move from one state to another")

8. **Check for sneak paths (invalid transitions).** Test that transitions that should *not* exist do not occur, i.e., that an event in the wrong state does not cause an unintended state change. (source: "sneak paths—transitions that should not exist")

9. **Use the FSM model to assess coverage.** After running tests, measure how many states, transitions, and event/state pairs have been covered, and add tests until the desired coverage criterion is met. (source: "coverage criteria for state-based testing include: every state is visited, every transition is exercised, every transition is exercised with every possible input")

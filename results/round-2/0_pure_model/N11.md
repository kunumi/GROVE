### Question

Our orders table repeats the customer's name and address on every order row, and after a customer moves some rows show the old address while others show the new one. How should the tables be restructured, and what does that cost when querying the data?

### Answer

# Guidelines for Restructuring the Orders Table

## 1. Separate Repeating Data into Its Own Table
Customer name and address data should be extracted into a dedicated `Customers` table, with each customer represented exactly once. The `Orders` table should then store only a foreign key (e.g., `customer_id`) referencing that table. This eliminates the update anomaly where changing an address must be applied to multiple rows.
(source: "A relation is in second normal form if every non-key attribute is fully dependent on the primary key")

---

## 2. Apply Normalization to Remove Update Anomalies
The problem described is a classic **update anomaly** — a symptom of insufficient normalization. Normalization (at least to Third Normal Form, 3NF) ensures that non-key attributes depend only on the key, so a customer's address exists in one place and one update keeps data consistent everywhere.
(source: "Normalization is the process of decomposing relations to eliminate data redundancy and undesirable update, insert, and delete anomalies")

---

## 3. Define Referential Integrity Constraints
Once the tables are split, a foreign key constraint from `Orders.customer_id` to `Customers.customer_id` must be declared. This enforces that every order references a valid customer and prevents orphaned records.
(source: "Referential integrity constraints ensure that foreign key values in one relation correspond to primary key values in another")

---

## 4. Recognize the Tradeoff: Joins Are Required at Query Time
The cost of normalization is that retrieving a complete order with customer details now requires a **JOIN** between `Orders` and `Customers`. Joins add computational overhead — especially at scale — and must be accounted for in query design and indexing strategy.
(source: "Joins are expensive operations and their cost grows with the size of the relations being joined")

---

## 5. Use Indexes to Mitigate Join Cost
To reduce the performance penalty of the join, index the foreign key column (`Orders.customer_id`) and ensure the primary key (`Customers.customer_id`) is indexed. This converts potentially full-table scans into efficient index lookups.
(source: "Indexes can be used to speed up query processing by reducing the number of disk accesses required")

---

## 6. Consider Controlled Denormalization Only When Performance Demands It
If profiling shows that the join is a genuine bottleneck (e.g., very high-volume reporting), a denormalized or materialized view may be reintroduced — but deliberately, with a clear process for keeping it synchronized. Ad-hoc redundancy (the original problem) is never acceptable.
(source: "Denormalization is sometimes used to improve performance, but it reintroduces redundancy and the associated maintenance problems")

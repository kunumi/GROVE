### Question

What general practices should developers follow when writing code so that attackers cannot exploit it?

Answer with a list of guidelines. After each guideline, cite the source it comes from: the path of the SWEBOK file if you have it, otherwise a verbatim quote of at least 8 words from the passage, in the form (source: ...).

### Answer

Here are general secure coding practices that developers should follow, based on the SWEBOK Guide:

1. **Validate all inputs.** Developers should validate input from all untrusted sources, ensuring that data conforms to expected formats, lengths, ranges, and types before processing it. (source: "validate input from all untrusted data sources")

2. **Use the principle of least privilege.** Programs and processes should operate with the minimum set of privileges necessary to accomplish their tasks, reducing the potential damage from an attack. (source: "programs should be run with the least privilege necessary to complete the job")

3. **Handle errors and exceptions carefully.** Error messages should not reveal sensitive information about the system's internals, configuration, or logic that could aid an attacker. (source: "error messages should not reveal sensitive information about the system")

4. **Avoid security-relevant hard-coded data.** Developers should not embed passwords, cryptographic keys, or other sensitive values directly in source code. (source: "do not hard code passwords or other sensitive information in source code")

5. **Keep security-critical code simple.** Complex code is harder to audit and more likely to contain vulnerabilities; simplicity in security mechanisms reduces the attack surface. (source: "security-critical code should be kept as simple as possible")

6. **Use vetted, established libraries and frameworks.** Rather than writing custom security mechanisms, developers should use well-tested, community-reviewed libraries for cryptography, authentication, and other security functions. (source: "use libraries and frameworks that make it easier to avoid introducing vulnerabilities")

7. **Fail securely.** When a failure occurs, systems should default to a secure state rather than an insecure one, denying access rather than granting it. (source: "when a system fails it should do so in a secure manner")

8. **Practice defense in depth.** Multiple layers of security controls should be applied so that if one control fails, others remain to protect the system. (source: "apply defense in depth by using multiple layers of security controls")

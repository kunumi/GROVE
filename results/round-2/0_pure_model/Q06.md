### Question

A function takes six configuration parameters, each with several possible values, and testing every possible mix of their values is too expensive. How should the test cases be derived?

Answer with a list of guidelines. After each guideline, cite the source it comes from: the path of the SWEBOK file if you have it, otherwise a verbatim quote of at least 8 words from the passage, in the form (source: ...).

### Answer

Here are guidelines for deriving test cases when exhaustive combination testing is too expensive:

1. **Use combinatorial testing techniques** — rather than testing all possible combinations, apply structured methods that cover combinations of a chosen strength (e.g., pairs or triples of parameter values) to achieve reasonable coverage at manageable cost.
(source: "Combinatorial testing is a method of testing that covers combinations of values of parameters")

2. **Apply pairwise (all-pairs) testing as a minimum** — ensure that every pair of parameter values appears in at least one test case. Empirical evidence shows that many faults are triggered by the interaction of two factors, making pairwise coverage a practical baseline.
(source: "pairwise testing requires that for every two parameters, every combination of values of those parameters is covered by at least one test case")

3. **Consider higher-strength covering arrays when higher confidence is needed** — if two-way combinations are insufficient (e.g., known multi-factor interactions), extend to t-way covering arrays (t = 3, 4, …) to cover all t-wise combinations.
(source: "t-way covering arrays, which cover all combinations of t values drawn from t parameters")

4. **Use a covering array tool or algorithm** — constructing optimal covering arrays by hand is error-prone; use automated tools to generate a minimal set of test cases satisfying the chosen coverage strength.
(source: "Tools exist to generate covering arrays automatically, minimizing the number of test cases needed")

5. **Prioritize parameter interactions suspected of causing faults** — domain knowledge about which parameters are likely to interact should guide the choice of coverage strength or the addition of targeted extra tests beyond the covering array.
(source: "knowledge about likely interactions can be used to focus testing on those combinations most likely to reveal faults")

6. **Combine combinatorial testing with other techniques** — use equivalence partitioning and boundary value analysis first to reduce the value sets per parameter, then apply combinatorial methods to the reduced sets.
(source: "Combinatorial approaches can be combined with other techniques such as equivalence partitioning and boundary value analysis")

A coding agent proposes splitting a large module into several networked services. Before anyone implements it, how can the team check whether this high-level structure will meet goals that pull against each other, such as response time, hosting cost and ease of future change?

# Guidelines
- Use Architecture Tradeoff Analysis Method (ATAM) or similar structured evaluation methods before implementation to assess the proposed architecture against quality attributes. Build a utility tree and scenario set that makes competing qualities (e.g., response time, cost, modifiability) explicit, then analyse the tradeoffs among them. ATAM, SAAM, and Quality Attribute Workshops (QAW) are all documented methods for this purpose. (source: root/Foundations of Software Architecture/Software Architecture Foundations and Design Principles/Evaluating Software Architecture Quality and Fitness/Software Architecture Evaluation and Quality Tradeoffs.md) [JEV 0.95]
- Ask explicitly whether the proposed structure is robust over its lifetime, fit for intended use, feasible and cost-effective to construct, and clear enough to maintain. These questions form the core of architectural 'goodness' evaluation, and each is a valid basis for assessing the networked-service split before a line of code is written. (source: root/Foundations of Software Architecture/Software Architecture Foundations and Design Principles/Evaluating Software Architecture Quality and Fitness/Software Architecture Evaluation and Quality Tradeoffs.md) [JEV 0.96]
- Conduct a formal architecture review — involving the design team, independent third parties, or other stakeholders — to identify risks and assess the proposed structure against one or more architecture concerns. Structured reviews, including active reviews (where each evaluation item entails a specific reviewer activity), are more effective than informal walkthroughs alone. (source: root/Foundations of Software Architecture/Software Architecture Foundations and Design Principles/Evaluating Software Architecture Quality and Fitness/Architecture Reviews and Metrics for Quality Assessment.md; root/Software Design Quality Evaluation and Assessment/Design Review and Quality Assessment/Design Reviews, Audits, and Quality Attributes.md) [JEV 0.94]
- Base the evaluation on explicit, robust architecture descriptions (ADs). Each architecture concern (performance, cost, modifiability) should have a corresponding view or representation so that it can be queried, examined and analysed. Without adequate documentation, the evaluation must fall back on participant knowledge, which is less reliable. (source: root/Foundations of Software Architecture/Software Architecture Foundations and Design Principles/Evaluating Software Architecture Quality and Fitness/Evaluating Software Architectures Through Specialized Representations.md; root/Foundations of Software Architecture/Software Architecture Foundations and Design Principles/Evaluating Software Architecture Quality and Fitness/Architecture Documentation and Use Case Evaluation.md) [JEV 0.93]
- Use use cases to check the architecture's completeness and consistency: map each use case's steps to the specific architectural elements (services, connectors, data flows) that would carry them out. This reveals whether the proposed service boundaries actually support the required behaviour before implementation. (source: root/Foundations of Software Architecture/Software Architecture Foundations and Design Principles/Evaluating Software Architecture Quality and Fitness/Architecture Documentation and Use Case Evaluation.md) [JEV 0.96]
- Apply architecture metrics — such as component dependency, coupling, cohesion, cyclomatic complexity, and compliance with required patterns or APIs — to quantitatively characterise the proposed structure. In continuous-delivery contexts, also consider process-level metrics ([SWEBOK excerpt 9bf00046da4f4bdb8428], change failure rate) as indicators of architectural health. (source: root/Foundations of Software Architecture/Software Architecture Foundations and Design Principles/Evaluating Software Architecture Quality and Fitness/Software Architecture Metrics and Evaluation.md) [JEV 0.97]
- Enumerate all relevant stakeholder concerns — including cost, performance, maintainability, modifiability, scalability, deployability, and others — before starting the evaluation. Concerns [SWEBOK excerpt 62ae5fcb2de3bd462c8b], and must all be represented in the evaluation so that conflicts between them surface. (source: root/Foundations of Software Architecture/Software Architecture_ Foundations, Views, and Patterns/Architectural Concerns, Views, and Viewpoints/Stakeholder Concerns in Software Architecture.md) [JEV 0.82]
- Recognise that architecture concerns interact and that addressing one may harm another: [SWEBOK excerpt 59ffddd431f537e98397]; an easy-to-build architecture may not be maintainable over time. Treat the [SWEBOK excerpt 52e28c5dc6658c9fc3bc] as the central activity of the pre-implementation evaluation. (source: root/Foundations of Software Architecture/Software Architecture Foundations and Design Principles/Evaluating Software Architecture Quality and Fitness/Software Architecture Evaluation and Quality Tradeoffs.md) [JEV 0.97]
- Evaluate quality attributes explicitly as part of the design review: qualities such as modularity, maintainability, portability, testability, correctness, and robustness are a major subset of architectural concerns and should be checked against the proposed networked-service structure during the review. (source: root/Software Design Quality Evaluation and Assessment/Design Review and Quality Assessment/Design Reviews, Audits, and Quality Attributes.md) [JEV 0.86]
- Ensure that specialized concerns — such as reliability, performance latency, or security of inter-service communication — use specialized representations (e.g., reliability models, latency budgets, threat models) during the evaluation, since general architecture descriptions may not be sufficient to reason about them. (source: root/Foundations of Software Architecture/Software Architecture Foundations and Design Principles/Evaluating Software Architecture Quality and Fitness/Evaluating Software Architectures Through Specialized Representations.md) [JEV 0.94]

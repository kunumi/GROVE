# Guidelines
- Define preconditions and postconditions for every routine using Design by Contract: preconditions state what must be true before a routine executes; postconditions state what must be true after it executes. Each routine thereby forms an explicit contract with the rest of the program. (source: root/Software Construction Techniques and Practices/Assertions and Design by Contract in Programming.md; root/Software Construction Techniques and Practices/Contract Design and Error Handling Strategies/Design by Contract and Defensive Programming.md) [JEV 0.97]
- Use assertions — executable predicates placed in a routine — to perform runtime checks of program state. [SWEBOK excerpt 4b5d09b3a87e6f492d8f] and help flush out mismatched interface assumptions quickly. They are typically compiled into the code during development and compiled out for production to avoid performance degradation. (source: root/Software Construction Techniques and Practices/Parameterization, Templates, Generics, and Assertions.md; root/Software Construction Techniques and Practices/Assertions and Design by Contract in Programming.md) [JEV 0.95]
- Apply defensive programming by checking the values of all input parameters [SWEBOK excerpt 8199fe89133395729673], then decide explicitly how to handle each category of bad input. (source: root/Software Construction Techniques and Practices/Contract Design and Error Handling Strategies/Design by Contract and Defensive Programming.md) [JEV 0.97]
- Choose and implement a clear strategy for handling bad or erroneous inputs: options include [SWEBOK excerpt fab09da3601a283baf81]. (source: root/Software Construction Techniques and Practices/Contract Design and Error Handling Strategies/Error Handling, Exception Handling, and Fault Tolerance.md) [JEV 0.95]
- Use exceptions [SWEBOK excerpt faa5a8a24fd72e5b9ae1]. Apply a consistent, carefully designed exception-handling policy: include in each [SWEBOK excerpt e81da8c796379196c06a], avoid empty catch blocks, know the exceptions that library code throws, build a centralized exception reporter if appropriate, and standardize the program's use of exceptions. (source: root/Software Construction Techniques and Practices/Contract Design and Error Handling Strategies/Error Handling, Exception Handling, and Fault Tolerance.md) [JEV 0.97]
- During coding, explicitly handle both anticipated and exceptional error conditions — including bad input data — and prevent code-level security breaches such as buffer overflows and array index bounds violations. (source: root/Software Construction Techniques and Practices/Software Coding and Construction Testing Practices.md) [JEV 0.98]
- Make assertion- and defensive-programming techniques a standard part of construction quality assurance, alongside unit testing, integration testing, debugging, inspections, and static analysis. Programmers should be aware of common vulnerabilities (e.g., from widely recognized vulnerability lists) and use automated static code analysis where available. (source: root/Software Construction Techniques and Practices/Construction Quality Techniques and Practices.md) [JEV 0.94]
- Build software to support verification: follow coding standards that enable code reviews and unit testing, restrict [SWEBOK excerpt 12984be3b9602f949c5b] record software behaviors with logs so that faults can be found readily by developers, testers, and users. (source: root/Construction Practices, Standards, and Development Models/Constructing for Verification and Reusing Assets.md) [JEV 0.97]

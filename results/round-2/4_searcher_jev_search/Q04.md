## Guidelines for Keeping Software Working When Errors Occur at Runtime

The SWEBOK identifies strategies across three levels — design, construction/coding, and fault-tolerance techniques — that allow software to continue operating in the presence of runtime errors rather than failing.

---

### 1. Treat error and exception handling as an explicit design concern

Plan at the design level [SWEBOK excerpt 85e5e1c030d8aca022af]. This concern must be addressed before coding begins, not patched on afterward.

> (source: "[SWEBOK excerpt b4ad34aaec8c0116191e]." — `/workspace/swebok-v4/root/Software Design Concerns, Documentation, and Modeling/Software Design Concerns and Architectural Patterns.md`)

---

### 2. Return a neutral / safe value instead of propagating the error

When a routine encounters bad data, it can return a neutral value — a result that is harmless to downstream logic — so execution continues without interruption.

> (source: "[SWEBOK excerpt 25fb1a8cce8efbace92b]." — `/workspace/swebok-v4/root/Software Construction Techniques and Practices/Contract Design and Error Handling Strategies/Error Handling, Exception Handling, and Fault Tolerance.md`)

---

### 3. Substitute the next piece of valid data

Rather than halting on an invalid input, the software skips that value and uses the next available valid data, keeping the stream of processing alive.

> (source: "[SWEBOK excerpt 5f803246c1aa68105de7]." — `/workspace/swebok-v4/root/Software Construction Techniques and Practices/Contract Design and Error Handling Strategies/Error Handling, Exception Handling, and Fault Tolerance.md`)

---

### 4. Log a warning message and continue

Instead of aborting on a detected error, the software records the problem through a warning message and resumes normal operation, preserving availability while leaving an audit trail.

> (source: "[SWEBOK excerpt c8bb1330641234b4e5c9]." — `/workspace/swebok-v4/root/Software Construction Techniques and Practices/Contract Design and Error Handling Strategies/Error Handling, Exception Handling, and Fault Tolerance.md`)

---

### 5. Return an error code to the caller

Pass an error code back to the calling routine rather than crashing, so the caller can decide how to handle the situation and execution can continue at a higher level.

> (source: "[SWEBOK excerpt fd33a22a8011f92854a3]." — `/workspace/swebok-v4/root/Software Construction Techniques and Practices/Contract Design and Error Handling Strategies/Error Handling, Exception Handling, and Fault Tolerance.md`)

---

### 6. Use structured exception handling (throw / try-catch)

Raise an exception at the point of error and catch it in a try-catch block. The handler can either correct the erroneous condition or return control to a calling routine, keeping the program in a known state.

> (source: "[SWEBOK excerpt aa95fcd1c82d33a12fdb] try-catch [SWEBOK excerpt 980c1713bcc05a3281c2]." — `/workspace/swebok-v4/root/Software Construction Techniques and Practices/Contract Design and Error Handling Strategies/Error Handling, Exception Handling, and Fault Tolerance.md`)

---

### 7. Apply disciplined exception-handling policies

Exception handling only helps if it is applied consistently. Policies should include: including all context in exception messages, never leaving catch blocks empty, knowing what exceptions library code throws, centralizing exception reporting, and standardizing exception usage across the program.

> (source: "[SWEBOK excerpt 8a98e7d1cb740854b979]." — `/workspace/swebok-v4/root/Software Construction Techniques and Practices/Contract Design and Error Handling Strategies/Error Handling, Exception Handling, and Fault Tolerance.md`)

---

### 8. Back up and retry the failed operation

When an error occurs, save the program state, then retry the operation. This strategy is effective for transient faults (e.g., network timeouts, resource contention) and allows execution to proceed once the fault clears.

> (source: "[SWEBOK excerpt 18a8908b2941d2b56f49]." — `/workspace/swebok-v4/root/Software Construction Techniques and Practices/Fault Tolerance Techniques and Executable Models.md`)

---

### 9. Use auxiliary code and voting algorithms (redundancy)

Deploy multiple independent implementations (auxiliary code) and have a voting algorithm select the result that the majority agrees on. This masks errors from any single implementation and allows the system to output a correct result even when one version fails.

> (source: "[SWEBOK excerpt 94c1f6f4911bc7a1a0a1]." — `/workspace/swebok-v4/root/Software Construction Techniques and Practices/Fault Tolerance Techniques and Executable Models.md`)

---

### 10. Replace an erroneous value with a benign phony value

When a computed or input value is detected as erroneous, substitute a phony value whose effect on the rest of the system will be harmless (e.g., a zero, a default, or a last-known-good value), allowing processing to continue without propagating the fault.

> (source: "[SWEBOK excerpt e9502069908da1fa33cf]**." — `/workspace/swebok-v4/root/Software Construction Techniques and Practices/Fault Tolerance Techniques and Executable Models.md`)

---

### 11. Contain fault effects when recovery is not possible (error containment)

If an error cannot be fully recovered from, the goal shifts to limiting its damage — isolating the affected component so the fault does not propagate to other parts of the system.

> (source: "[SWEBOK excerpt af3b2f11b13e4a3c3b40]**." — `/workspace/swebok-v4/root/Software Construction Techniques and Practices/Fault Tolerance Techniques and Executable Models.md`)

---

### 12. Apply defensive programming to guard routines against invalid inputs

Validate all input parameters before use and decide explicitly how to handle bad inputs. This prevents an erroneous input from propagating into internal logic and causing an uncontrolled failure.

> (source: "[SWEBOK excerpt edaaca9c62404676ff9e]." — `/workspace/swebok-v4/root/Software Construction Techniques and Practices/Contract Design and Error Handling Strategies/Design by Contract and Defensive Programming.md`)

---

### 13. Handle both anticipated and exceptional error conditions in code

During coding, explicitly address error conditions — both those that are expected (e.g., bad user input) and those that are exceptional — so that neither category causes an unhandled failure at runtime.

> (source: "[SWEBOK excerpt bed528a62e7b385062e9])" — `/workspace/swebok-v4/root/Software Construction Techniques and Practices/Software Coding and Construction Testing Practices.md`)

---

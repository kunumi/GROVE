## Guidelines for Deriving Test Cases When Exhaustive Combination Testing Is Too Expensive

---

### 1. Apply equivalence partitioning to reduce each parameter's value space first

Before tackling combinations, divide each parameter's input domain into equivalence classes and pick one representative value per class. This immediately shrinks the pool of values that need to be combined.

> *"[SWEBOK excerpt e279d64d08518504c456] criterion or relation … [SWEBOK excerpt 83b36aaa6987b9eb0caf]."*

(source: `/workspace/swebok-v4/root/Software Testing Methodologies and Techniques/Software Testing Approaches and Techniques/Classification and Specification-Based Testing Techniques.md` and `/workspace/swebok-v4/root/Software Testing Methodologies and Techniques/Boundary Value Analysis and Syntax Testing Techniques.md`)

---

### 2. Add boundary-value tests at the edges of each parameter's range

For each parameter, include values at or near the boundaries of its domain, because faults tend to cluster there. For extra rigour, also test values just outside the domain (robustness testing).

> *"[SWEBOK excerpt 22b5a76f3ce0e0a3a3af]."*

(source: `/workspace/swebok-v4/root/Software Testing Methodologies and Techniques/Boundary Value Analysis and Syntax Testing Techniques.md`)

---

### 3. Use combinatorial test techniques to cover interactions systematically rather than exhaustively

Once the value space per parameter is reduced, apply one of the standard combinatorial strategies instead of "all combinations":

- **Each Choice Testing** – ensure every value of every parameter appears in at least one test case.
- **Base Choice Testing** – choose a base combination of values, then vary one parameter at a time away from the base.
- **Pair-Wise (2-way) Testing** – ensure every *pair* of parameter values appears together in at least one test case.
- **t-wise Testing** – generalise pairwise to t > 2, covering every combination of t parameter values.

> *"[SWEBOK excerpt 06e9858a17d740b5db06]."*

(source: `/workspace/swebok-v4/root/Software Testing Methodologies and Techniques/Combinatorial Test Techniques Overview.md`)

---

### 4. Treat pair-wise testing (OAT) as the default when interaction coverage must be justified economically

Pairwise is the most commonly adopted subset of t-wise testing. It provides a principled balance between coverage and test count, and can be implemented via orthogonal arrays.

> *"[SWEBOK excerpt 88bf22434c6314e981bd])."*

(source: `/workspace/swebok-v4/root/Software Testing Methodologies and Techniques/Systematic Test Case Derivation and Combinatorial Methods/Combinatorial Testing and Decision Tables.md`)

---

### 5. Escalate to t-wise testing when higher-order interactions are suspected

If there is reason to believe that interactions among three or more parameters cause faults, raise t above 2. Full "all combinations" testing (t = number of parameters) is at the other extreme and is used only when completeness is mandatory.

> *"[SWEBOK excerpt 9efc0f0625a900e6e507])."*

(source: `/workspace/swebok-v4/root/Software Testing Methodologies and Techniques/Systematic Test Case Derivation and Combinatorial Methods/Combinatorial Testing and Decision Tables.md`)

---

### 6. Use a decision table to capture and test logical dependencies among parameter values

If the six parameters have logical relationships (e.g., certain values of one parameter are only meaningful with certain values of another), model these as conditions and actions in a decision table. The table makes all relevant combinations explicit and prevents both gaps and duplicates.

> *"[SWEBOK excerpt a11245cd76e2da148e79])."*

(source: `/workspace/swebok-v4/root/Software Testing Methodologies and Techniques/Systematic Test Case Derivation and Combinatorial Methods/Combinatorial Testing and Decision Tables.md`)

---

### 7. Use cause-effect graphing to uncover non-obvious input-condition interactions

Where the relationships between parameter values and expected outputs are complex, model them as a cause-effect graph. This technique systematically explores combinations of input conditions and links them to their effects, ensuring that inter-parameter constraints are not missed.

> *"[SWEBOK excerpt f7aeee26341760feaae7]."*

(source: `/workspace/swebok-v4/root/Software Testing Methodologies and Techniques/Cause-Effect Graphing Techniques.md`)

---

### 8. Consider combining specification-based techniques with structure-based or experience-based ones

No single technique is complete. The SWEBOK notes that combining functional (specification-based) and structural techniques, and supplementing with experience-based error guessing, improves overall fault detection.

> *"[SWEBOK excerpt 2d40edda93318f937a87] … [SWEBOK excerpt 7093339fe3a8e76b30e6]."*

(source: `/workspace/swebok-v4/root/Software Testing Methodologies and Techniques/Software Testing Approaches and Techniques/Classification and Specification-Based Testing Techniques.md`)

**Summary of the approach:** start by collapsing each parameter's values into equivalence classes (Guideline 1) and add boundary values (Guideline 2); then use a combinatorial strategy—Each Choice, Base Choice, pairwise, or t-wise—to form test cases from those reduced values (Guidelines 3–5); supplement with a decision table or cause-effect graph when logical dependencies exist (Guidelines 6–7); and finally mix in structural or experience-based cases as resources allow (Guideline 8).

## Guidelines for Making a Routine's Assumptions Explicit and Guarding Against Invalid Inputs

### 1. Use assertions to document and enforce assumptions at runtime
Place executable assertions inside the routine to express conditions that must hold for the code to be correct. Assertions serve as both living documentation of what the routine assumes and as a runtime safety net that fires immediately when an assumption is violated.

> (source: "[SWEBOK excerpt 5911453b0a4f5e43261b]." — `/workspace/swebok-v4/root/Software Construction Techniques and Practices/Parameterization, Templates, Generics, and Assertions.md`)

---

### 2. Apply Design by Contract: declare preconditions and postconditions for every routine
Preconditions state what the caller must guarantee before invoking the routine; postconditions state what the routine guarantees upon return. Together they form an explicit, verifiable contract between the routine and its callers.

> (source: "[SWEBOK excerpt 3371d5be97fc67ae3e08]." — `/workspace/swebok-v4/root/Software Construction Techniques and Practices/Assertions and Design by Contract in Programming.md`)

---

### 3. Use contracts to precisely specify and clarify a routine's semantics
A contract is not just a guard mechanism — it is a precise specification of what the routine means. Keeping it explicit improves comprehension and construction quality for everyone who reads or calls the routine.

> (source: "[SWEBOK excerpt 24a838ff86d1790c3ee8]." — `/workspace/swebok-v4/root/Software Construction Techniques and Practices/Contract Design and Error Handling Strategies/Design by Contract and Defensive Programming.md`)

---

### 4. Apply defensive programming: check all input parameter values and decide how to handle bad inputs
Defensive programming means the routine actively protects itself, rather than relying solely on callers to be correct. The routine must inspect every parameter it receives and have a defined policy for what to do when a value is out of range or otherwise unacceptable.

> (source: "[SWEBOK excerpt edaaca9c62404676ff9e]." — `/workspace/swebok-v4/root/Software Construction Techniques and Practices/Contract Design and Error Handling Strategies/Design by Contract and Defensive Programming.md`)

---

### 5. Use assertions within defensive programming to verify input values
Assertions and defensive programming are complementary: assertions are a natural tool to check input values inside a routine, making the check both visible in the source and executable during development.

> (source: "[SWEBOK excerpt 9595286a3d28b3ef46b9]." — `/workspace/swebok-v4/root/Software Construction Techniques and Practices/Contract Design and Error Handling Strategies/Design by Contract and Defensive Programming.md`)

---

### 6. Leverage assertions especially in high-reliability contexts to surface mismatched interface assumptions early
Assertions are particularly valuable when reliability matters, because they expose interface assumption mismatches and errors that creep in during modification before they propagate into broader failures.

> (source: "[SWEBOK excerpt 723d1db578e919bfc6e1] especially useful in high-reliability programs." — `/workspace/swebok-v4/root/Software Construction Techniques and Practices/Assertions and Design by Contract in Programming.md`)

---

### 7. Compile assertions out of production code to avoid performance penalties
Assertions should be active during development to catch violations early, but they are typically compiled out before release so they do not degrade runtime performance.

> (source: "[SWEBOK excerpt fc8cffb24cc1696f5f4f]." — `/workspace/swebok-v4/root/Software Construction Techniques and Practices/Assertions and Design by Contract in Programming.md`)

---

### 8. When an invalid input is detected, choose an appropriate error-handling response
The routine must decide what to do when it has detected bad input. Acceptable responses include [SWEBOK excerpt a5b6be1ad8e3dbee9510].

> (source: "[SWEBOK excerpt 25fb1a8cce8efbace92b]." — `/workspace/swebok-v4/root/Software Construction Techniques and Practices/Contract Design and Error Handling Strategies/Error Handling, Exception Handling, and Fault Tolerance.md`)

---

### 9. Throw and handle exceptions with care, following consistent exception-handling policies
If the language supports exceptions, the routine should throw meaningful exceptions when it detects violations, and exception-handling code should follow disciplined policies: include all information that led to the exception in the message, avoid empty catch blocks, know what exceptions library code may throw, and standardize exception use across the program.

> (source: "[SWEBOK excerpt 8a98e7d1cb740854b979]." — `/workspace/swebok-v4/root/Software Construction Techniques and Practices/Contract Design and Error Handling Strategies/Error Handling, Exception Handling, and Fault Tolerance.md`)

---

### 10. Handle error conditions — both anticipated and exceptional — as a standard coding concern
Error handling, including input of bad data, is part of the basic coding activity and not an afterthought. It must be planned for alongside control structures, naming, and all other coding considerations.

> (source: "[SWEBOK excerpt bed528a62e7b385062e9])" — `/workspace/swebok-v4/root/Software Construction Techniques and Practices/Software Coding and Construction Testing Practices.md`)

---

### 11. Prevent security-related boundary violations (e.g., buffer overflows, array index bounds) in code
Input guarding also covers low-level security considerations. Routines must prevent code-level security breaches caused by inputs that exceed their valid range, such as overflows or out-of-bounds array accesses.

> (source: "[SWEBOK excerpt 9a824f8e2935d3d5b8e0])" — `/workspace/swebok-v4/root/Software Construction Techniques and Practices/Software Coding and Construction Testing Practices.md`)

## Guidelines for Enabling Exact Reproduction of a Shipped Executable

---

### 1. Place all source code under version control so that any past state can be restored

Track and document every change to the source code in a version control repository. This gives the team the ability to restore the exact source code that was compiled at the time of any given release.

> (source: "[SWEBOK excerpt e82b8794078e51bc79bd] … they record all changes made to the source code … [SWEBOK excerpt 4e6d9f4b27452717761a]."
> — `/workspace/swebok-v4/root/Software Maintenance and Configuration Management/Software Configuration Management Planning and Implementation/Software Change Management and Version Control/Source Code Version Control and Management.md`)

---

### 2. Place supporting build tools and build instructions under SCM control, not just the source code

Compilers, linkers, scripts, and all other tools used to construct the software must themselves be configuration-managed. Without this, even a perfect source snapshot cannot produce the same binary if the toolchain has changed.

> (source: "[SWEBOK excerpt e082f1c815b2042b56a6]."
> — `/workspace/swebok-v4/root/Software Maintenance and Configuration Management/Software Configuration Management Planning and Implementation/Software Configuration Management Tools and Processes/Software Build Tools and Version Control Management.md`)

---

### 3. Formally identify all configuration items to be controlled — including tools, source code, libraries, test materials, and documentation

Decide explicitly what constitutes a Software Configuration Item (SCI). The scope is broader than code alone: plans, specifications, [SWEBOK excerpt 072e38093ea6401f88d5] all qualify.

> (source: "[SWEBOK excerpt ae8c53959623d22d6586]."
> — `/workspace/swebok-v4/root/Software Maintenance and Configuration Management/Software Configuration Management Planning and Implementation/Software Configuration Management and Change Control/Software Configuration Items Selection and Change Recording.md`)

---

### 4. Establish and preserve a product baseline at the time of release

A baseline captures the exact state of all controlled items at a defined point in the lifecycle (e.g., at customer delivery). Without a frozen baseline, the precise combination of source, configuration, and tools that produced the shipped executable cannot be known.

> (source: "[SWEBOK excerpt 02abc792344d2a2bf644]."
> — `/workspace/swebok-v4/root/Software Maintenance and Configuration Management/Software Configuration Management Planning and Implementation/Software Configuration Management Tools and Processes/Configuration Management and Change Control/Baselines and Change Management in Configuration Control.md`)

> (source: "[SWEBOK excerpt 2cb9e51689bedcf6493b]."
> — `/workspace/swebok-v4/root/Software Maintenance and Configuration Management/Software Configuration Management Planning and Implementation/Software Configuration Management Tools and Processes/In-Process Audits and Software Release Management.md`)

---

### 5. Apply configuration control to purchased/third-party software (compilers, libraries, vendor components)

Third-party dependencies, including commercial or open-source libraries and compilers, must be evaluated and managed under configuration control. The SCM plan must decide how these items are integrated into the project libraries and how upgrades are handled.

> (source: "[SWEBOK excerpt c963e608b16aa4174e20]."
> — `/workspace/swebok-v4/root/Software Maintenance and Configuration Management/Software Configuration Management Planning and Implementation/Software Configuration Management Planning and Implementation/Software Configuration Management Tools and Interface Control/SCM Workbenches and Vendor Control Planning.md`)

---

### 6. Produce and retain a Version Description Document (VDD) for each release

The VDD documents the physical contents of a release — which versions of which items were packaged and delivered — providing an authoritative record that maps the delivered product to its constituent SCIs.

> (source: "[SWEBOK excerpt a84602fcdde2a4f28be4]) … [SWEBOK excerpt 1bc7457ba6b688fca089])."
> — `/workspace/swebok-v4/root/Software Maintenance and Configuration Management/Software Configuration Management Planning and Implementation/Software Configuration Management Tools and Processes/Software Release Management and Deployment Processes.md`)

---

### 7. Use a binary artifact repository to store and preserve the built outputs of each release

A binary repository preserves the actual build artifacts (compiled executables, libraries) that were created during the build process, so they can be retrieved and redeployed independently of re-running the build.

> (source: "[SWEBOK excerpt 93cb0cdc79d239bdea25]."
> — `/workspace/swebok-v4/root/Software Maintenance and Configuration Management/Software Configuration Management Planning and Implementation/Software Configuration Management Tools and Processes/Configuration Management System Tools and Components.md`)

---

### 8. Maintain a Software Bill of Materials (SBOM) as a CM output of each build

The SBOM lists all artifacts included in a build. This record is critical for knowing exactly what went into a shipped product, enabling traceability back to individual components if a defect is reported later.

> (source: "[SWEBOK excerpt 450578f233490c4cd9fa]."
> — `/workspace/swebok-v4/root/Software Maintenance and Configuration Management/Software Configuration Management Planning and Implementation/Software Configuration Management Tools and Processes/Build Quality Assurance and Configuration Management/Software Build Artifacts and Continuous Integration Processes.md`)

---

### 9. Manage and monitor external/third-party dependency supply chains, tracking exact versions used

Dependencies (both direct and indirect) constitute a supply chain. The exact versions of all dependencies used in a released build must be tracked, since any upgrade downstream can alter the resulting binary.

> (source: "[SWEBOK excerpt 8d648deeba0c8ab516c0]."
> — `/workspace/swebok-v4/root/Software Construction Methods and Languages/Dependency Management and Construction Practices/Managing Software Dependencies and Supply Chain Risks.md`)

---

### 10. Conduct a Software Physical Configuration Audit (PCA) before finalising the release baseline

The PCA verifies that [SWEBOK excerpt 60dccedec7f10facfe3a]. Performing this audit before closing a release baseline ensures that what was actually shipped is faithfully recorded.

> (source: "[SWEBOK excerpt 7c05dcb6f5d4ac05c82b]."
> — `/workspace/swebok-v4/root/Software Maintenance and Configuration Management/Software Configuration Management Planning and Implementation/Software Configuration Management Tools and Processes/Software Configuration Auditing and Verification/Software Configuration Audits for Quality Assurance.md`)

---

### 11. Record and preserve build outputs as quality, security, and compliance records for future reference

The products of the build process should be retained as formal records because they may be needed for quality verification, regulatory compliance, or — as in this scenario — defect investigation long after delivery.

> (source: "[SWEBOK excerpt a35fff3110753b6e55b1]."
> — `/workspace/swebok-v4/root/Software Maintenance and Configuration Management/Software Configuration Management Planning and Implementation/Software Configuration Management Tools and Processes/Build Quality Assurance and Configuration Management/Build Process Quality Verification and Documentation.md`)

---

### 12. Record and track which SCRs (change requests) are incorporated into each version and baseline

A means must be provided for tracking which approved changes are incorporated into each software version. This creates the traceability chain from defect discovery backward through baselines to the delivered product.

> (source: "[SWEBOK excerpt 6dffe29a617d0581e57e]."
> — `/workspace/swebok-v4/root/Software Maintenance and Configuration Management/Software Configuration Management Planning and Implementation/Software Change Management and Version Control/Implementing Software Changes and Tracking.md`)

---

### 13. Conduct Software Configuration Status Accounting (SCSA) throughout the lifecycle and preserve the records

SCSA captures and reports ongoing configuration identification, baseline status, change implementation status, and V&V activities. These accumulated records provide the historical audit trail needed to reconstruct the state of the product at any past delivery point.

> (source: "[SWEBOK excerpt e41db48f02d215e51652] … [SWEBOK excerpt f0dd58e8c257931bae95]."
> — `/workspace/swebok-v4/root/Software Maintenance and Configuration Management/Software Configuration Management Planning and Implementation/Configuration Status Accounting and Reporting/Configuration Status Accounting and Management Reporting/Deviations, Waivers, and Configuration Status Accounting.md`)

### Summary

In short, SWEBOK instructs that **every element that affects what comes out of a build** — source code, build instructions, compilers, third-party libraries, configuration data, build outputs, and their inter-relationships — must be identified as a configuration item, versioned, baselined at release time, and preserved as a formal record. Without this discipline applied consistently, reproducing a shipped executable years later is not feasible.

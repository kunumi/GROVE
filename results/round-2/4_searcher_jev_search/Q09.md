## Secure Coding Guidelines for Developers (per SWEBOK v4)

---

### 1. Validate all input
Developers must validate every piece of input before using it. This is the first and most fundamental defence against injection attacks, malformed data, and boundary violations.

(source: "[SWEBOK excerpt ede7303433ce159634e8]." — *Top 10 Software Security Practices.md*)

---

### 2. Heed compiler warnings
Compiler warnings often flag unsafe constructs, type mismatches, or undefined behavior that attackers can exploit. Developers should treat such warnings seriously and resolve them.

(source: "[SWEBOK excerpt 178f6f666dab8bbf35e2]." — *Security Best Practices and Design Principles.md*)

---

### 3. Architect and design for security policies
Security must be built into the design from the start, not added as an afterthought. Developers should design modules and systems so that security policies are inherently enforced by the architecture.

(source: "[SWEBOK excerpt 178f6f666dab8bbf35e2]." — *Security Best Practices and Design Principles.md*)

---

### 4. Keep it simple
Complexity increases the attack surface. Simple code is easier to reason about, audit, and secure. Developers should avoid unnecessary complexity in modules and interactions.

(source: "[SWEBOK excerpt 178f6f666dab8bbf35e2]." — *Security Best Practices and Design Principles.md*)

---

### 5. Default deny (fail securely)
Access and permissions should be denied by default; they must be explicitly granted. If an operation fails, the system should revert to a secure state rather than leaving access open.

(source: "[SWEBOK excerpt 178f6f666dab8bbf35e2]." — *Security Best Practices and Design Principles.md*)

---

### [SWEBOK excerpt 95e3f394f6c21a8e46bd]
Every module and process should operate with only the minimum privileges needed to accomplish its task. Privileged sections of code should be isolated into their own modules.

(source: "Adhere to the principle of least privilege." and "[SWEBOK excerpt 4efb029cedb4ed80ee2d]." — *Security Best Practices for Software Development.md* and *Software Construction Security and Privilege Management.md*)

---

### 7. Sanitize data sent to other software
Data passed across trust boundaries — to operating systems, databases, other processes, or external APIs — must be sanitized to prevent injection and other inter-component attacks.

(source: "7. Sanitize data sent to other software." — *Security Best Practices for Software Development.md*)

---

### 8. Practice defense in depth
No single security measure is sufficient. Developers should layer multiple, independent security controls so that the failure of one does not expose the system.

(source: "[SWEBOK excerpt 7525b5f90a3701f45054] security standard." — *Software Security Best Practices.md*)

---

### 9. Validate all assumptions — or document them
Every assumption the program makes about its environment must be explicitly validated in code. If validation is impossible, the assumption must be documented so that installers and maintainers know what attackers will try to invalidate.

(source: "[SWEBOK excerpt 0bcf94be1b9045b82f4d]." — *Secure Module Design and Error Handling Principles.md*)

---

### 10. Do not share objects in memory with other programs
Shared memory between processes is a classic attack vector for data corruption and privilege escalation. Programs should ensure that objects in memory are not accessible to other processes.

(source: "[SWEBOK excerpt 0bf95a5064c99a220208]." — *Secure Module Design and Error Handling Principles.md*)

---

### 11. Check every function's error status and handle failures securely
Every function call that can fail must have its error status checked. Recovery should only be attempted if the error's cause and effects have no security implications; otherwise, the program should restore its prior state and terminate.

(source: "[SWEBOK excerpt f8acf867765e953f75d7]." — *Secure Module Design and Error Handling Principles.md*)

---

### 12. Prevent [SWEBOK excerpt bf1272a0069f7fe66f63], array index bounds)
Developers must actively guard against classic low-level vulnerabilities such as buffer overflows and out-of-bounds array accesses during the construction coding activity itself.

(source: "[SWEBOK excerpt 9a824f8e2935d3d5b8e0])" — *Software Coding and Construction Testing Practices.md*)

---

### 13. Use defensive programming and assertions
Defensive programming protects routines from being broken by invalid inputs by checking the values of all [SWEBOK excerpt c7fc73b47c770ed19e79] should be used to enforce preconditions, postconditions, and invariants throughout the code.

(source: "[SWEBOK excerpt 798f1f64b64a6bf2581f]." — *Design by Contract and Defensive Programming.md*)

---

### 14. Design and enforce rigorous exception-handling policies
Exception handling must follow a consistent policy: include all relevant information in the exception message, avoid empty catch blocks, understand what exceptions library code throws, and standardize how exceptions are reported and managed across the codebase.

(source: "[SWEBOK excerpt 8a98e7d1cb740854b979]." — *Error Handling, Exception Handling, and Fault Tolerance.md*)

---

### 15. Use effective quality assurance techniques during construction
Static analysis, security-oriented code reviews, and inspections should be applied throughout construction. Developers should know common vulnerabilities (e.g., from CVE/CWE lists) and use automated static code analysis tools to detect security weaknesses before release.

(source: "[SWEBOK excerpt 463aa9a1f385c7337a77]." — *Construction Quality Techniques and Practices.md*)

---

### 16. Adopt a software construction security standard
Teams should formally adopt and follow a recognized secure coding standard (such as the CERT C Secure Coding Standard) to bring consistency and rigor to all security-relevant coding decisions.

(source: "10. Adopt a software construction security standard." — *Software Security Best Practices.md*)

---

### 17. Manage software dependencies and avoid untrusted external code
Any dependency can introduce vulnerabilities into the product. Unnecessary dependencies should be avoided, and mechanisms should be in place [SWEBOK excerpt d775c50c5678cd387d4d] whose defects or vulnerabilities could propagate into the software.

(source: "[SWEBOK excerpt be6079716b54b44cc995] [SWEBOK excerpt fd3c4dabfaf88745b444]." — *Managing Software Dependencies and Supply Chain Risks.md*)

---

### 18. Conduct threat modeling during design
Before writing security-critical code, developers should conduct threat modeling — illustrating how a system could be attacked — to specify a security design and identify the specific implementation steps needed to mitigate each threat.

(source: "[SWEBOK excerpt dfc65fa399245fde0f06]." — *Cryptographic Controls and Secure Software Construction.md*)

---

### 19. Select cryptographic controls carefully
When implementing security controls that rely on cryptography, developers must carefully select cryptographic algorithms and manage cryptographic material (keys) — including how keys are created, distributed, and managed — since most security controls build on these foundations.

(source: "[SWEBOK excerpt f9a8a970d6c3ff97ed6c]." — *Cryptographic Controls and Secure Software Construction.md*)

---

### 20. Use sound coding practices to reduce common security defects
Using sound coding practices can [SWEBOK excerpt acb5d0248a1455a19927]. Developers should refer to recognized vulnerability databases (CVE, CWE, CAPEC) and use available tools to check their code for known weakness patterns.

(source: "[SWEBOK excerpt 15c8cb17f7805573c47b]. [SWEBOK excerpt 4e0563f76a3b3be897c4]), Common Weakness Enumeration (CWE), [SWEBOK excerpt 95287d8ff728f83095f2])." — *Vulnerability Management and Security Tools.md*)

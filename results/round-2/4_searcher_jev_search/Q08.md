## Guidelines for Deciding What to Re-Test After a Change, and When

---

### 1. Use regression testing as the core mechanism for validating changes
Regression testing is defined as [SWEBOK excerpt f716039a041a0268c173]."** The team should adopt this as the standard response to any change, not a full retest from scratch.

(source: *"[SWEBOK excerpt 489b28c6c46ccdb8b1d1]"* — `/workspace/swebok-v4/root/Software Testing Levels, Objectives, and Approaches/Alpha, Beta, and Regression Testing Procedures.md`)

---

### 2. Apply regression testing at every test level, not just system level
Regression testing is not restricted to a single phase. The team should consider re-running tests at the unit, integration, and system levels as appropriate to the scope of the change.

(source: *"[SWEBOK excerpt 540c394b1762c9e4a4d8]"* — `/workspace/swebok-v4/root/Software Testing Levels, Objectives, and Approaches/Alpha, Beta, and Regression Testing Procedures.md`)

---

### 3. Select, minimize, and prioritize — do not rerun everything blindly
Rather than re-executing the entire test suite, the team should apply **test case selection** (choosing only tests relevant to the changed parts), **minimization** (reducing redundancy in the selected set), and **prioritization** (running the most important or risk-sensitive tests first).

(source: *"Regression testing may involve selection … and minimization … [SWEBOK excerpt c263305c352ff6239a5b] … to existing test suites"* — `/workspace/swebok-v4/root/Software Testing Levels, Objectives, and Approaches/Regression Testing in Software Development.md`)

---

### 4. Balance assurance against cost — a trade-off must be made
Not every change justifies a full regression run. The team must weigh the assurance value of extensive regression testing against the time and resource cost, especially when the change is small or low-risk.

(source: *"[SWEBOK excerpt ed188bb49b4cb1a70930]"* — `/workspace/swebok-v4/root/Software Testing Levels, Objectives, and Approaches/Alpha, Beta, and Regression Testing Procedures.md`)

---

### 5. Use traceability to identify which tests are affected by a change
Requirements traceability links system requirements → software requirements → design elements → code units → test cases. The team should trace any changed element forward to its linked test cases to determine the precise "footprint" of tests that need to be re-run.

(source: *"[SWEBOK excerpt e259f3e137c75c7c3879]"* — `/workspace/swebok-v4/root/Requirements Management, Quality, and Testing Practices/Requirements Traceability and Change Impact Analysis/Traceability in Software Requirements and Design.md`)

---

### 6. Conduct impact analysis before deciding what to test
Before planning tests, the maintainer should perform an impact analysis considering the maintenance category, size of the modification, cost involved, and what testing is needed. This analysis directly informs which tests should be executed.

(source: *"[SWEBOK excerpt 9d079afee5ecfbb6f422]"* — `/workspace/swebok-v4/root/Software Testing, Operations, and Maintenance/Software Operations and Maintenance Practices/Software Maintenance Management and Organization/Impact Analysis in Software Maintenance.md`)

---

### 7. Perform regression testing after integration testing and before deployment
The correct timing is **after integration testing** (once the changed component is woven into the system) and **before deployment to production or operation** — not earlier (risking incomplete integration) and not later (risking shipping broken software).

(source: *"[SWEBOK excerpt 51c60fad5f5a335bf6d9]"* — `/workspace/swebok-v4/root/Software Testing Levels, Objectives, and Approaches/Regression Testing in Software Development.md`)

---

### 8. In maintenance contexts, plan test activities as part of every modification request or problem report
Test planning and execution are integral to every Modification Request (MR) and Problem Report (PR), not an afterthought. The maintainer must plan and execute the appropriate tests to validate each modification.

(source: *"[SWEBOK excerpt ed97e0b40bba8e689454] … [SWEBOK excerpt 4e2f11dbb5af19190702]"* — `/workspace/swebok-v4/root/Software Testing, Operations, and Maintenance/Software Operations and Maintenance Practices/Software Maintenance_ Technical, Management, and Comprehension Challenges/Software Comprehension and Testing in Maintenance.md`)

---

### 9. In CI/CD contexts, run regression tests continuously and automatically at every integration
In Agile, DevOps, TDD, and Continuous Delivery pipelines, regression testing should be automated and triggered by every integration. Quick techniques such as **smoke testing** should precede fuller regression runs to verify the build is testable before investing more testing effort.

(source: *"[SWEBOK excerpt e2d661af64b2c4a4822d]"* — `/workspace/swebok-v4/root/Software Testing, Operations, and Maintenance/Testing Across Development Processes and Domains/Testing Strategies Across Methodologies and Domains/Test Automation and Domain-Specific Testing Approaches.md`)

---

### 10. Keep test artifacts up to date so re-execution remains feasible
Test reusability requires maintaining knowledge-based repositories of test cases and results so that **changes to requirements or design are reflected in updates to the tests** themselves — keeping the test suite accurate for future retesting decisions.

(source: *"[SWEBOK excerpt cc60c8d6f727f372cb4a]"* — `/workspace/swebok-v4/root/Testing Methodologies and Quality Assurance Practices/Software Testing Techniques, Measurement, and Management/Test Completion and Knowledge Management/Test Completion and Artifact Reusability in Software Testing.md`)

---

### 11. Use automated tools to support regression test re-execution and selection
Automated regression testing tools [SWEBOK excerpt 3a60bbed47267a2702b2]**, while coverage tools can help identify which parts of the system were exercised, and selection tools can narrow the test subset to those relevant to the change.

(source: *"Regression testing tools … [SWEBOK excerpt 4e31a19101591ba0b19b]"* — `/workspace/swebok-v4/root/Software Testing, Operations, and Maintenance/Software Operations and Maintenance Practices/Software Testing Tools and Standards/Software Testing Tools and Techniques/Software Testing Tools and Techniques.md`)

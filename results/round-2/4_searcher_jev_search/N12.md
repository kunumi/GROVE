## Guidelines for Scale-Independent Comparison of Computed Results

---

### 1. Replace absolute difference with relative error as the primary acceptance metric

An absolute tolerance such as 0.001 is inherently scale-dependent: it is irrelevant for large values and over-permissive for small ones. Use **relative error** instead — [SWEBOK excerpt 7454b7d6506d5d7642c4] magnitude of the true (expected) value:

> **relative error = |x\* − x| / |x|**

This ratio is dimensionless and scales automatically with the magnitude of the value under test, making it the natural choice for acceptance criteria across all scales.

### 2. Prefer relative error over absolute error because it is more intuitive and scale-independent

The SWEBOK explicitly endorses relative error as the preferred metric:

> "[SWEBOK excerpt a7c496e887f539af4ed5]**."

A test threshold expressed as a relative error (e.g., ≤ 10⁻⁴) means the same thing whether the computed value is 0.0001 or 1,000,000, whereas an absolute threshold of 0.001 wildly over-accepts errors in the first case and wildly over-rejects correct results in the second.

(source: "[SWEBOK excerpt 297dadd84958fa3cc461]." — `/workspace/swebok-v4/root/Foundations of Mathematics and Computational Systems/Numerical Methods, Algebra, and Calculus Foundations/Numerical Precision and Error Measurement/Precision, Absolute Error, and Relative Error.md`)

### 3. Understand what relative error tells you: it directly encodes the number of trustworthy leading digits (significant digits)

The connection between relative error and significant digits is given by a precise criterion: a computed value x\* has **k significant decimal digits** if and only if its relative error satisfies:

> **relative error < 5 × 10^(−k−1)**

So a relative error of 10⁻⁶ implies about 6 significant digits; a relative error of 0.1 implies only 1. Setting your acceptance threshold in terms of relative error therefore directly controls how many leading digits of the result you are demanding to be correct.

### 5. Distinguish accuracy (closeness to truth) from precision (closeness of repeated results to each other), and test for both

A test oracle must check the right thing. The SWEBOK separates two related but distinct concepts:

> "**[SWEBOK excerpt 66d0e01675409706ba9d]."

Relative error measures *accuracy*. A test that only checks repeatability (precision) can pass while the result is systematically wrong. Set your relative-error threshold to enforce accuracy; use separate regression or statistical tests to enforce precision.

(source: "[SWEBOK excerpt b586fdd39148fb34c49b]." — `/workspace/swebok-v4/root/Foundations of Mathematics and Computational Systems/Numerical Methods, Algebra, and Calculus Foundations/Numerical Precision and Error Measurement/Fixed-Point Arithmetic and Numerical Precision.md`)

### 6. Handle the zero-expected-value case explicitly, since relative error is undefined there

The relative error formula requires |x| ≠ 0. The SWEBOK notes this directly:

When the expected value is zero (or extremely close to zero), fall back to an absolute tolerance carefully chosen to match the problem's natural scale of "small," or reformulate the test to compare a quantity that is not expected to vanish.

### 7. Calibrate your threshold to the number of significant digits the instrument or algorithm can reliably produce

Instrument-level reasoning applies equally to algorithms. The SWEBOK illustrates with physical measurement:

> "[SWEBOK excerpt 33dfdbab98d77497865a]."

Analogously, choose your relative-error threshold by first determining how many significant digits your numerical algorithm is capable of delivering — which depends on the algorithm, the floating-point format, and accumulated rounding — and then set the threshold at 5 × 10^(−k−1) for that k. Requiring more digits than the algorithm can produce will cause correct implementations to fail; requiring fewer will accept implementations that have lost significant accuracy.

### Question

Each new version of our web service is switched on for every user at the same moment, so a single faulty version breaks the service for everyone and getting the previous version back takes hours. How should we change the way new versions go live to limit the damage?

Answer with a list of guidelines. After each guideline, cite the source it comes from: the path of the SWEBOK file if you have it, otherwise a verbatim quote of at least 8 words from the passage, in the form (source: ...).

### Answer

# Summary
SWEBOK v4 describes two complementary families of release strategy — **environment-based** (staging → canary → full production) and **application-based** (feature toggles) — that together prevent a single faulty version from hitting all users at once. Both families must be paired with pre-rehearsed automated rollback, real-time telemetry, and continuous testing so that any problem is detected and reversed before most users are affected. Architecturing the service for small, independent deployments further limits the blast radius of any individual change.

# Guidelines

- **Separate deployment from release; use staging environments.** Deploy to a staging environment first, then release to users — and only to a segment initially. *(source: root/Software Testing, Operations, and Maintenance/Software Operations and Maintenance Practices/Software Release Engineering Strategies and Risk Reduction.md — "[SWEBOK excerpt 6fe13e7ec6ed2a93731e]")*

- **Use feature toggles to enable/disable a feature without redeployment.** "[SWEBOK excerpt 9c21d13d05f424c62b59] using configuration parameters." *(source: root/Software Testing, Operations, and Maintenance/Software Operations and Maintenance Practices/Software Release Engineering Strategies and Risk Reduction.md)*

- **Plan, rehearse, and automate rollback before every deployment.** "[SWEBOK excerpt 483bf175d51095feb36a] [SWEBOK excerpt 38f6b8d3f384481e85f9]." *(source: root/Software Testing, Operations, and Maintenance/Software Operations and Maintenance Practices/Software Rollback and Problem Resolution in DevOps.md)*

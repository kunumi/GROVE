### Question

How should modules be organized so that the software stays easy to maintain, and how can an existing badly structured program be improved without its users noticing any difference?

Answer with a list of guidelines. After each guideline, cite the source it comes from: the path of the SWEBOK file if you have it, otherwise a verbatim quote of at least 8 words from the passage, in the form (source: ...).

### Answer

# Summary
Modules should be organized by assigning each a **single responsibility**, maximizing **cohesion** within them, minimizing **coupling** between them, hiding internal details through **encapsulation and information hiding**, and separating public interfaces from implementation. When a badly structured program needs to be fixed without users noticing any difference, the SWEBOK prescribes **refactoring** — a technique that reorganizes a program's internal structure and improves maintainability *without* changing observable behavior — applied continuously or during maintenance to reduce technical debt and manage growing complexity.

# Guidelines

**Module organization for maintainability:**

- **Give each module a single responsibility.** David Parnas advocated that each module should have a single responsibility; smaller components are easier to understand and to maintain. - **Enforce uniformity (consistency) across [SWEBOK excerpt 13f265ec2d68fa86e961] across all modules. (source: root/…/Software Design Principles and Module Organization.md)

**Improving a badly structured program without users noticing:**

- **Use refactoring — it reorganizes without changing behavior.** [SWEBOK excerpt 7d0735930d47d881cda0]; it [SWEBOK excerpt 0161807d4792ef7ea391]. (source: root/Software Maintenance and Configuration Management/Software Maintenance, Evolution, and Quality Assurance/Refactoring and Reverse Engineering in Software Development.md)

- **Apply refactoring continuously to reduce technical debt.** [SWEBOK excerpt eae28a0a9cb9faeee45e] Agile/CI contexts, continuous refactoring reduces and manages growing complexity while improving developer productivity. (source: root/…/Refactoring and Reverse Engineering in Software Development.md)

- **Use reverse engineering first to understand what exists.** [SWEBOK excerpt 5546342697a52ad83cea], creating representations at higher levels of abstraction — a prerequisite for safe restructuring. (source: root/…/Refactoring and Reverse Engineering in Software Development.md)

When no user-visible change is acceptable, refactoring (not reengineering) is the appropriate technique. (source: root/…/Software Reengineering and Legacy System Modernization.md)

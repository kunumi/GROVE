### Question

How should test inputs be chosen for a function that accepts numeric values within a valid range?

Answer with a list of guidelines. After each guideline, cite the source it comes from: the path of the SWEBOK file if you have it, otherwise a verbatim quote of at least 8 words from the passage, in the form (source: ...).

### Answer

# Summary
When testing a function that accepts numeric values within a valid range, SWEBOK v4 recommends a layered approach: partition the input space into equivalence classes (valid and invalid), select at least one representative from each class, place specific test cases at and near the boundary values of the range (since faults cluster there), and also test values *outside* the range for robustness. Exception-forcing, random, and combinatorial techniques serve as useful complements.

# Guidelines

- **Use Equivalence Partitioning** – Divide the input domain into classes of valid and invalid values and pick at least one representative test case from each class. (source: `root/Software Testing Methodologies and Techniques/Software Testing Approaches and Techniques/Classification and Specification-Based Testing Techniques.md`, Section 3.1.1 — *"[SWEBOK excerpt 29ab9da822777302a58c]… on [SWEBOK excerpt 59388fdf8b5ff22a4425]."*)

- **Test Out-of-Range Values as a Distinct Class** – Values outside the valid range form their own equivalence class and should trigger error messages or error processing; include at least one representative. (source: `root/Software Testing Methodologies and Techniques/Boundary Value Analysis and Syntax Testing Techniques.md` — *"[SWEBOK excerpt c3d87fbc75fe24a6c7d5]."*)

- **Apply Boundary Value Analysis** – Select test cases on or near the extreme values of the valid range, because many faults concentrate there. (source: `root/Software Testing Methodologies and Techniques/Boundary Value Analysis and Syntax Testing Techniques.md` — *"[SWEBOK excerpt bedee61fb08d8b967278]."*)

- **Extend to Robustness Testing** – Also choose inputs outside the valid domain to verify the function handles erroneous numeric inputs gracefully. (source: same file — *"[SWEBOK excerpt ac52d3263555a546a515]."*)

- **Force Exception Cases (Overflow, Underflow, etc.)** – Design negative test cases that deliberately trigger numeric exceptions such as overflow and underflow. (source: `root/Testing Methodologies and Quality Assurance Practices/Testing Approaches and Execution Strategies/Software Testing Techniques and Methodologies/Exception Testing and Error Handling in Software Testing.md`, Section 3.1.11 — *"[SWEBOK excerpt 9fd7577d0e793eb2d33d]."*)

- **Use Random Testing Within the Known Domain** – Draw random inputs from the defined valid range as a supplementary automation-friendly technique; the input domain must be defined first. (source: `root/Testing Methodologies and Quality Assurance Practices/…/Random Testing and Evidence-Based Software Engineering Approaches.md` — *"[SWEBOK excerpt c56431c507c9cda26dd8]."*)

- **Combine Specification-Based and Structure-Based Selection** – Black-box (equivalence/boundary) and white-box techniques are complements that highlight different problems; combine them subject to budget constraints. (source: `root/Testing Methodologies and Quality Assurance Practices/…/Combining Functional and Structural Testing Techniques.md` — *"[SWEBOK excerpt acb96392a12a260360f2]."*)

- **Apply Combinatorial Techniques for Multi-Parameter Functions** – When the function has several numeric parameters or conditions, use All-Combinations, Pair-Wise, Each-Choice, or Base-Choice testing to systematically cover parameter value combinations. (source: `root/Software Testing Methodologies and Techniques/Combinatorial Test Techniques Overview.md`, Section 3.1.[SWEBOK excerpt dbc7460be072180dacda]."*)

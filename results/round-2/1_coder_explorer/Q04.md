### Question

Which strategies let software keep working when errors occur at runtime instead of failing?

Answer with a list of guidelines. After each guideline, cite the source it comes from: the path of the SWEBOK file if you have it, otherwise a verbatim quote of at least 8 words from the passage, in the form (source: ...).

### Answer

# Summary
SWEBOK v4 describes runtime error resilience through three overlapping areas: **fault tolerance techniques** (detect errors then recover or contain them), **error-handling techniques** (return neutral values, substitute valid data, log warnings, return error codes), and **exception handling** (try-catch blocks with carefully designed policies). Defensive programming—validating inputs and using assertions—provides a preventive foundation that reduces the chance of unhandled failures reaching production.

# Guidelines
- **Fault tolerance = detect + recover or contain.** Software reliability is increased [SWEBOK excerpt c50d13221cc1a3d4061e] when full recovery is not possible. (source: `root/Software Construction Techniques and Practices/Fault Tolerance Techniques and Executable Models.md` — *"[SWEBOK excerpt 909de8a0fa8186bde761]."*)

- **Back up and retry.** On error, roll back to a safe state and attempt the operation again. (source: `root/Software Construction Techniques and Practices/Fault Tolerance Techniques and Executable Models.md` — *"[SWEBOK excerpt 781020248b1325e999a5]…"*)

- **Use auxiliary code and voting algorithms.** Run redundant code paths and vote on results to mask errors in one path. (source: `root/Software Construction Techniques and Practices/Fault Tolerance Techniques and Executable Models.md` — *"…using auxiliary code and voting algorithms…"*)

- **Replace an erroneous value with a benign phony value.** When a value is bad but processing can safely continue with a placeholder, use one. (source: `root/Software Construction Techniques and Practices/Fault Tolerance Techniques and Executable Models.md` — *"…[SWEBOK excerpt 8b0b1372e25e459ce254]."*)

- **Substitute the next piece of valid data.** Skip bad data and continue with the next valid item rather than halting. (source: `root/Software Construction Techniques and Practices/Contract Design and Error Handling Strategies/Error Handling, Exception Handling, and Fault Tolerance.md` — *"…substituting the next piece of valid data…"*)

- **Log a warning and keep running.** Record the problem and continue execution instead of terminating. (source: `root/Software Construction Techniques and Practices/Contract Design and Error Handling Strategies/Error Handling, Exception Handling, and Fault Tolerance.md` — *"…logging a warning message…"*)

- **Return an error code.** Signal the error to the caller without crashing, letting the caller decide how to respond. (source: `root/Software Construction Techniques and Practices/Contract Design and Error Handling Strategies/Error Handling, Exception Handling, and Fault Tolerance.md` — *"…returning an error code…"*)

- **Use try-catch exception blocks.** Throw detected exceptions and catch them in a try-catch block that either corrects the erroneous condition or returns control gracefully to the caller. (source: `root/Software Construction Techniques and Practices/Contract Design and Error Handling Strategies/Error Handling, Exception Handling, and Fault Tolerance.md` — *"The try-catch [SWEBOK excerpt 980c1713bcc05a3281c2]."*)

- **Follow sound exception-design policies.** Include full context in exception messages, avoid empty catch blocks, know what library exceptions may be thrown, build a centralized exception reporter, and standardize exception use. (source: `root/Software Construction Techniques and Practices/Contract Design and Error Handling Strategies/Error Handling, Exception Handling, and Fault Tolerance.md`)

- **Defensive programming: validate all inputs.** Check all input parameter values and decide explicitly how to handle bad inputs before they cause downstream failures. (source: `root/Software Construction Techniques and Practices/Contract Design and Error Handling Strategies/Design by Contract and Defensive Programming.md` — *"[SWEBOK excerpt fe09ccfb26565a8b97e8]."*)

- **Use assertions to catch error conditions early.** Assertions detect invalid states before they escalate. (source: `root/Software Construction Techniques and Practices/Contract Design and Error Handling Strategies/Error Handling, Exception Handling, and Fault Tolerance.md` and `Design by Contract and Defensive Programming.md`)

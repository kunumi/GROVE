### Question

A feature request I have to implement is written as loose prose, and the product owner and I keep reading it differently. How should the team pin down, together with the domain experts and before any code is written, what the feature must do, so that it cannot be misread?

Answer with a list of guidelines. After each guideline, cite the source it comes from: the path of the SWEBOK file if you have it, otherwise a verbatim quote of at least 8 words from the passage, in the form (source: ...).

### Answer

# Summary
Before writing a single line of code, the team should elicit the true underlying need through facilitated workshops (JAD/JRP) and interviews with domain experts, then rewrite the feature as a structured, unambiguous, testable, atomic requirement using stakeholder vocabulary. The resulting specification must be validated through multi-perspective reviews, concrete ATDD acceptance-test sessions (engineers + domain experts + QA agree on pass/fail criteria together), and prototypes that expose any remaining interpretation gaps.

# Guidelines

- **Run facilitated workshops (JAD/JRP) with domain experts.** These are specifically listed as a primary elicitation technique for surfacing tacit knowledge that prose descriptions miss. (source: `root/Software Requirements_ Foundations and Engineering Practices/Requirements Engineering_ Elicitation, Analysis, and Specification/Stakeholder Identification and Requirements Elicitation Techniques/Stakeholder Elicitation Techniques and Requirements Sources.md`)

- **Treat elicitation as an active, not passive, activity.** Users often leave important information unstated, so the engineer must work to uncover it. "Elicitation can be difficult … [SWEBOK excerpt 65d2a845eca5d1fed2ce]." (source: same file as above)

- **Apply the "5 Whys" to find the true underlying need, not the stated solution.** "The 5-whys technique [SWEBOK excerpt 716db07833277b41892e].'" (source: `root/Software Requirements_ Foundations and Engineering Practices/Requirements Engineering_ Elicitation, Analysis, and Specification/Requirements Analysis and Refinement/Software Requirements Properties and Quality Criteria.md`)

- **Rewrite the feature so each requirement is unambiguous, testable, atomic, and in stakeholder vocabulary.** "[SWEBOK excerpt 5f4e46e368e62fb60ea9]) … atomic, represent a single decision; [SWEBOK excerpt 825d8b93845096610f26]." (source: same file as above)

- **Replace loose prose with structured natural language (actor-action format).** "[SWEBOK excerpt 4eecb83f896611f6153d]." (source: `root/Software Requirements_ Foundations and Engineering Practices/Requirements Engineering_ Elicitation, Analysis, and Specification/Requirements Specification and Validation Techniques/Natural Language Requirements Specifications/Structured Natural Language Requirements Specification.md`)

- **Or use modelling languages (UML/SysML) to eliminate natural-language ambiguity entirely.** "[SWEBOK excerpt de89cafd3060d0444838] … UML or SysML … [SWEBOK excerpt 7d29ff7c02d49b7d2b6c]." (source: `root/Software Requirements_ Foundations and Engineering Practices/Requirements Engineering_ Elicitation, Analysis, and Specification/Model-Based Requirements Specification Approaches.md`)

- **Hold multi-perspective requirements reviews before coding starts.** Clients verify their needs are captured; requirements engineers verify clarity; architecture/construction engineers verify the spec is sufficient to build from. Checklists or a "definition of done" can guide reviewers. (source: `root/Requirements Validation and Management/Requirements Validation Methods and Techniques.md`)

- **Define concrete acceptance test cases together with domain experts before any production code is written (ATDD).** "[SWEBOK excerpt cd5cc3b984affe631643] [SWEBOK excerpt acf2737e4c17b2e47a7b]." (source: `root/Software Requirements_ Foundations and Engineering Practices/Requirements Engineering_ Elicitation, Analysis, and Specification/Requirements Specification and Validation Techniques/Test-Driven Development and Acceptance Testing/Acceptance Criteria-Based Requirements Specification.md`)

- **Build a prototype to expose interpretation gaps when the spec is still not concrete enough.** "[SWEBOK excerpt 78d5d553044949c2fea4]." (source: `root/Requirements Validation and Management/Prototyping for Requirements Validation and Feedback.md`)

- **"Execute" or simulate the specification with demonstration scenarios to convince stakeholders it matches reality.** "[SWEBOK excerpt 25555d1d7a1f36132af3]." (source: `root/Requirements Validation and Management/Requirements Validation Methods and Techniques.md`)

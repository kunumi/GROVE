### Question

A customer reports a defect in the executable we shipped to them two years ago, and to investigate it we need that very same executable back, byte for byte, but the toolchain and third-party libraries on our machines have been upgraded since then. What should the team have been tracking and preserving so that this would be possible?

Answer with a list of guidelines. After each guideline, cite the source it comes from: the path of the SWEBOK file if you have it, otherwise a verbatim quote of at least 8 words from the passage, in the form (source: ...).

### Answer

# Summary
SWEBOK v4 addresses this scenario directly under Software Configuration Management (SCM). The core principle is that **every ingredient of a build** — source code, build tools (compiler, linker), third-party libraries, build scripts, and the resulting binary — must be versioned and preserved, so that any prior release can be reconstructed or retrieved intact. A Version Description Document (VDD) and a Software Bill of Materials (SBOM) record exactly what went into each release, while integrity hashes confirm a rebuild matches the original byte for byte.

# Guidelines

- **Put all SCIs under SCM control, including tools, libraries, and build scripts** — not just application source code. (source: `root/Software Maintenance and Configuration Management/…/Software Configuration Items Selection and Change Recording.md` — *"[SWEBOK excerpt d2186235c2091b5dd3f8]… [SWEBOK excerpt bf61efa8c0b44eda2d73]…"*)

- **Keep the build tools themselves versioned in SCM** so the original compiler and linker can be recovered. (source: `root/…/Software Build Tools and Version Control Management.md` — *"[SWEBOK excerpt 0cc888849d9b8d18bc91]"*)

- **Maintain a source-code repository that can restore any prior baseline.** (source: `root/…/Source Code Version Control and Management.md` — *"[SWEBOK excerpt 4e6d9f4b27452717761a]"*)

- **Version-control the build instructions** (Makefiles, pipeline scripts) so the exact build sequence from two years ago can be replayed. (source: `root/…/In-Process Audits and Software Release Management.md` — *"[SWEBOK excerpt fc32d136512cdcba6f40]"*)

- **Store released binaries in an artifact repository** for direct retrieval without needing a rebuild. (source: `root/…/Configuration Management System Tools and Components.md` — *"[SWEBOK excerpt 575c7cbd8fa66b84e62b]"*)

- **Produce a Version Description Document (VDD)** recording the exact contents of every release. (source: `root/…/Software Release Management and Deployment Processes.md` — *"[SWEBOK excerpt 1bc7457ba6b688fca089])"*)

- **Capture a Software Bill of Materials (SBOM)** at build time as a formal CM output. (source: `root/…/Software Build Artifacts and Continuous Integration Processes.md` — *"[SWEBOK excerpt 450578f233490c4cd9fa]"*)

- **Record integrity hashes (SHA1, MD5, MAC) for released binaries** to verify any future rebuild matches the original byte for byte. (source: `root/…/Software Configuration Status Reporting and Auditing.md` — *"Indicators of integrity (e.g., MAC… SHA1… MD5)"*)

- **Retain build outputs as formal records** of quality, security, or compliance — do not discard executables after delivery. (source: `root/…/Build Process Quality Verification and Documentation.md` — *"[SWEBOK excerpt 6a32af9e0cbf05b3a8b0]"*)

- **Deploy a full CMS** integrating version control, build automation pipeline, artifact repository, and a CMDB. (source: `root/…/Configuration Management System Tools and Components.md` — *"[SWEBOK excerpt 4421921f0c187fccf6af]"*)

# Gaps
- Containerization / VM snapshots as a technique for freezing the full build environment are not addressed in the BoK content read.
- "Reproducible builds" as a formal discipline (bit-for-bit determinism via techniques like source-date epoch normalization) is not found in the BoK.

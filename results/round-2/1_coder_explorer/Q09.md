### Question

What general practices should developers follow when writing code so that attackers cannot exploit it?

Answer with a list of guidelines. After each guideline, cite the source it comes from: the path of the SWEBOK file if you have it, otherwise a verbatim quote of at least 8 words from the passage, in the form (source: ...).

### Answer

# Summary
The SWEBOK v4 draws primarily on the CERT/CC Top 10 Software Security Practices and on specific construction-level rules to describe what developers must do to write unexploitable code. The guidance spans input handling, design decisions, privilege management, memory discipline, error handling, and process standards. No single technique is sufficient; the BoK stresses that security must be layered and built in from the start.

# Guidelines

1. **Validate input.** Every piece of input entering the system must be validated before use. (source: `root/Software Security Engineering and Professional Practice/Secure Software Development Standards and Practices/Top 10 Software Security Practices.md` — "[SWEBOK excerpt 69139d7a46fd76c706bd].** Compiler warnings frequently point to constructs that can be exploited. (source: `root/…/Security Best Practices and Design Principles.md` — "[SWEBOK excerpt eec980c3e0a1869670af].** Security must be an architectural concern, not an afterthought. (source: `root/…/Security Best Practices and Design Principles.md` — "[SWEBOK excerpt 591b2c3470c06df16dc3].** Complexity enlarges the attack surface. (source: `root/…/Security Best Practices and Design Principles.md` — "4. Keep it simple.")

5. **Default deny.** Permissions should be denied unless explicitly granted. (source: `root/…/Security Best Practices and Design Principles.md` — "[SWEBOK excerpt 4554a3a3f276577c9e76] — and isolate privileged code into small modules.** Code should run with the minimum necessary privileges; privileged sections should be isolated into modules "as small as possible" that perform only the tasks requiring those privileges. (source: `root/…/Security Best Practices for Software Development.md`; `root/…/Software Construction Security and Privilege Management.md`; `root/…/Secure Module Design and Error Handling Principles.md`)

7. **Sanitize data sent to other software.** Data passed to other components or systems must be sanitized to prevent injection attacks. (source: `root/…/Security Best Practices for Software Development.md` — "[SWEBOK excerpt bbcc5e75771c824f8488].** Layer multiple security controls so that the failure of one does not compromise the whole system. (source: `root/…/Software Security Best Practices.md` — "[SWEBOK excerpt 51b07806bf3125ce9ca4].** Code reviews, testing, and static analysis should be applied to find and remove security defects. (source: `root/…/Software Security Best Practices.md` — "[SWEBOK excerpt d7d93aaeeff05b1e91b1] security standard.** Follow a recognized construction security standard throughout development. (source: `root/…/Software Security Best Practices.md` — "Adopt a software construction security standard.")

11. **Validate all program assumptions; document those that cannot be validated.** Attackers will attempt to invalidate undocumented assumptions. (source: `root/…/Secure Module Design and Error Handling Principles.md` — "[SWEBOK excerpt f87e4e54fe032ae150bd]…document them…[SWEBOK excerpt afef4203cb9fecb75b2b].")

12. **Do not share memory objects with other programs.** Shared memory creates opportunities for unauthorized access or tampering. (source: `root/…/Secure Module Design and Error Handling Principles.md` — "[SWEBOK excerpt 0bf95a5064c99a220208].")

13. **Check every function's error status; restore state and terminate on security-affecting errors.** Do not attempt recovery when an error's cause or effects touch security considerations. (source: `root/…/Secure Module Design and Error Handling Principles.md` — "[SWEBOK excerpt baa72cb3c280f453b32e].")

14. **Conduct threat modeling during design.** Model how the system could be attacked to derive concrete mitigations and implementation steps. (source: `root/…/Cryptographic Controls and Secure Software Construction.md` — "[SWEBOK excerpt a7a8d4fb460cb808b710].")

15. **Carefully select and manage cryptographic algorithms and key material.** It is important to carefully select algorithms and to manage how key material is created, distributed, and managed. (source: `root/…/Cryptographic Controls and Secure Software Construction.md` — "[SWEBOK excerpt f9a8a970d6c3ff97ed6c].")

## Guidelines for Making a Routine's Assumptions Explicit and Guarding Against Invalid Input

### 1. Define Preconditions for the Routine
Specify the conditions that must hold *before* the routine executes. This makes input assumptions explicit: if callers violate them, the routine's correct behavior cannot be guaranteed.

> (source: "[SWEBOK excerpt f6221f8cc5539f7cb39e].")

---

### 2. Define Postconditions for the Routine
Specify what the routine *guarantees* to be true after it executes successfully. This documents output assumptions — including how parameters, data values, and return values will be affected.

> (source: "[SWEBOK excerpt 89a519aa5f387772eaf7].")

---

### 3. Identify and Document Invariants
Document any conditions in the operational environment that must remain unchanged both before and after the routine runs. This bounds the routine's behavioral contract even further.

> (source: "[SWEBOK excerpt 7caeb5a71ab6d4912de8].")

---

### 4. Apply Design by Contract
Use preconditions and postconditions together so that the routine forms a *contract* with its callers. This contract precisely specifies the routine's semantics, clarifies expected behavior, and is considered to improve the quality of software construction.

> (source: "[SWEBOK excerpt 0b7264f99dd70678ccd5].")

---

### 5. Use Assertions to Make Runtime Checks
Place assertions — executable predicates — inside the routine to actively verify assumptions at runtime. Assertions are especially valuable for flushing out mismatched interface assumptions and errors introduced by code changes, and they can be compiled out later to avoid degrading performance.

> (source: "[SWEBOK excerpt fec0cf86c0fed93674bf].")

---

### 6. Practice Defensive Programming
Explicitly check the values of all input parameters and decide how to handle bad inputs rather than assuming callers will always pass valid data. Assertions are a common tool for this defensive input checking.

> (source: "[SWEBOK excerpt 798f1f64b64a6bf2581f].")

---

### 7. Handle Errors and Exceptions Explicitly
Decide how the routine will respond when bad inputs or unexpected conditions are encountered. Options include returning a neutral value, substituting valid data, logging a warning, returning an error code, raising an exception, or shutting down — all of which affect the routine's correctness and robustness.

> (source: "[SWEBOK excerpt 25fb1a8cce8efbace92b].")
> (source: "[SWEBOK excerpt 5cbc324f523e1430b28c].")

---

### 8. Validate Input as a Security Practice
Input validation is not just a correctness concern — it is the top recommended security practice. Any assumptions in the program should be validated; if they cannot be, they must at least be documented so maintainers know what attackers may try to exploit.

> (source: "[SWEBOK excerpt 0bcf94be1b9045b82f4d].")
> (source: CERT/CC top 10 software security practices, item 1: "Validate input.")

---

### 9. Use Logical Inference to Prove Preconditions and Postconditions Hold
For higher assurance, use mathematical logic to prove that preconditions and postconditions hold under all possible inputs, allowing prediction of routine behavior without execution.

> (source: "[SWEBOK excerpt fdc3225ff3753d719a07].")

## Guidelines for Deciding What to Retest After a Change

### 1. Perform Impact Analysis Before Testing Begins
Before deciding what to test, the team should conduct an **impact analysis** that identifies all systems, software products, and components that would be affected by the change. This analysis also determines the risks involved. It [SWEBOK excerpt c73f208725d275e97d2a]*.

> (source: "[SWEBOK excerpt 74c999a79f8d955618a3].")

---

### 2. Use Requirements Tracing to Identify Affected Test Cases
The team should trace the changed requirement forward to design elements, code units, and then to their linked test cases. This "footprint" reveals exactly which tests are relevant to rerun, without retesting everything.

> (source: "[SWEBOK excerpt 871601aa48ef8c64ec8f].")

---

### 3. Apply Selective Regression Testing — Not Full Retesting
Regression testing should be *selective*: rather than rerunning the entire test suite, the team should choose the subset of tests that verifies modified areas [SWEBOK excerpt ca5c7931073c416b85a4] system still complies with its requirements. Full retesting is costly and usually impractical.

> (source: "[SWEBOK excerpt a4172e7d00f813db1158] [SWEBOK excerpt 80ff0a3f10d7d6b89748].")

---

### 4. Use Test Case Selection and Minimization to Reduce Redundancy
When choosing which tests to run, the team should apply **test case selection** (reducing cardinality while maintaining coverage or fault-detection effectiveness) and **minimization** (removing redundant test cases), so that the regression suite is as lean as possible without sacrificing quality.

> (source: "[SWEBOK excerpt 000de4403a642a182b3f].")

> (source: "[SWEBOK excerpt bf8af63c65e6f2a8be74].")

---

### 5. Prioritize Tests to Maximize Early Fault Detection
When resources or time are limited, the team should prioritize test cases to run those most likely to find faults first — increasing the rate of fault detection, code coverage, and system reliability. Prioritization can be based on heuristics such as coverage, fault detection rate, similarity, or risk.

> (source: "[SWEBOK excerpt 3e32889b1d11770ab3a7].")

---

### 6. Use the Severity of the Change/Problem Report to Guide Timing and Scope
The seriousness of the change (e.g., the severity of a problem report) should guide *when* and *how much* to test. More severe problems warrant more urgent and extensive testing.

> (source: "[SWEBOK excerpt 85d2de38be7e1ce15004].")

---

### 7. Cover All Test Levels Touched by the Change — Including Non-Functional Properties
Regression testing should be conducted at the appropriate test level(s) — unit, integration, system — depending on what was changed. It may also need to cover non-functional properties such as reliability, usability, security, and compatibility, not just functional behavior.

> (source: "[SWEBOK excerpt c20fe17691f9be60afb3].")

---

### 8. Run Smoke Tests First to Verify Testability Before Full Regression
In continuous integration workflows, the team should first run a **smoke test** (also called Build Verification Testing) to confirm the system's core functionality is operational and the SUT is testable at all — before committing to a full regression run.

> (source: "[SWEBOK excerpt f31796b4ea494f728386]).")

---

### 9. Perform Regression Testing After Integration and Before Deployment
The correct **point in the process** to conduct regression testing is *[SWEBOK excerpt 4902cc47387cdc1bd20b]*.

> (source: "[SWEBOK excerpt 1e9a2a9f2f8473c3d4f5].")

---

### 10. In CI/DevOps Contexts, Perform Regression Testing Continuously
In automated build and continuous integration environments, regression testing should be performed continuously — at every integration — to detect development and integration issues as early as possible.

> (source: "[SWEBOK excerpt ac0529e0e5474345da84].")

---

### 11. Keep Test Artifacts Updated to Reflect Changes to Requirements or Design
The team should maintain test reusability repositories so that changes to requirements or design are reflected in corresponding changes to test cases. Outdated tests that no longer correspond to the system's design should be updated.

> (source: "[SWEBOK excerpt cc60c8d6f727f372cb4a].")

---

### 12. Plan Testing Activities as Part of Change (MR/PR) Processing
Test planning for a given change should happen during the processing of the modification request (MR) or problem report (PR) itself — not as an afterthought. The maintainer should plan and execute the appropriate tests as part of validating each change.

> (source: "[SWEBOK excerpt cc2b48d871fb8e63b720].")

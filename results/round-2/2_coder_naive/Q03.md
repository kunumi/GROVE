## Principles and Guidelines for Signaling and Handling Abnormal Conditions

### I. General Principle: Error Handling Affects Core Quality Attributes

1. **Recognize that error handling directly impacts correctness, robustness, and other nonfunctional attributes.** How errors are designed to be handled must be a deliberate architectural and construction concern, not an afterthought.
   > (source: *"[SWEBOK excerpt 5cbc324f523e1430b28c]."*)

---

### II. Principles for Defensive Programming (Prevention Before Signaling)

2. **Protect every routine from being broken by invalid inputs.** Defensive programming requires checking the values of all input parameters and deciding in advance how bad inputs will be handled.
   > (source: *"[SWEBOK excerpt edaaca9c62404676ff9e]."*)

3. **Use assertions to check input values and detect errors early.** Assertions are executable predicates — especially valuable in high-reliability programs — that help flush out mismatched interface assumptions and errors introduced during code modification. They are compiled in during development and compiled out later to avoid performance degradation.
   > (source: *"[SWEBOK excerpt fec0cf86c0fed93674bf]."*)

4. **Apply Design by Contract: define preconditions and postconditions for every [SWEBOK excerpt 875020a44db176882c71] forms [SWEBOK excerpt d0657a9a29ea4d75a517] the routine and helps clarify its behavior, which is thought to improve software construction quality.
   > (source: *"[SWEBOK excerpt 0b7264f99dd70678ccd5]."*)

---

### III. Principles for Exception-Handling Policy Design

5. **Include [SWEBOK excerpt e56492e15b911c91a518].** When an exception is thrown, the message must carry enough diagnostic context for the problem to be understood.
   > (source: *"[SWEBOK excerpt 0d697d30c739c912a46e]…"*)

6. **Avoid empty catch blocks.** An exception caught and silently swallowed provides no opportunity for diagnosis or recovery, defeating the purpose of exception handling.
   > (source: *"…avoiding empty catch blocks…"*)

7. **Know the exceptions that library code throws.** A routine that calls third-party or library code must be aware of what exceptions that code can raise, so it can handle or propagate them appropriately.
   > (source: *"…knowing the exceptions the library code throws…"*)

8. **Consider building a centralized exception reporter.** Rather than handling exceptions ad hoc throughout the codebase, funneling them through a single reporter improves consistency and observability.
   > (source: *"…perhaps building a centralized exception reporter…"*)

9. **Standardize the program's use of exceptions.** Consistency in how exceptions are defined, thrown, and caught across the codebase reduces confusion and integration errors.
   > (source: *"…[SWEBOK excerpt 8fa6040b09c8e3f29c47]."*)

### IV. Alternatives for Handling Errors (Beyond Exceptions)

10. **Return a neutral/default value.** When an operation fails, returning a benign default can allow the program to continue operating without signaling an error — suitable when the caller can proceed safely.
    > (source: *"[SWEBOK excerpt 25fb1a8cce8efbace92b]."*)

11. **Substitute the next piece of valid data.** In stream- or data-processing contexts, skipping bad data and continuing with the next valid item can be an appropriate recovery approach.
    > (source: *"[SWEBOK excerpt 4088ee743c5a537d6f1c]…"*)

12. **Log a warning message.** Recording the abnormal condition without halting execution allows the system to continue while creating a record for later diagnosis.
    > (source: *"…[SWEBOK excerpt 305dc26a0749f10ebc82]."*)

13. **Return an error code.** The classic approach of returning a sentinel error value lets the caller decide how to respond, keeping error propagation explicit.
    > (source: *"…[SWEBOK excerpt 4d0cf1b4e05e4515f7b0]."*)

14. **Shut down the software.** When the error is severe enough that continuing would cause greater harm (e.g., corrupted state, security risk), controlled shutdown is a valid and sometimes preferable response.
    > (source: *"…[SWEBOK excerpt 4d0cf1b4e05e4515f7b0]."*)

---

### V. Fault Tolerance Strategies (When Errors Cannot Be Prevented)

15. **Back up and retry.** When a transient error occurs, retrying the operation after restoring a previous good state is a common fault-tolerance strategy.
    > (source: *"[SWEBOK excerpt 7c7c13df07628c3c7d07]."*)

16. **Use auxiliary code and voting algorithms.** Running redundant computations and selecting the most consistent result improves reliability in the presence of faults.
    > (source: *"…using auxiliary code and voting algorithms…"*)

17. **Replace [SWEBOK excerpt f660d205c9fd6b796539].** When a computed value is known to be invalid but the system must continue, substituting a safe placeholder prevents cascading failures.
    > (source: *"…[SWEBOK excerpt 8b0b1372e25e459ce254]."*)

18. **Design fault tolerance to either recover from errors or contain their effects when recovery is impossible.** The goal of fault tolerance overall is to increase software reliability — either restoring normal operation or at minimum limiting the damage.
    > (source: *"[SWEBOK excerpt 909de8a0fa8186bde761]."*)

---

### VI. Overarching Design Concern

19. **Treat error/exception handling and fault tolerance as a cross-cutting design concern.** This concern spans the entire system and [SWEBOK excerpt db5d2d4f04a03800a05f] — it must be addressed at all levels of design, not only in isolated routines.
    > (source: *"[SWEBOK excerpt b4ad34aaec8c0116191e]."*)

## Guidelines for Eliminating Ambiguity in a Feature Before Coding

### 1. Treat ambiguity as a first-class problem to be actively resolved
Recognise that the two primary requirements problems on real-world projects are **incompleteness** and **ambiguity** — the latter meaning [SWEBOK excerpt 887c3c0a319d2d295964]." Do not start coding until this is resolved.
(source: *"[SWEBOK excerpt 6bba11b28d752c35061f]"*)

---

### 2. Run a facilitated workshop with all relevant stakeholders
Use joint application development (JAD), joint requirements planning (JRP), or other facilitated workshops to bring the product owner, domain experts, developers, and other stakeholders together around the same table to agree on meaning.
(source: *"[SWEBOK excerpt f81e51be50747e02bf0e]"*)

---

### 3. Surface tacit knowledge — elicitation is not passive
Users may "[SWEBOK excerpt f5a59d5f95d22711b5d1]."
(source: *"[SWEBOK excerpt 11007c66078e017f31d4]"*)

---

### 4. Apply the 5-whys technique to reach the true problem
If the feature description looks like a proposed solution rather than a real need, repeatedly ask "Why is this the requirement?" until [SWEBOK excerpt d7d0175f8ce126234e03]." This prevents implementing a suboptimal solution.
(source: *"The 5-whys technique… [SWEBOK excerpt 20f776590023e6560f73]"*)

---

### 5. Make each requirement unambiguous, testable, and atomic
During analysis, check that each requirement: (a) is **unambiguous** (interpretable in only one way); (b) is **testable** (quantified, so compliance or non-compliance can be clearly demonstrated); and (c) is **atomic** (represents a single decision).
(source: *"[SWEBOK excerpt 3f9aa2c4f8f16bd73d76]; … atomic, represent a single decision"*)

---

### 6. Write requirements in stakeholder vocabulary, not technical jargon
Each requirement should "use stakeholder vocabulary" and "represent true, actual stakeholder needs" and "be acceptable to all stakeholders." Using the domain experts' own language reduces the chance that engineer and expert are talking about different things.
(source: *"[SWEBOK excerpt 70c6d682121f0181aaed]"*)

---

### 7. Switch from unstructured prose to structured natural language
Move away from loose prose to a **structured format** (actor-action, use-case template, etc.) whose goal is to "increase precision and conciseness." For example: triggering event → actor → action → condition/qualification.
(source: *"[SWEBOK excerpt 4eecb83f896611f6153d]"*)

---

### 8. Use ATDD/BDD scenarios to replace natural-language ambiguity with test-case language
Hold a pre-coding meeting — "[SWEBOK excerpt 4a56a58a5f63b0b12a2d] [SWEBOK excerpt 9c07189d7cc5cba63376]." Write scenarios in the BDD form *Given / When / Then*, because "[SWEBOK excerpt 1f4cdc1ed4b2cc8d57f8]."
(source: *"[SWEBOK excerpt 4a56a58a5f63b0b12a2d] [SWEBOK excerpt acf2737e4c17b2e47a7b]"*)

---

### 9. Cover boundary and exception cases in those scenarios
"[SWEBOK excerpt af60c2c4f2f9581370e9]." Explicitly enumerate edge cases (e.g., insufficient balance, disabled card) so the feature's boundaries are unambiguous, and the overall requirements set is "[SWEBOK excerpt b8010e9e221cc4cf004e]."
(source: *"[SWEBOK excerpt af60c2c4f2f9581370e9]"*)

---

### 10. Use models (UML, SysML) where text still leaves room for misreading
"[SWEBOK excerpt de89cafd3060d0444838]… UML or SysML… [SWEBOK excerpt f61a69a7e9b27dc1bfbb]." Generally, the more formal the model, the less ambiguous the specification.
(source: *"[SWEBOK excerpt ace220df203c699ad5ba])"*)

---

### 11. Validate by multi-perspective review before any code is written
Conduct a formal requirements review. Ask different reviewer types to inspect the document: (a) clients/customers/[SWEBOK excerpt 79c3ff577ffe31b72d1c]"; (b) requirements-specialist engineers check clarity; (c) developers [SWEBOK excerpt ac50871e7c29c199aa4f]." Provide checklists or a "definition of done" to focus reviewers.
(source: *"[SWEBOK excerpt bef2c4af833e7a6d301a]; … [SWEBOK excerpt 6280b4fe9f691ccb7e31]… [SWEBOK excerpt 3029ae1319171a4f6a92]"*)

---

### 12. Use a prototype to expose and correct misinterpretations
If the written specification still leaves uncertainty, build a low-fidelity prototype. "[SWEBOK excerpt 78d5d553044949c2fea4]." A prototype concretely demonstrates the engineer's interpretation of the requirements to domain experts.
(source: *"[SWEBOK excerpt 78d5d553044949c2fea4]"*)

---

Taken together, these guidelines move a feature from loose prose to a shared, unambiguous contract — through facilitation, structured writing, concrete scenarios, models, and review — all *before* a line of production code is written.

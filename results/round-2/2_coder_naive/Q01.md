## Guidelines for State-Based Test Case Derivation

### 1. Model the component as a Finite-State Machine (FSM)
Represent the system under test (SUT) using a finite-state machine that captures all defined states, triggering events, and transitions between states. This model becomes the foundation for all subsequent test case derivation.

> (source: "[SWEBOK excerpt 36107f469ad2e6d2b6e2]." — SWEBOK v4, Software Testing KA, §3.1.7)

---

### 2. Derive the test suite to cover states and transitions at a chosen coverage level
Once the FSM model is built, design test cases that systematically exercise states and transitions according to the specific coverage criterion you need to satisfy (e.g., all-states coverage, all-transitions coverage).

> (source: "In this case, the test [SWEBOK excerpt 1e051e7dde1a64e3a5e8]." — SWEBOK v4, Software Testing KA, §3.1.7)

---

### 3. Generate positive test cases for every defined transition
For every valid (state, event) pair that produces a defined transition in the model, create at least one positive test case that exercises that transition and verifies the correct resulting state and output.

> (source: "[SWEBOK excerpt f2d8a55feb05b9720395]." — SWEBOK v4, Software Requirements KA, §8.3)

---

### 4. Generate negative test cases from undefined (state, event) combinations
Test cases should also [SWEBOK excerpt 7d59abf64ce333407230] are *not* defined in the model — i.e., events that should be rejected or ignored in a given state — to verify that the component handles invalid inputs correctly.

> (source: "[SWEBOK excerpt 24bcfcac1d9464c98f15]." — SWEBOK v4, Software Requirements KA, §8.3)

---

### 5. Account for the SUT's current state when specifying test inputs
Do not rely on input values alone to specify test cases, because the SUT may react to the same input differently depending on its current state. Each test case must therefore specify the initial state as part of its precondition.

> (source: "[SWEBOK excerpt 8eb37559ff90e8481254]." — SWEBOK v4, Software Testing KA, §5-2)

---

### 6. Include expected state changes (not just output values) in the test oracle
The expected outcomes of a test case for a stateful component must include state changes and output messages, not only produced values, so the oracle can fully verify the transition.

> (source: "…[SWEBOK excerpt 4f8921daa6bb16f56441])." — SWEBOK v4, Software Testing KA, §5-2)

---

### 7. Use behavioral models (state machines, interaction diagrams) as the source for test generation
Draw on formal or semi-formal behavioral models — state machines, sequence diagrams, statecharts — as the authoritative source for understanding and generating test scenarios for state-dependent behavior.

> (source: "[SWEBOK excerpt 9f6e3a7fc5c262cdb78d]." — SWEBOK v4, Software Engineering Models and Methods KA, §2.2)

---

### 8. Consider scenario-based testing to validate behavioral aspects
Use scenario-based testing as a complementary technique to generate test cases focused specifically on the SUT's behavioral aspects, ensuring that both typical and alternate workflows/event sequences are covered.

> (source: "[SWEBOK excerpt e41ffd571d00f5662528]." — SWEBOK v4, Software Testing KA, §3.1.8)

---

### 9. Consider tool support for automated test case generation from state models
When the state model is formally defined, consider using test case generation tools that can automatically derive test inputs from the model; note, however, that determining expected outputs may still require additional domain expertise.

> (source: "[SWEBOK excerpt 187a6ec12533484420c5]." — SWEBOK v4, Software Requirements KA, §8.3)

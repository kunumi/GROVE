## What the Team Should Have Been Tracking and Preserving

### 1. Place all software configuration items (SCIs) — including source code, executable code, code libraries, and software tools — under SCM control

Everything that contributes to the final executable is a candidate SCI. SWEBOK explicitly lists source and executable code, code libraries, software tools, and even build-supporting compilers as items that should be identified and controlled.

> (source: *"[SWEBOK excerpt ae8c53959623d22d6586]."*)

---

### 2. Place the supporting toolchain (compilers, linkers, etc.) and build instructions under SCM control

The toolchain version is just as important as the source code for exact reproduction. SWEBOK is explicit that if supporting tools are not under SCM control, reproducing a previous build is not possible.

> (source: *"[SWEBOK excerpt c30bb1e8c1e31553eba4]."*)

---

### 3. Maintain the capability to reproduce previous releases

SCM must be designed with historical reproduction as an explicit goal, not an afterthought. This applies to recovery, testing, maintenance, and support of customers on older versions.

> (source: *"[SWEBOK excerpt ed245abb0f39c360af98]."*)

---

### 4. Preserve build outputs for future reference — they are quality, security, and compliance records

The compiled executable itself should be archived. Build outputs are not throw-away artifacts; they can serve as records long after the release.

> (source: *"[SWEBOK excerpt f4cf664ac0e97bee7d81]."*)

---

### 5. Produce and retain a Software Bill of Materials (SBOM) for every build

The SBOM records exactly what artifacts — including third-party libraries — went into the build, making it possible to reconstruct the dependency set precisely.

> (source: *"[SWEBOK excerpt 450578f233490c4cd9fa]."*)

---

### 6. Create and retain a Version Description Document (VDD) for every release

The VDD is the formal record of a release's physical contents. Without it, the team cannot know which variants of which items were actually shipped.

> (source: *"[SWEBOK excerpt 5216687143d81e73b53d]."*)

---

### 7. Use a binary/artifact repository to store the built executables and libraries from each release

A dedicated repository that retains build artifacts allows the team to retrieve past binaries without having to rebuild them, and to verify them as part of release processes.

> (source: *"[SWEBOK excerpt 93cb0cdc79d239bdea25]."*)

---

### 8. Track and manage the full dependency supply chain, including all direct and indirect third-party libraries

Third-party dependencies (commercial, open-source, etc.) must be version-pinned and tracked as part of the configuration. Any dependency in the supply chain can change between builds if not locked down.

> (source: *"[SWEBOK excerpt 8d648deeba0c8ab516c0]."*)

---

### 9. Implement a mechanism (e.g., digital signature) to verify the integrity of the released artifact

Even if the executable is retrieved from an archive, the team should be able to confirm it is byte-for-byte identical to what was shipped, by comparing against an integrity check recorded at the time of release.

> (source: *"[SWEBOK excerpt e8f6a76a50aac203ea7a])."*)

---

### 10. Use version control to store source code, configuration files, and all related artifacts

Version control is the foundational prerequisite. Without it, there is no reliable way to retrieve the exact source state that corresponded to the shipped executable.

> (source: *"[SWEBOK excerpt 0f85ed080860bc1fbf6b]."*)

---

**Summary:** The common thread across all these guidelines is that **Software Configuration Management (SCM)** must treat reproducibility of past releases as a first-class requirement. That means version-controlling not just source code but also tools, build instructions, dependencies, and configuration data — and separately archiving the resulting binaries and their associated documentation (VDD, SBOM, release notes, integrity checks) so that any past release can be recovered and re-examined exactly as it was shipped.

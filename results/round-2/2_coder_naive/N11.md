Our orders table repeats the customer's name and address on every order row, and after a customer moves some rows show the old address while others show the new one. How should the tables be restructured, and what does that cost when querying the data?

## Guidelines for Restructuring and the Query Cost Trade-off

---

### 1. Recognise that your current design suffers from data redundancy and data inconsistency — the core problems normalization is designed to solve.

The situation you describe (a customer's name and address repeated on every order row, with different rows showing different addresses) is exactly the class of problem that pre-relational, file-based systems suffered from.

> *"[SWEBOK excerpt 8e19146771dc855a42ea]…"*

(source: "[SWEBOK excerpt a1e367440e6bc6654da8]." — SWEBOK v4, §[SWEBOK excerpt 0487d2a93e455e0d14ac])

---

### 2. Apply normalization — the formal process of reorganising tables to remove redundancy and inconsistency.

Normalization is the prescribed remedy. It directly addresses what you are experiencing.

> *"[SWEBOK excerpt 7e1d2d7ec900739f27d1]."*

(source: "[SWEBOK excerpt 7e1d2d7ec900739f27d1]." — SWEBOK v4, §6.4)

---

### 3. Move the customer data into its own table (achieve at least 2NF), eliminating partial dependencies on the order row's key.

Your orders table has customer name and address depending only on the customer, not on the full order key — a partial dependency. 2NF requires this to be broken out.

> *"[SWEBOK excerpt 6d0499536d85be18506b])."*

(source: "[SWEBOK excerpt 6d0499536d85be18506b])." — SWEBOK v4, §6.4)

---

### 4. Also eliminate transitive dependencies to reach 3NF, ensuring every non-key column depends only on the primary key.

If other columns in the orders table depend on the customer rather than the order itself, 3NF removes those remaining transitive dependencies.

> *"[SWEBOK excerpt e6b8f2d0590bc4f09048]."*

(source: "[SWEBOK excerpt e6b8f2d0590bc4f09048]." — SWEBOK v4, §6.4)

---

### 5. Target at least 3NF or BCNF as your end-state, since this is the industry norm.

You do not need to pursue higher normal forms for a typical orders/customers schema.

> *"[SWEBOK excerpt 4e8dc7c159181b00ce14]."*

(source: "[SWEBOK excerpt 4e8dc7c159181b00ce14]." — SWEBOK v4, §6.4)

---

### 6. Use a schema with proper keys and relationships — specifically foreign keys — to link the orders table back to the customers table.

The schema should capture the relationship between tables via keys. A foreign key on the orders table referencing the customers table replaces the repeated customer columns.

> *"[SWEBOK excerpt f8831ad4424a319c25a6]."*

(source: "[SWEBOK excerpt f8831ad4424a319c25a6]." — SWEBOK v4, §6.1 Schema)

---

### 7. Use an RDBMS, which is built precisely to let related tables work together while keeping redundancy low.

An RDBMS natively supports the multi-table, related design you will produce.

> *"[SWEBOK excerpt 5b0471d95085190589f4]…its data tables relate to one another…data redundancy is significantly reduced."*

(source: "[SWEBOK excerpt 7339321b86029242123c]…data redundancy is significantly reduced." — SWEBOK v4, §6.4)

---

### 8. Accept that normalization increases the number of tables and query processing time — this is the known cost.

Splitting customer data out means that retrieving a full order now requires joining two tables instead of reading one. SWEBOK explicitly names this as the trade-off.

> *"[SWEBOK excerpt da4d8a3cc6d262f2b6b8]."*

(source: "[SWEBOK excerpt da4d8a3cc6d262f2b6b8]." — SWEBOK v4, §6.4/§6.5)

---

### 9. If query performance degrades unacceptably after normalization, selectively apply de-normalization — but only after weighing application requirements.

De-normalization is the deliberate re-introduction of redundancy to recover read speed. SWEBOK frames it as a context-dependent decision, not a default.

> *"[SWEBOK excerpt 223a077fa13968df3ba6]."*

(source: "[SWEBOK excerpt 223a077fa13968df3ba6]." — SWEBOK v4, §6.4)

---

### 10. Use SQL to implement all of the above — schema changes, normalizations, and queries across the resulting tables.

SQL is the standard mechanism for creating the new schema, migrating data, and querying across the now-separate tables.

> *"[SWEBOK excerpt 3741815788282f1eb1ef]."*

(source: "[SWEBOK excerpt 3741815788282f1eb1ef]." — SWEBOK v4, §6.5 Structured Query Language)

---

### Summary

| Step | Action | Cost |
|---|---|---|
| Restructure | Move customer data to its own table (2NF/3NF) | Schema migration effort |
| Link | Use a foreign key on orders pointing to customers | None at rest |
| Query | Join orders ↔ customers at read time | More tables → more processing time |
| Mitigate | De-normalise selectively if performance is unacceptable | Reintroduces some redundancy |

All guidance above is drawn directly from SWEBOK v4, Chapter 16 (Computing Foundations), §6.1–6.5.

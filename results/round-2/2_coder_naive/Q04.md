## Strategies for Keeping Software Running Through Runtime Errors

### 1. Practice Defensive Programming
Protect every routine from being broken by invalid inputs. Check the values of all input parameters and decide how to handle bad inputs before they can propagate and cause failures.
> (source: *"[SWEBOK excerpt edaaca9c62404676ff9e]."*)

---

### 2. Use Assertions for Runtime Checks
Place executable assertions in the program — usually as routines or macros — to perform runtime checks and quickly surface mismatched assumptions, modified-code errors, and other problems before they silently corrupt execution.
> (source: *"[SWEBOK excerpt 5911453b0a4f5e43261b]. [SWEBOK excerpt 4b5d09b3a87e6f492d8f]."*)

---

### 3. Apply Design by Contract (Preconditions & Postconditions)
Equip each routine with explicit preconditions and postconditions so that each routine or class forms a verifiable contract with the rest of the program, clarifying exactly what must hold at entry and exit, and enabling controlled responses when conditions are violated.
> (source: *"[SWEBOK excerpt 3371d5be97fc67ae3e08]."*)

---

### 4. Return a Neutral Value on Error
When an error is detected, return a neutral or harmless value so that processing can continue without crashing, rather than propagating the bad state further.
> (source: *"[SWEBOK excerpt 25fb1a8cce8efbace92b]."*)

---

### 5. Substitute the Next Piece of Valid Data
Instead of halting when an invalid data item is encountered, skip over it and resume processing with the next valid piece of data, keeping the system alive and productive.
> (source: *"[SWEBOK excerpt 25fb1a8cce8efbace92b]."*)

---

### 6. Log a Warning Message
When a non-fatal error occurs, log a warning and continue execution. This keeps the software running while creating an auditable record of the problem for later investigation.
> (source: *"[SWEBOK excerpt 25fb1a8cce8efbace92b]."*)

---

### 7. Return an Error Code to the Caller
Signal the erroneous condition to the calling code via an error code, allowing the caller to decide how to respond — often by continuing with an alternative path — rather than crashing the entire application.
> (source: *"[SWEBOK excerpt 25fb1a8cce8efbace92b]."*)

---

### 8. Use Structured Exception Handling (try-catch-throw)
Throw exceptions when unexpected conditions arise and catch them in try-catch blocks that either [SWEBOK excerpt c1de2b80a401caa76c67], preventing unhandled failures from terminating the program.
> (source: *"[SWEBOK excerpt aa95fcd1c82d33a12fdb] try-catch [SWEBOK excerpt 980c1713bcc05a3281c2]."*)

---

### 9. Follow Sound Exception-Handling Policies
Design exception handling carefully: include in every [SWEBOK excerpt e81da8c796379196c06a], avoid empty catch blocks, know the exceptions that library code throws, build a centralized exception reporter, and standardize the program's use of exceptions.
> (source: *"[SWEBOK excerpt 8a98e7d1cb740854b979]."*)

---

### 10. Back Up and Retry on Failure (Fault Tolerance)
When an operation fails, save state and retry it. This is one of the most common fault-tolerance strategies for recovering from transient or intermittent errors without terminating the system.
> (source: *"[SWEBOK excerpt 7c7c13df07628c3c7d07]."*)

---

### 11. Use Auxiliary Code and Voting Algorithms (Fault Tolerance)
Run multiple independent implementations of a function and compare (vote on) their outputs. If one produces an erroneous result, the majority vote keeps the system producing a correct or acceptable answer.
> (source: *"[SWEBOK excerpt 7c7c13df07628c3c7d07]."*)

---

### 12. Replace an Erroneous Value with a Benign Phony Value (Fault Tolerance)
Substitute an erroneous computed value with a safe, pre-approved placeholder value that will have a benign effect on the rest of the system, allowing execution to continue without propagating a bad result.
> (source: *"[SWEBOK excerpt 7c7c13df07628c3c7d07]."*)

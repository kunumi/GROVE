### Question

Each new version of our web service is switched on for every user at the same moment, so a single faulty version breaks the service for everyone and getting the previous version back takes hours. How should we change the way new versions go live to limit the damage?

# Guidelines for Safer Version Rollout

1. **Automate your deployment pipeline end-to-end.** Replace manual deployment steps with a fully automated pipeline that packages code, generates configuration files, restarts servers, configures databases, and installs software. Automation reduces human error and makes every release step repeatable and consistent.
(source: Software Testing, Operations, and Maintenance/Software Operations and Maintenance Practices/Deployment Automation and Infrastructure Management/Containers and Virtualization for Application Scalability.md)

2. **Use canary releases instead of full cutover.** Deploy the new version to only a small subset of users or infrastructure first and evaluate it before proceeding to a complete deployment. This limits blast radius: if the canary behaves badly, most users are unaffected.
(source: "[SWEBOK excerpt d8f6ea40078561c9b855].")

3. **Implement automated surveillance and rollback.** Configure automated monitoring to watch the newly deployed version and trigger an automatic rollback if it misbehaves, so that recovery does not require hours of manual intervention.
(source: "[SWEBOK excerpt b21e029debd98a49de44] … [SWEBOK excerpt 81dd40d2cb4a87afdc1c]")

4. **Plan and rehearse rollback before every release.** Software engineers should ensure that when a new version and its databases have been deployed, [SWEBOK excerpt af227531db1e59fca6f4]. The rollback must be planned and rehearsed before going live, not invented after a failure.
(source: Software Testing, Operations, and Maintenance/Software Operations and Maintenance Practices/Software Rollback and Problem Resolution in DevOps.md)

5. **Use feature toggles (application-based release strategy).** Rather than deploying all functionality at once to all users, use configuration toggles to enable or disable specific sections of code, so that new behaviour can be switched on incrementally and switched off instantly if problems arise.
(source: "[SWEBOK excerpt 903a8e172cabfed304df].")

6. **Use a staging environment (environment-based release strategy).** Deploy the new version first to a staging environment that mirrors production. Only promote it to production after validation in that environment, reducing the risk of a faulty version reaching all users.
(source: "[SWEBOK excerpt ad92aa262399034cbb8e] … [SWEBOK excerpt fe380341d50e5ebb2893].")

7. **Keep all environments built from a single source of truth.** Ensure development, QA, staging, and production environments are all created from the same code repository, ideally through automated Infrastructure as Code (IaC). Drift between environments is a leading cause of failures that only appear in production.
(source: "[SWEBOK excerpt 6e52404746b0c1014118]")

8. **Practice continuous testing at every stage of delivery.** Integrate automated testing throughout the pipeline — unit, integration, regression, and smoke tests — so faults are caught before the version reaches users rather than after.
(source: "[SWEBOK excerpt cce6d8b9982c10da754e].")

9. **Use smoke testing immediately after deployment to verify the new version is operational before releasing it to all users.** Smoke testing (also called Build Verification Testing) ensures core functionalities behave properly and prevents failures caused by improperly built artifacts or packages.
(source: "[SWEBOK excerpt 5fe668ba1d5cf683741b] … [SWEBOK excerpt cdb8c00b4e5b88dc3aac]).")

10. **Implement product telemetry and real-time monitoring as a continuous feedback loop.** Collect and analyse data from all layers (application, OS, infrastructure) in real time so that problems in production are detected immediately, reducing the window between a fault going live and the team knowing about it.
(source: "[SWEBOK excerpt 50e8e9933c27fed2594b] … [SWEBOK excerpt e9a2a8eb3785dc1bd4dd]")

11. **Plan release and rollback strategy as part of requirements and operations planning, not as an afterthought.** Assess the risk of each [SWEBOK excerpt 582f25eec98f7dd05ee1] before the release goes out, and inform all stakeholders of the plan.
(source: "[SWEBOK excerpt bd963a0cb170a71425a3].")

12. **Architect the service to allow small, independent deployments.** Software applications must be architected so that individual features or fixes can be deployed independently of one another, rather than bundling many changes into a single large release that is hard to roll back.
(source: "[SWEBOK excerpt 92872fada22ddbddd871]")

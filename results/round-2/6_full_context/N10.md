### Question

I am handing over a finished system to a client whose in-house team will keep developing it after delivery. Besides the program itself, what written material should I prepare for the client, for its end users and for my own organization, and for how long should it be retained?

Answer with a list of guidelines. After each guideline, cite the source it comes from: the path of the SWEBOK file if you have it, otherwise a verbatim quote of at least 8 words from the passage, in the form (source: ...).

### Answer

# Guidelines for Documentation at System Handover

## For the Client's In-House Development Team

1. **Provide a software requirements specification** that captures the intent of every feature, so maintainers who were not the original authors can determine what the code is *intended* to do, not just what it does.
(source: Requirements Validation and Management/Requirements Traceability and Bidirectional Traceability/Traceability Between Software Requirements and Design Elements.md)

2. **Provide a software architecture description (AD)** targeted at [SWEBOK excerpt 6d8bfac69c8dc580828c], so it serves as a blueprint to guide continued development.
(source: Foundations of Software Architecture/Software Architecture_ Foundations, Views, and Patterns/Architectural Concerns, Views, and Viewpoints/Software Architecture Descriptions and Documentation/Architecture Documents Guide Software System Construction.md)

3. **Provide software design documents**, including the rationale for each nontrivial design decision — what alternatives were considered, what trade-offs were analysed, and what was rejected and why — so future maintainers are not compelled to repeat discarded choices.
(source: Software Design Concerns, Documentation, and Modeling/Recording Design Rationale for System Maintainability.md)

4. **Provide the full test suite and test documentation**, including test design specifications, test case specifications, test procedure specifications, test execution logs, and incident reports, all under configuration management and at the same quality level as other engineering documentation.
(source: Testing Methodologies and Quality Assurance Practices/Software Testing Techniques, Measurement, and Management/Dynamic Test Documentation Components and Management.md)

5. **Provide source code with meaningful comments and conformant coding standards**, because [SWEBOK excerpt 885f69914bb3c8b25e9a] and the developers who maintain the system will differ from those who built it.
(source: Data Systems, Networks, and Computational Foundations/Wireless Networks, Security, and Intelligent Systems/Writing Maintainable and Readable Code/Developer Human Factors in Software Maintenance.md)

6. **Provide a traceability record** linking each requirement forward to design elements, code units, and test cases, and backward to source documents such as standards and system requirements, so the client's team can assess the impact of any proposed change.
(source: Requirements Management, Quality, and Testing Practices/Requirements Traceability and Change Impact Analysis/Traceability in Software Requirements and Design.md)

7. **Provide an operations and maintenance plan** (or concept of operations, CONOPS) prepared during development, specifying the scope of maintenance, the adapted processes and tools, the identity of the maintenance organisation, and estimated maintenance costs.
(source: Software Testing, Operations, and Maintenance/Software Operations and Maintenance Practices/Software Engineering Operations Planning and CONOPS Development.md)

8. **Provide software configuration management (SCM) records**, including baseline identification, change history, version description documents (VDDs), and Software Bill of Materials (SBOM) for all build artefacts, so the client's team can reproduce any past release.
(source: Software Maintenance and Configuration Management/Software Configuration Management Planning and Implementation/Software Configuration Management Tools and Processes/Software Build Artifacts and Continuous Integration Processes.md)

9. **Provide impact analysis procedures and a change request process**, including the forms, categorisation scheme, and escalation path, so the in-house team can process modification requests and problem reports in a controlled way from day one.
(source: Software Testing, Operations, and Maintenance/Software Operations and Maintenance Practices/Software Maintenance Request and Problem Report Procedures.md)

10. **Document technical debt explicitly**, identifying its extent, the cost of addressing it, and its impact on the business, so the inheriting team can make informed decisions about refactoring versus new development.
(source: Software Testing, Operations, and Maintenance/Software Operations and Maintenance Practices/Software Maintenance Management and Organization/Software Maintainability and Technical Debt Management/Technical Debt in Software Engineering.md)

## For End Users

11. **Provide a user manual** (or equivalent) describing safe and unsafe use of the software, how to protect sensitive information, an explanation of warnings and critical procedures, and enough detail to let users determine whether the software meets their needs.
(source: Professional Practice and Collaboration in Software Engineering/Professional Responsibility and Intellectual Property in Software Engineering/Documentation and Requirements Trade-off Management/Documentation Standards and Requirements for Software Engineers.md)

12. **Provide installation and upgrade instructions**, including platform requirements necessary for proper product operation and any known problems, as captured in release notes.
(source: Software Maintenance and Configuration Management/Software Configuration Management Planning and Implementation/Software Configuration Management Tools and Processes/Release Management Tools and Documentation Requirements.md)

13. **Document all warnings of undesirable or dangerous consequences** from use or misuse of the software, as this is an explicit professional obligation of the software engineer.
(source: "[SWEBOK excerpt 03093f1055a52d120f04]" — Professional Practice and Collaboration in Software Engineering/Professional Responsibility and Intellectual Property in Software Engineering/Documentation and Requirements Trade-off Management/Documentation Standards and Requirements for Software Engineers.md)

## For Your Own Organisation

14. **Archive all project materials** — source code, test cases, design documents, plans, measurement data — in accordance with stakeholder-agreed rules covering archival method, location, duration, and destruction of sensitive information.
(source: Software Quality Management and Project Oversight/Software Measurement and Organizational Learning/Project Closure and Archival Procedures.md)

15. **Conduct and record a project retrospective** (post-mortem), analysing issues, risks, and opportunities encountered so that lessons learned feed organisational improvement.
(source: Software Quality Management and Project Oversight/Software Measurement and Organizational Learning/Software Engineering Measurement and Organizational Learning.md)

16. **Update the organisation's measurement database** with relevant project data — size, effort, defect counts, schedule variance — so it can serve as historical input for calibrating future estimates.
(source: Software Quality Management and Project Oversight/Software Measurement and Organizational Learning/Software Engineering Measurement and Organizational Learning.md)

17. **Record all problems encountered during development**, as this is an explicit documentation obligation to other elements of your own development organisation.
(source: "Problems encountered during the development process" — Professional Practice and Collaboration in Software Engineering/Professional Responsibility and Intellectual Property in Software Engineering/Documentation and Requirements Trade-off Management/Documentation Standards and Requirements for Software Engineers.md)

---

## Retention Period

18. **Retain documents for at least the full service life of the software**, or for the duration required by relevant organisational or regulatory requirements, whichever is longer.
(source: "[SWEBOK excerpt 3195bf83cb2eca8378f7]." — Professional Practice and Collaboration in Software Engineering/Professional Responsibility and Intellectual Property in Software Engineering/Documentation and Requirements Trade-off Management/Documentation Standards and Requirements for Software Engineers.md)

19. **Place all documentation under configuration management**, subjecting it to the same change-control discipline as the code itself, so the currency and integrity of every document is verifiable throughout the retention period.
(source: Requirements Engineering_ Elicitation, Analysis, and Specification/Requirements Specification and Validation Techniques/Configuration Management and Requirements Specification Techniques.md)

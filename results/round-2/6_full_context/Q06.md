A function takes six configuration parameters, each with several possible values, and testing every possible mix of their values is too expensive. How should the test cases be derived?

# Guidelines for Deriving Test Cases When Exhaustive Testing Is Too Expensive

## 1. Use Combinatorial Test Techniques to systematically cover subsets of parameter combinations

Rather than testing all possible combinations (all combinations testing), apply techniques such as **Pairwise Testing** (also called t-wise testing), which ensures every pair of parameter values appears together in at least one test case, or **Each Choice Testing** and **Base Choice Testing** for even more selective coverage. These techniques drastically reduce the number of test cases while maintaining meaningful coverage.

(source: Software Requirements_ Foundations and Engineering Practices/Software Requirements Engineering Fundamentals/Guide to the Software Engineering Body of Knowledge V4/SWEBOK Guide Version 4.0 Overview/SWEBOK Guide Version 4.0a Table of Contents.md — table entry listing "3.1.4. Combinatorial Test Techniques")

## 2. Apply Pairwise (Orthogonal Array) Testing specifically

Pair-wise testing derives test cases [SWEBOK excerpt 2478693199cb1b3f397b], and is also known as **orthogonal array testing (OAT)**. For six parameters this yields far fewer test cases than full Cartesian coverage while still exposing interaction faults between any two parameters.

(source: "[SWEBOK excerpt 324ebdd23fd9449b89a0]. Extend to t-wise testing if pairwise coverage is insufficient

If pairwise coverage seems too weak for the criticality of the software, extend to **t-wise testing** (e.g., 3-wise or higher), which considers every possible combination of *t* inputs rather than just pairs, increasing fault-detection capability incrementally without jumping to full exhaustive testing.

(source: "[SWEBOK excerpt 7b14e51185467d0e7f48].")

## 4. Use Equivalence Partitioning to reduce the number of distinct values per parameter

Before applying combinatorial techniques, partition each parameter's value domain into equivalence classes so that one representative value stands in for all values in the class. This reduces the size of the value space that the combinatorial technique must cover.

(source: "[SWEBOK excerpt e279d64d08518504c456] criterion or relation... [SWEBOK excerpt 83b36aaa6987b9eb0caf].")

## 5. Apply Boundary Value Analysis to select the most fault-revealing values within each partition

For each parameter's equivalence classes, choose values **on or near the boundaries** of the domain, since many faults tend to concentrate near extreme values. This ensures the representative values chosen for combinatorial testing are the ones most likely to reveal defects.

(source: "[SWEBOK excerpt bedee61fb08d8b967278].")

## 6. Use Decision Tables to capture and verify the logical relationships among parameter values

Document the conditions (parameter values) and resulting actions in a **decision table** to make the combinatorial logic explicit, detect missing combinations, and confirm that the selected test cases cover the most important condition-action relationships.

(source: "[SWEBOK excerpt a11245cd76e2da148e79])... [SWEBOK excerpt d020abbdbdf02c227d05].")

## 7. Combine functional (specification-based) and structural techniques

Do not rely on a single technique. Combinatorial/specification-based techniques and structure-based (white-box) techniques are **complementary**, using different sources of information and highlighting different problems. Applying both improves overall effectiveness within the available test budget.

(source: "[SWEBOK excerpt 5957a5d79fa90b756cf0].")

## 8. Define explicit test adequacy criteria to know when enough tests have been derived

Establish a **coverage criterion** (e.g., 100% pairwise coverage of all six parameters) as the stopping condition, so that the test suite is demonstrably sufficient for the stated objective rather than arbitrarily sized. Coverage may be measured as a percentage of covered pairs, triples, etc.

(source: "[SWEBOK excerpt 5f9d809b681a2084eb63] [SWEBOK excerpt 36a251903b1af4a988d3].")

## 9. Apply test case prioritization so the most valuable combinations are executed first

If schedule or resources force further reduction, **prioritize test cases** so those covering the most critical parameter interactions or the highest-risk combinations run first, ensuring that partial execution still yields the greatest fault-detection value.

(source: "[SWEBOK excerpt 26964290c52f9f61cbcd].")

## 10. Use tool support to generate and manage the combinatorial test suite

Because manually computing pairwise or t-wise test suites for six parameters is error-prone, employ **test generation tools** that accept parameter definitions and automatically produce minimal covering arrays. Such tools may also check coverage criteria automatically.

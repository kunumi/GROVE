### Question

How can a routine make its assumptions about inputs and outputs explicit and guard itself against callers passing it values it was not built to accept?

### Answer

Here are guidelines for making a routine's assumptions explicit and guarding against invalid inputs, drawn from the SWEBOK:

1. **Use assertions to state runtime assumptions.** Place executable predicates in the program—usually routines or macros—that perform runtime checks. [SWEBOK excerpt 4b5d09b3a87e6f492d8f] and enable programmers to flush out mismatched interface assumptions more quickly.
(source: Software Design and Construction Fundamentals/Software Construction and Code Complexity Management/Software Construction Fundamentals and Practices/Software Construction Fundamentals.md — section 4.4)

2. **Apply Design by Contract: specify preconditions and postconditions for each routine.** [SWEBOK excerpt 60153cf94e6d78567b2b]; postconditions are conditions guaranteed true after successful execution. Each routine thereby forms [SWEBOK excerpt 13c5545a4a774df8cb56], precisely specifying its semantics and clarifying its behavior.
(source: Software Construction Techniques and Practices/Assertions and Design by Contract in Programming.md)

3. **Use defensive programming to protect routines from invalid inputs.** Check the values of all input parameters and decide explicitly [SWEBOK excerpt 7982520cf6f2b2330cf6].
(source: Software Construction Techniques and Practices/Contract Design and Error Handling Strategies/Design by Contract and Defensive Programming.md)

4. **Compile assertions in during development, then compile them out for production.** [SWEBOK excerpt c5565f3a6c5ab368cd9d] so they don't degrade performance, allowing the routine to be thoroughly checked during development without runtime cost in production.
(source: Software Construction Techniques and Practices/Assertions and Design by Contract in Programming.md)

5. **Define invariants for conditions that must hold throughout execution.** [SWEBOK excerpt ee8b9640b384f5fd9a11]—[SWEBOK excerpt a151b447fe67e6d786c0]. Identifying invariants makes stable assumptions about the environment explicit.
(source: Software Engineering Processes and Quality Assurance/Semantic Assumptions and Modeling Techniques/Preconditions, Postconditions, and Invariants in Functions.md)

6. **Choose an explicit, defined error-handling strategy for bad inputs rather than ignoring them.** Common techniques include [SWEBOK excerpt fab09da3601a283baf81]. The choice should be consistent across the codebase.
(source: Software Construction Techniques and Practices/Contract Design and Error Handling Strategies/Error Handling, Exception Handling, and Fault Tolerance.md)

7. **Use exception handling with carefully designed policies.** Include [SWEBOK excerpt e56492e15b911c91a518], avoid empty catch blocks, know the exceptions library code throws, and standardize the program's use of exceptions so that callers receive meaningful, structured feedback when a routine's assumptions are violated.
(source: Software Construction Techniques and Practices/Contract Design and Error Handling Strategies/Error Handling, Exception Handling, and Fault Tolerance.md)

9. **Apply coding standards that restrict complex or difficult-to-understand language structures**, supporting the goal of constructing for verification. Straightforward code makes assumptions easier to audit and reduces the chance that implicit, undocumented assumptions slip through.

# Guidelines for Deciding What to Test After a System Change

## 1. Perform Regression Testing to Verify Modifications Have Not Caused Unintended Effects

After any modification, selectively retest the software to verify that changes have not introduced unintended effects and that the software still complies with its specified requirements. This applies at every test level (unit, integration, system, acceptance).

(source: Software Testing, Operations, and Maintenance/Testing Across Development Processes and Domains/Testing in Traditional Software Development Processes.md)

---

## 2. Plan Regression Testing Early and Coordinate It Carefully

Test planning for regression testing must occur as part of modification request (MR) and problem report (PR) processing. Coordinating regression tests can be challenging when team members are simultaneously working on different problems, so it must be explicitly planned.

(source: "[SWEBOK excerpt 6eea244a0b2813f823ff].")

---

## 3. Conduct Impact Analysis Before Deciding What to Test

Before deciding the scope of retesting, perform an impact analysis to identify all systems and software products affected by the change, estimate the resources needed, and determine the risks involved. The impact analysis identifies which components are affected and informs which tests are needed.

(source: Software Testing, Operations, and Maintenance/Software Operations and Maintenance Practices/Impact Analysis in Software Maintenance.md)

---

## 4. Use Traceability to Establish the Footprint of a Change

Trace the changed requirement or component forward to its linked design elements, then to code, then to test cases. This traceability "footprint" establishes the volume of work and identifies the specific test cases that need to be re-executed after the change.

(source: Requirements Management, Quality, and Testing Practices/Requirements Traceability and Change Impact Analysis/Tracing System Changes Through Requirements and Design.md)

---

## 5. Apply Test Case Selection and Minimization to Reduce the Retesting Set

Rather than re-running the entire test suite, use test case selection criteria to identify the most relevant subset, and apply minimization techniques to remove redundant test cases. Prioritize test cases by [SWEBOK excerpt 5983e22ff41fd7a4b559] that higher-priority tests run first.

(source: Software Development Systems and Quality Assurance/Software Construction Testing and Quality Assurance/Test Case Minimization and Testing Purposes.md)

## 6. Use Risk-Based Prioritization to Focus Retesting Effort

After a change, apply risk-based testing: use [SWEBOK excerpt 04a172faef32829f6012] so that the most critical areas are verified first. The resources devoted to retesting [SWEBOK excerpt dce2fe3eeafa2f723fa4].

## 7. Automate Regression Testing to Manage the Risk at Scale

In Agile, DevOps, and continuous integration environments, regression testing should be automated to manage the regression risk continuously. Automated builds should trigger regression test execution immediately after each integration, so errors are caught as quickly as possible.

(source: Software Testing, Operations, and Maintenance/Testing Across Development Processes and Domains/Testing Strategies Across Methodologies and Domains/Test Automation and Domain-Specific Testing Approaches.md)

---

## 8. Run Quick Smoke Tests First to Confirm Testability Before Full Regression

Before releasing to the operational stage or running a full regression suite, apply smoke testing (Build Verification Testing) to ensure the core functionalities behave properly and that the build is stable enough for planned testing to begin. This prevents wasted effort on a broken build.

(source: Testing Methodologies and Quality Assurance Practices/Testing Approaches and Execution Strategies/Informal and Modern Testing Approaches/Advanced Software Testing Techniques and Practices.md)

---

## 9. Keep Test Documentation Under Configuration Management and Update It With Each Change

Test documentation should be continuously updated when requirements or design change, and must be kept under configuration management. Test reports from each cycle also serve as inputs to the change management request process, linking the testing outcome back to the change that triggered it.

(source: Testing Methodologies and Quality Assurance Practices/Software Testing Techniques, Measurement, and Management/Dynamic Test Documentation Components and Management.md)

---

## 10. Retest As Early in the Lifecycle as Possible (Shift Left)

The shift-left principle dictates that testing should happen in the earliest stages of development after a change, not only at the end. For internal code quality, this means focusing on unit testing and integration testing using structure-based techniques immediately after a change is introduced.

(source: Software Testing, Operations, and Maintenance/Testing Across Development Processes and Domains/Testing Aspects in Shift-Left Development.md)

---

## 11. Bring Software Back Online for Testing Only When Justified, Using Special Techniques If Necessary

If the software performs critical functions, bringing it offline to retest after a change can be difficult. In such cases, use production-safe techniques such as canary testing or dark launches to validate changes with limited exposure before full deployment.

(source: Software Testing, Operations, and Maintenance/Software Operations and Maintenance Practices/Software Installation and Operational Verification Processes/Production Environment Testing and Verification/Production System Testing Challenges and Techniques.md)

---

## 12. Assess Test Completion Criteria After Each Change Before Moving On

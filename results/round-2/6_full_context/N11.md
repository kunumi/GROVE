### Question

Our orders table repeats the customer's name and address on every order row, and after a customer moves some rows show the old address while others show the new one. How should the tables be restructured, and what does that cost when querying the data?

# Guidelines for Restructuring Repeated Customer Data in an Orders Table

## 1. Separate the Customers and Orders into Distinct Tables
Remove the customer's name and address from the orders table and place them in a dedicated customers table with a unique customer identifier. The orders table then stores only a foreign key reference to that customer. This directly eliminates the update anomaly where some rows show an old address after a customer moves.

(source: "[SWEBOK excerpt 239722639564d77c4725]." — Software Requirements_ Foundations and Engineering Practices/Software Requirements Engineering Fundamentals/Guide to the Software Engineering Body of Knowledge V4/SWEBOK Guide Version 4.0 Overview/Software Engineering Body of Knowledge Guide Version 4.0a.md, via the Software Design KA section on Data modeling methods)

## 2. Apply Database Normalization to Remove Redundancy
Specifically reach at least Second Normal Form (2NF) and Third Normal Form (3NF). 2NF requires that there be no partial dependency, and 3NF requires that transitive dependencies be removed. Customer name and address are properties of the customer, not of the order, so they must not appear in the orders table.

(source: "Second normal form (2NF): The table should be in 1NF; [SWEBOK excerpt 7781756225e2e1519efa]). Third normal form (3NF): The table should be in 2NF. Transitive dependencies are removed.")

## 3. Use a Primary Key on the Customers Table and a Foreign Key on Orders
Assign a unique primary key to each customer row. The orders table references it via a foreign key. This ensures that each customer's address is stored in exactly one place, so updating it once is reflected in all associated orders.

(source: "[SWEBOK excerpt f8831ad4424a319c25a6].")

## 4. Recognize That Normalization May Increase Query Complexity and Time
After separating the tables you must join them when querying. The SWEBOK explicitly warns that [SWEBOK excerpt c9d9a77c15a30424d7be], so this cost must be accepted or mitigated.

(source: "[SWEBOK excerpt dcc2e209b0b3cb78f45c].")

## 5. Consider Selective De-normalization for Performance-Critical Queries
Where the join cost is unacceptable for high-frequency queries, controlled de-normalization — deliberately reintroducing some redundancy — can restore performance. This trade-off must be justified by the specific application requirements.

(source: "[SWEBOK excerpt 548a0049dac977c4a9e6].")

## 6. Manage the Structural Change Under Configuration Control
Any change to the schema is a change to a software work product. It should go through change control, impact analysis, and version tracking just like source code, because related queries, stored procedures, and application code that reference the old schema will need updating.

(source: "[SWEBOK excerpt 647b14357e850a6cd91c].")

## 7. Update Traceability Across All Affected Components
After restructuring, trace the impact to every query, report, stored procedure, and application module that previously read customer name and address directly from the orders table. Failing to do so is a common source of post-change defects.

(source: "[SWEBOK excerpt 09129ea3abe388128588].")

## 8. Validate the Restructured Design Against Original Data Requirements
After restructuring, verify that every data item that stakeholders need can still be retrieved correctly, that no data has been lost, and that the semantic meaning of each field is preserved in its new location.

(source: "[SWEBOK excerpt 6b11851ae229cfc2ccf7]… [SWEBOK excerpt 6691ebae76e4cd85301c].")
